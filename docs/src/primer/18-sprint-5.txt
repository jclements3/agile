== Sprint 5: Grading the requirements, and a trace that defends itself {#sprint-5}

::: bridge
You know: requirement review comments, and the trace matrix you rebuild before each review.

Here it is called: the recipe check and the trace gate.

What is new: the trace defends itself: a change that breaks it cannot merge.
:::

::: survival
What you have: a model whose structure is nearly closed, a pipeline that checks every change, a model site the
program office has seen once, and a team that has started to trust the checks ([[sprint-4]]).

What you need from this chapter: how the team turned two questions into machinery -- *are the requirements we
inherited good enough to verify?* and *can we stop a change that quietly breaks the trace?* -- and how a mistake
that used to survive until the next milestone review was caught in four minutes on a Friday morning.
:::

=== The question this sprint answered {#sprint-5-question}

Every sprint chapter in this part starts with the systems-engineering question the team answered, because that is
how the team learned to start every sprint. Sprint 5's question was one Jim kept coming back to after the sprint 4 review, where the program manager had
opened the model site on a phone and said they had never seen the model without a briefing: *if the model is
checked, what is it checked against? If the requirements are weak, a checked model is a well-organized mistake.*

The question was fair, and it split into two questions the team could work on:

1. **Are the requirements good enough to be verified?** Not "are they right" -- that is the stakeholders' call -- but
   are they written so that someone could design to them and test them? That is what the requirement recipe
   ([[recipe]]) measures.
2. **Can the model defend its own trace?** By now the pipeline *reported* trace gaps on every merge request:
   requirements nothing satisfies, requirements nothing verifies, text that differs from DOORS. Reporting is not
   the same as preventing. Nothing stopped an engineer from deleting a `satisfy` line by accident.

The mood had turned. The pulse survey at the sprint 4 retrospective came in at
{{value: docs/tidewater/sprints/04/morale.json mean}} out of 5, up from the sprint 3 dip; Bob, who had asked in
week one why they could not just send the Word document, now opened merge requests without being asked. The team
was not yet enthusiastic. It was, in Jim's words at the kickoff, "past the point of wanting to go back."

=== Week 1: clutter out, a ratchet in {#sprint-5-week-1}

==== Tuesday and Wednesday: the Legacy Import package {#sprint-5-legacy}

The drop-1 model carries a package called *Legacy Import*: the residue of the document port years ago. It holds a
duplicated block (`Battery_old`), a copy of a subsystem (`Copy of SensorSuite`), an unused placeholder
(`TBD Component`) and a "requirement" that is really a slide title. [[cameo]] measured it as part of the spider
web.

Tom's task (#102) was to remove it from the government's v2 model. Jim's task (#103) was to ask the prime to remove
it from the v1 model, as discrepancy report DR-5.

The thought process behind doing both is worth spelling out, because it is the pattern for every piece of clutter
the team inherits:

- **Deleting it in v2 alone is not enough.** The Legacy Import file is converter output. It lives on the vendor
  branch ([[pipeline]]), and every future prime drop will bring it back. Git will see the government's deletion on
  `develop` and the prime's unchanged copy on `vendor/prime`, and every drop merge will raise a delete/modify
  question until the prime deletes it upstream.
- **Waiting for the prime alone is not enough either.** The clutter inflates the spider-web measures, confuses
  every new reader, and the prime's next drop is weeks away.
- **So: delete it now, and file the DR.** The deletion makes the government's model clean today. The DR makes the
  problem the prime's to fix, with an id both sides can cite. When the prime's drop finally removes the package,
  the conflict disappears on its own.

Tom's merge request, !16, removed the package. Its pipeline went green on the first run. Jim sent DR-5 the same
morning:

{{include-md: docs/tidewater/sprints/05/samples/discrepancy-report-DR-5.md}}

Notice what the DR does not say. It does not say *you made a mess*. It names the elements, says why they are a
problem, and asks for one concrete action. A discrepancy report is an engineering request between two teams that
will work together for years; write it the way you would want to receive it.

You can see the deletion in the team's history. In the Tidewater sandbox, from Tom's clone:

```sh run sandbox=tidewater cwd=work/tom expect="Remove the Legacy Import clutter"
git checkout -q develop
git log --oneline -3 -- model/legacy
```

The second line of the output is the drop-1 import that created the file; the first is Tom's removal. That is the
whole history of the package in the government's model: arrived with the prime's drop, left by a reviewed merge
request. Compare that with the Cameo years, when a package like this could be deleted from a shared model by anyone
with a license and nobody would know who or why.

==== Friday 4 December: the trace becomes a ratchet {#sprint-5-ratchet}

One job in the pipeline changed this week, in Tom's story TW-93. Until then, the `trace` job reported gaps and was allowed to fail:
red in the job list, green for the merge. The reason was sound. The model inherited gaps that only the prime can
close -- requirements the v1 model never satisfied, never verified, or worded differently from DOORS -- and a gate
that failed on every one of them would have blocked every merge request the team ever opened.

The ratchet keeps that reason and adds a rule: **a merge request may not make the trace worse.** The job runs the
trace twice -- once on the merge result, once on the target branch -- and compares the *sets* of orphan, unverified
and drifted requirement ids. A gap that is already on `develop` is old news and is reported. A gap that this change
adds fails the job, names the requirement, and blocks the merge.

!17 put the ratchet in. Its own pipeline was green. The interesting part came a week later.

::: sidebar The decision: gate, ratchet, or report
The team considered three designs before Tom wrote a line, and the reasoning is the part to copy.

**Make the trace a hard gate.** Every orphan, every unverified requirement, every drifted text fails the merge
request. Clean, simple, and unusable: the inherited gaps would fail every merge request until the prime fixed its
model, which could take months. Within a week someone would set the job to `allow_failure`, and the gate would be a
decoration.

**Keep reporting.** Leave the job allowed to fail and trust people to read it. That is what the team had been doing
since sprint 3 ([[sprint-3]]). It works until the day someone is in a hurry, and a reporting job that is always red
trains everyone to ignore red.

**Ratchet.** Fail only on what this change makes worse. The inherited gaps stay visible in every report and on the
model site; a new gap blocks the merge and names the requirement. The cost is complexity in the job -- it has to
check out the target branch and run the trace twice -- and one subtle requirement: the comparison must be between
*sets of requirement ids*, not counts. A change that fixes one orphan and creates another leaves the count the same
and the model worse; a ratchet that compared counts would let it through. Test your ratchet with exactly that case.

The same pattern -- report everything, block only what gets worse -- is how the team handles every inherited
problem: outline violations, complexity, recipe findings. It is the single most useful idea in this sprint.
:::

=== The recipe: grading the requirements {#sprint-5-recipe}

The story *Grade our requirements with the recipe* (TW-94) is the engineering heart of the sprint. The recipe
([[recipe]]) describes a requirement as a single sentence with up to eighteen parts, six of them required, and lists
the target verbs that are rarely verifiable ("provide", "have", "be", "be able to"). `req-recipe.pl` reads each
requirement, decomposes it into those parts, and reports what is missing or weak.

Jim ran it on the three DOORS modules -- the stakeholder needs, the system requirements and the segment
requirements -- in the government's model, where the DOORS text lands unchanged. You can run the same command in the
Tidewater sandbox:

```sh run sandbox=tidewater cwd=work/jim expect="requirements=30 findings=15 missing=0"
perl "$KIT/tools/sysml/req-recipe.pl" model/requirements/stakeholder model/requirements/system model/requirements/segment | tail -1
```

The summary line says the DOORS text holds {{count: docs/tidewater/sprints/05/recipe-doors.txt ^TW-}} graded
requirements and that none of them is missing a required part. The findings are about *quality*, not
completeness. Here is the first one in the full report the pipeline kept:

{{include: docs/tidewater/sprints/05/recipe-doors.txt | lines 1-10}}

The network "shall provide marine weather observations." *Provide* how? To whom, how often, within what? A test
engineer cannot write a pass criterion for *provide*. That is not pedantry: it is the difference between a
requirement that can be verified at acceptance and one that will be argued about.

==== Why a discrepancy report, and not an edit {#sprint-5-dr6}

The obvious next step would have been to fix the wording in the model. Jim did not, and the reason is ADR 0008
(*DOORS stays authoritative for requirement text*), recorded in sprint 2 ([[sprint-2]]). The DOORS text is the
prime's, under the contract. If the government rewrites it in the v2 model, the model and DOORS disagree -- which is
exactly the *drift* the trace job exists to catch -- and the next drop will undo the edit anyway.

So the findings went to the prime as DR-6, sent on Tuesday 8 December:

{{include-md: docs/tidewater/sprints/05/samples/discrepancy-report-DR-6.md}}

The DR quotes the tool's summary and four representative findings, and asks for one action. It does not list every
finding: the prime can run the same tool on the same text (it is in the kit) and get the same answer. Making the
check reproducible on the other side is worth more than a long attachment.

You can open the DR in the sandbox's GitLab, as Jim did:

```sh run sandbox=tidewater cwd=. expect="DR-6: Weak verbs"
perl "$KIT/bin/gitlab.pl" --local gitlab --project tidewater/model issue show 110 | head -3
```

Its labels say a lot in a small space: `type::discrepancy`, `owner::prime`, `severity::2`, `area::requirements`,
`phase::port`. Anyone in the program can filter the board for *everything the prime owes us* without a spreadsheet.

==== Why the recipe is not a gate yet {#sprint-5-recipe-gate}

The obvious question once Jim's findings came in was: *should the recipe fail the pipeline?* Not yet, and the reason is ownership. Every finding in the DOORS text is the prime's to fix; a gate on
it would block the government's merge requests for the prime's wording. What the team did instead was add the recipe
to the pipeline as a *report* -- its findings show up in the merge request's code quality widget and as metrics on
the model site -- so that a merge request which *adds* a requirement in the government's own packages can be held
to the recipe in review, and so that the count is visible when the prime's next drop arrives. When the government
writes its own requirements, later in the program, a recipe ratchet on its own packages is the natural next step.

=== Week 2: metadata, a dry run, a tabletop and a catch {#sprint-5-week-2}

==== Monday 7 December: procured parts as metadata {#sprint-5-procured}

Bob's !18 replaced the converter's TODO lines for the v1 `Procured` stereotype with SysML v2 metadata: each
procured part now carries `@Procured { supplier = "..."; partNumber = "..."; }` from the government's Conventions
package. It is a small change with a long tail. Supply-chain questions -- *which parts come from which supplier?* --
become a search over the model instead of a call to the prime ([[security]] returns to this).

The design choice behind it is worth a paragraph, because every v1 profile a team inherits raises the same
question. The v1 model expressed "procured" as a stereotype from a project profile, with the supplier and part number
as tagged values. SysML v2 offers three ways to carry the same information: plain attributes on each part
definition, a specialization of a `ProcuredPart` part definition, or metadata. Bob chose metadata, for two reasons.
Procurement is a fact *about* the part, not a property *of* the system -- the buoy does not behave differently
because its modem came from a particular vendor -- and metadata is the v2 construct for facts about elements. And
metadata is what the kit's checks and views read: the same pattern the level tags use ([[workbook]]). One rule for
all the metadata keeps the model's conventions few enough to remember.

Sprint 4's retrospective had already said *stop estimating procured parts as if they were simple*. Procured parts
carry more than they show: every one needs a look before its metadata can be written, because a v1 profile enforces
that the stereotype is applied, not that its tagged values are consistent or complete.

==== Thursday 10 December: the spillage tabletop {#sprint-5-tabletop}

Tom, as the team's part-time security owner, ran a tabletop with the ISSM (#108): *a marked file has been pushed to
the model repository by mistake. What do you do?* The steps the team walked through are the ones in
[[security]]: stop pushing, tell the ISSM before doing anything else, do not "fix" history yourself (a rewritten
branch on a server does not remove the data from clones, caches and backups), and let the security office decide
the containment.

The issue's record of the tabletop is one line: *Done: Spillage tabletop: a marked file pushed by mistake.* That
is not good enough, and it is worth saying plainly because it is the most common way a tabletop is wasted. Its value
is in what you learned -- who to call, how long the first hour took, what you did not know -- and a closed issue with
no notes preserves none of it. A tabletop's record should hold three bullets: what we did, what surprised us, what we
change.

=== Reading the sprint's own numbers {#sprint-5-analytics}

At every sprint end the pipeline's records go through `gitlab.pl analytics` ([[analytics]]). Sprint 5's report
starts like this:

{{include: docs/tidewater/sprints/05/analytics.txt | lines 1-20}}

Three readings matter, and one of them is a trap.

**The trap: "issue created -> first commit".** The median is the longest stage in the value stream by far. Read
naively, it says the team let issues sit for a week before touching them. Read correctly, it says the team filed
sprint 5's stories and tasks at the sprint 4 refinement and the sprint 5 kickoff, and started each task on its
planned day. That is a queue by design, not a delay. A value stream measures *waiting*; whether the waiting is a
problem depends on whether anybody needed the work sooner.

**The real signal: "MR opened -> first review" and "first review -> merged".** A merge request waited a few hours
for its first review and was merged within minutes of approval. In the document era, a model change waited for a
review board measured in weeks ([[directive]] has the notional baseline). The scorecard's review turnaround,
{{value: docs/tidewater/sprints/05/scorecard.json 10_review_turnaround_hours}} hours, is the same fact.

**Change failure rate: zero.** No merge to `develop` needed a revert or a fix-forward. The one failed pipeline of the
sprint was !20's first run -- a merge request pipeline, which is where failures *should* happen. A failure on a
merge request is the system working; a failure on `develop` is the system missing something. Keep the two apart
when you talk about pipeline health, or a good sprint will sound like a bad one.

=== What went wrong, and what the team did about it {#sprint-5-wrong}

A case study that only reports successes teaches nothing. Sprint 5's problems were small, and each one taught
something.

- **A real `satisfy` was deleted as a duplicate.** Caught by the ratchet on the merge request, fixed in the same
  merge request ([[sprint-5-catch]]). The retrospective turned it into practice: prune trace links from the
  generated trace report, never by eye.
- **The spillage tabletop left no lesson behind.** One closed issue and a one-line comment ([[sprint-5-tabletop]]).
  The fix is a three-bullet record, and it costs five minutes.
- **The intake issue for the first drop is still open.** Tom's stand-up on Friday 11 December still lists *TW-25 intake prime
  drop v1.0 (2026-10-02), by Oct 16* as today's work -- a task due two months earlier. The drop was imported and merged
  in sprint 2; nobody closed the intake issue, so the drafting tool keeps offering it. The analytics for sprint 6
  will list it as the oldest open issue. An issue that is really done but not closed pollutes every report built on
  issues; close what you finish, or the tools will keep reminding you of things that are not true.
- **On-time delivery was seven of eight, not eight of eight.** The quad counts TW-67 as late because it carried over
  from sprint 4 ([[sprint-5-management]]). That is correct. A story that crosses a sprint boundary is late, even
  when nobody did anything wrong. Do not argue with the measure; explain it once.

=== Exercises {#sprint-5-exercises}

::: exercise {#ex-s5-recipe} Grade a module
In the Tidewater sandbox, run `req-recipe.pl` on `model/requirements/segment` alone. Pick the two lowest-scoring
requirements and rewrite them to the recipe, as a reply to DR-6 would ([[recipe]] has the pattern). Check your
rewrites with `req-recipe.pl --strict` on a text file.
:::

::: exercise {#ex-s5-ratchet} Break the trace on purpose
Do practice lesson 11 (`perl agile.pl practice 11`) if you have not. Then, on a branch in the Tidewater sandbox's
`work/bob` clone, delete one `satisfy` line, commit, and run `perl ci/job.pl trace` with both `CI_PIPELINE_SOURCE=merge_request_event` and
`CI_MERGE_REQUEST_TARGET_BRANCH_NAME=develop` in the environment (with only the target branch set, the job treats the
run as a branch pipeline and says "not a merge request: reported only"). Find the line that names the requirement
you orphaned.
:::

::: exercise {#ex-s5-dr} Write a discrepancy report
Choose one finding from `recipe-doors.txt` that DR-6 does not quote. Write a DR for it from the Discrepancy Report
template ([[templates]]): what we found, why it matters to verification, what we ask the prime to do. Keep it under
a hundred words.
:::

::: exercise {#ex-s5-retro} Read the record of a tabletop
Read issue #108 in the sandbox (`gitlab.pl issue show 108`). Write the three bullets the team's new template asks
for, as if you had run the tabletop: what you did, what surprised you, what you would change.
:::

=== Applying this to your project {#sprint-5-apply}

- **Grade the requirements before you design to them.** Run a recipe-style check on the inherited text in your first
  month, not before your first review. Send the findings to whoever owns the text.
- **Make the trace a ratchet, not a gate.** If you inherit gaps you cannot close, a gate that fails on every gap
  will be turned off within a week. A gate that fails only on *new* gaps will stay on for the life of the program.
- **Delete inherited clutter in your model and upstream at the same time.** One without the other leaves you
  fighting the same file at every delivery.
- **Rehearse your first release where nobody can see it.** A sandbox project costs nothing and turns the first real
  baseline into the second attempt.
- **Record what a tabletop taught you.** A closed issue with no notes is a meeting nobody can learn from.
