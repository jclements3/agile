Updating the data in Vim

The only editor you need for the townhall. Two files, ten verbs, one keystroke to compile.

1. Set-up (once)

# Git Bash, in the kit
$ echo 'source ~/projects/agile/vim/scrum.vim' >> ~/.vimrc
$ cd ~/projects/agile/data/demo          # any directory inside a project works: daily.pl finds scrum.conf upward
$ vim

scrum.vim adds the :S… commands, <leader>s… mappings (the leader is \ unless you set mapleader), syntax highlighting for stand-up files and the journal, and task-id completion. Nothing else to install.

2. The files you touch

FileWhat it isHow you edit it
standups/YYYY-MM-DD.txtToday's stand-up notes: one section per team, terse verb lines.This is where you type. :SNew creates it; compile appends it to the journal.
scrum.txtThe journal: a ledger of every point movement. The account a task's points sit in is its state.Almost never by hand. Compile writes it; you read it (:SJournal). See §9 for the exceptions.
scrum.confProject settings: recipients, unit, marking, calendar mode, townhall time.Plain key = value; edit when the program's facts change.
roster.txtThe people: Name | email | Team | Role | Org, name as Teams shows it.Edit in Vim, or daily.pl roster add …; daily.pl roster checks it against the journal.
standups/…-chat.txt, …-answers.txtPasted Teams chat and the Y/T/B records derived from it.:SChat opens the paste buffer; :SAnswers derives the records. Read-only after that.

3. The daily loop (two minutes after the townhall)

:SNew          today's file, one "== Team" section each, the open items listed as comments
…type the verbs (§4)…
:SDry          validate: shows the postings compile would write, or every error — nothing is written
:SCompile      (or \sc) save + validate + append to scrum.txt; the file is marked "# compiled"
:SReport       reports/: dashboard, tree, roadmap, brief, status mail, cockpit (marked)
:SCockpit      rebuild ./dashboard.html at the kit root; press F5 in the browser
:SDraft        Outlook draft to the leads — review, then send from Outlook
:STig          look before you commit: tig on the project — j/k walk the commits, Enter shows the diff, q returns
:SCommit       git commit of the journal + stand-up files (each project is its own repo)
:SAll          compile + report + draft + commit in one go (\sa)
A stand-up file with a mistake is rejected whole, with every error listed — nothing is half-applied. Fix the lines and run :SCompile again.

5. Vim tricks that pay off daily

Complete task ids from the journal

In a stand-up buffer the journal is the dictionary: type done B-1 and press Ctrl-X Ctrl-K to complete B-1221, B-1222… (Ctrl-N completes from open buffers too). iskeyword includes -, so * on an id searches the whole id.

Look a task up without leaving the file

:SJournal                 open scrum.txt; then  * on the id in the stand-up file,  or  /B-11  and  n  to walk its history
:vimgrep /B-11/ scrum.txt standups/*.txt | copen   every mention, in a quickfix list; Enter jumps
:SBacklog BMC2            the team's backlog in the message area;  :SSprint  :SBlocked  :SMembers  likewise

Read a spec without leaving Vim

Specs and deliverables arrive as PDF and Word. :SDocs runs bin/docs2txt.pl, which reads them as text through the converters Git for Windows already ships (pdftotext, docx2txt, antiword, odt2txt), so a document is grepped like the journal:

:SDocs grep -i "interface control" ~/specs/*.pdf ~/specs/*.docx   FILE:LINE: match, every document at once
:SDocs -o txt/ ~/specs/ICD-rev-C.docx                              one .txt per document — then  :vimdiff txt/ICD-rev-B.txt txt/ICD-rev-C.txt
:SDocs tools                                                        which converters were found
:r !perl ~/projects/agile/bin/docs2txt.pl grep -i "shall" spec.pdf   pull the hits into the stand-up file as the basis for new tasks
The last form is how a requirements document becomes backlog: grep the "shall" statements into the buffer, then turn each line into a new ID PTS title … with a macro.

Draft today's statuses from yesterday's

:SPropose       one line per person: "Ann: Y B-121 done? T B-1222 … B none -- 👍 if right, or repost". Paste the block into the chat at 0830.
:SAnswers       add  --assume  (daily.pl answers --assume) to put the proposal on the record for anyone who stayed silent, marked (assumed)
An assumed status is amber the first day, red from the second, and never marks anything done. Silence changes a flag, not the ledger.

Lint the statuses during the meeting

People type Y did B-11 T doing B-12 B none in the meeting chat. While they are still on the call, paste the chat so far and check it:

:SChat          today's chat buffer; paste (Ctrl-A, Ctrl-C in the Teams chat, then  p)
:SLint          (\sl) one line per person: ERROR (unusable), warn (no task id / unknown id), ok. Errors open the quickfix list;  :cn  jumps to the person
:SLintReply     the reply lines -- paste them back into the chat; the person answers with a thumbs-up or reposts
:!perl ~/projects/agile/bin/daily.pl lint --reply --confirm %   read-backs for everyone: "I read your status as: Y … / T … / B …  👍 if right" -- the table entry, privately with --private
:!perl ~/projects/agile/bin/daily.pl lint --private %   or send each correction 1:1: a page of private Teams chat links, message pre-filled (needs roster.txt for e-mails)
  Hey Bob! Did you mean: Y did B-11 / T will b in the lab / B none ?  👍 if yes, or repost as: Y did B-11 T doing B-12 B none
:SAnswers       after the meeting; add  --guess  (daily.pl answers --guess) to take the "did you mean" readings that were thumbed up

The chat buffer's syntax highlighting shows delimiters (Y T B) in one colour, task ids in another and a stray lowercase delimiter in a warning colour, so the bad line is usually visible before you lint. A person's last message wins, so a repost simply replaces the first attempt.

Turn a list into verb lines

:r !perl ~/projects/agile/bin/daily.pl backlog BMC2   pull the backlog into the buffer under the cursor
…delete the rows you won't commit, then:
:'<,'>s/^\s*\(\S\+\).*/commit \1/          keep the id column, prefix "commit "
:'<,'>normal I done                         or just prefix each selected line with a verb

Other habits: . repeats the last edit on the next line; qa…q records a macro, 10@a replays it ten times; Ctrl-V block-select a column of ids, y, then paste them onto one done line with J to join; :sort u on a block of ids; :g/^block/p lists every blocker in the file.

Navigate the file

== Team headers are paragraph boundaries: } / { jump section to section, zf} folds one, zM folds all, zR opens all. :set list shows stray tabs (values are space-separated).

6. Sprint planning (Day 1)

Same file, three verbs per team:

== BMC2
sprint 2
cap 24
commit B-13 Ann
commit B-14 Bob
commit B-1221                       # last sprint's carryover comes back with "commit" too
new! B-16 2 Sprint-2 spike: track fusion p:1 e:"B1 Develop Fire Control" t:"B Battle Management & Fire Control" o:"Cy BMC2"

Load over 100% turns the card amber, over 110% red, so :SDry then :SStatus before you compile tells you whether the plan is sane.

7. The master backlog (Day 9 refinement)

A == Master section intakes to the master backlog, which you (not a team) own. Refinement moves tasks down to a team; pruning retires stale ones.

== Master
new M-2 8 Cross-segment timing budget p:1 e:"E1 Engineer the System" t:"E Systems Engineering & Integration"

== SEI
refine M-1                          # now in SEI's backlog; commit it next sprint
prune E-12223 merged into E-12222

8. Fixing mistakes

  • Before compile: just edit the file. :SDry is free; use it until it prints no errors.
  • After compile, wrong verb: don't edit history. Post the correction as another verb in the next file (carry what you wrongly marked done, est to the right size, commit what you dropped). The journal stays a true record and the reports follow.
  • After compile, the whole file was wrong: :STig (or git log / git diff in the project) shows exactly what the compile appended (a ; ---- standup DATE block); git checkout -- scrum.txt before you commit, or git revert HEAD after, then delete the # compiled line at the top of the stand-up file and compile again.
Never renumber or delete postings inside scrum.txt — points are conserved and every report is derived from the full history. Corrections are new postings.

9. When you do edit the journal by hand

Three legitimate cases, all safe because they don't move points:

  1. Metadata fixes. Owner, epic, tome or priority on an intake line: ; id: B-11, epic: …, owner: …, prio: 1, tome: …. A tome renamed across the program is one substitution: :%s/tome: B Battle Mgmt/tome: B Battle Management \& Fire Control/g.
  2. Bulk intake at program start: sim/idef0-backlog.pl generates a stand-up file from the IDEF0 model, so even this is usually a compile, not a hand edit.
  3. Sprint capacity block: the ~ Sprint N / Team 24 SP lines, if you prefer them here to cap lines.
; an entry is: date, payee, then postings that sum to zero
2026-09-23 Intake B-11 Define Software Requirements
    Backlog:BMC2       5 SP   ; id: B-11, epic: B1 Develop Fire Control, owner: Ann BMC2, prio: 1, tome: B Battle Management & Fire Control
    Equity:Intake

After any hand edit: :SStatus (it re-parses the whole journal and reports the first error with a line number) and :SCommit.
