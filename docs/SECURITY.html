Security

What the kit protects, what it does not, and where the gates are. Companion to the DevSecOps dashboard (perl bin/devsecops.pl).

Threat model, in one paragraph

The asset is program data: the journal, stand-up answers, attendance and the reports derived from them, which may be confidential to your organisation. The kit is code with no secrets in it; the data lives in data/<project>/, each project its own git repo wherever your organisation keeps such things. The two things that must not happen: program data leaving that storage (a push to a public remote, a mail outside the allowed domains, a paste into an AI service your organisation has not sanctioned), and a marked report going out without its marking.

What is not covered

  • Transport. Marking is not encryption. Mail leaves via Outlook under the org's S/MIME/TLS policy; the kit does not encrypt.
  • Endpoint. The journal is plain text on disk. Its protection is the laptop's (BitLocker, access control), not the kit's.
  • Static analysis for Perl. perlcritic is CPAN and not available on the target. strict/warnings, perl -c on every file and 875 tests stand in; perlcritic can run in the Linux CI job if wanted.
  • Outlook COM. The one layer not unit-testable offline; TEST-PLAN.html is the manual session on the target.
A personal GitHub remote is for the kit only. Nothing under data/ may be pushed, ever; the hygiene job exists to catch the mistake, not to permit the attempt.

Reporting a problem

Open an issue on the kit repo with the command, the (redacted) input and the output. Never attach journal or stand-up files from a real program.
