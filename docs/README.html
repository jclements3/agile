Set up once (10 minutes)

unzip agile.zip ~/tools/agile            # anywhere; nothing depends on the location
mkdir ~/scrum && cd ~/scrum
perl ~/tools/agile/bin/daily.pl init       # scrum.conf, scrum.txt, standups/, reports/, git init
vim scrum.conf                               # recipients, unit, marking (or blank banner to disable)
echo 'source ~/tools/agile/vim/scrum.vim' >> ~/.vimrc
perl ~/tools/agile/bin/daily.pl roster add "Lee, Ann" ann.lee@example.com Alpha Lead ACME   # once per person, name exactly as Teams shows it

In scrum.conf set facilitator to your own Teams display name, so the lines you post in the meeting chat ("Y/T/B in chat, please") are not linted as a status. The townhall's time and length are townhall_start and townhall_minutes (init writes an open hour at 07:30; set 08:30 and 15 for the fixed fifteen minutes this page describes); daily.pl invite words the invitation to match.

Names: a value with spaces is quoted in a stand-up file (o:"Bob Ray", e:"Win Contracts"); commit ID owner and assign ID owner take the rest of the line as the owner (commit A-1 Bob Ray, assign A-1 "Lee, Ann"). "Last, First" names work everywhere; the owner must be spelled exactly as Teams shows it. The first stand-up file of a new project says sprint 1; tasks you commit under it start the sprint.

Every daily.pl command takes --today YYYY-MM-DD (catch up a missed day, replay, rehearse) and -c FILE (a scrum.conf elsewhere); --dry shows what compile would write.

Seed the journal: either paste tasks into scrum.txt following examples/scrum.txt, or make today's stand-up file and use new ID PTS title p:1 e:Epic o:Owner lines — the compiler writes the ledger entries. Sprint planning is the same file with commit ID owner and cap N lines per team.

Every daily townhall (one Teams call, all teams, 0830–0845, 2 minutes at the keyboard after)

The default rhythm is one joint townhall, not per-team stand-ups: everyone joins one fixed recurring Teams call and types Y/T/B into the shared chat. Anyone who needs to sync with another team says so on the line and either sets up a follow-up meeting or raises it as a decision — it isn't worked live. See WORKFLOW.html §4 for the minute-by-minute runbook; §4a covers the per-team variant for programs that can't get everyone on one call.

commit ID [owner]                team backlog, master backlog or last sprint's carryover -> this sprint
new ID PTS title [p:N e:E t:T o:O]  intake to the team backlog  new!  straight into the sprint
                                 (under a "== Master" section: intake to the master backlog)
refine ID                        master backlog (or another team's) -> this team's backlog
prune ID reason                  retire a backlog task -> Removed; the reason stays on the posting

block ID reason   unblock ID     tracked on the task; shows in reports until unblocked
hold ID reason    resume ID      interrupted by higher-priority work; stays committed, tagged HOLD on the weekly quad
punt ID reason                   too hard as written (any reason): out of the sprint, back on the team backlog (TODO) for replanning
redo ID reason                   found wrong after the demo: last sprint's Done -> this sprint's Committed; REDO on the quad
pass ID Team                     started it, another team should do it: whole task to that team's Committed, same sprint

note … risk … absent Name…       report only
sprint N                         override the current sprint (file-wide or per team)

Calendar (Outlook / Teams)

Teams' calendar is the Exchange calendar Outlook shows, so Calendar.pm drives classic Outlook through PowerShell COM (-EncodedCommand, no scripts on disk, no execution-policy issue). scrum.conf: standup_match picks the stand-up meetings, team_from_subject maps subject to team, attendance is the CSV log. calendar = mock + calendar_fixture = file.json runs the whole thing offline; cal.pl dump captures a fixture from the real calendar. The COM layer is the only untested part of the kit — TEST-PLAN.html is the 30-minute laptop session to close that.

Stand-up in chat: the three questions, flags, and your AI service

Participants answer in the meeting chat (Y: … / T: … / B: …, one line with bare delimiters Y did this T doing that B none (uppercase, in that order, a name before the Y is ignored), or yesterday/today/blockers, or 1/2/3). Paste the chat into standups/<date>-<Team>-chat.txt; daily.pl answers records one Y/T/B line per person in standups/<date>-<Team>-answers.txt, logs who answered as attendance, runs deterministic checks (silent people, blockers, blockers persisting N days, the same plan N days running, unknown or off-sprint task ids, "done" claims) and writes suggested lines into the stand-up file: done, unblock and absent commented for you to confirm; block ID why for a blocker that names a task (not repeated while that task is still blocked, so its age keeps counting); risk Name: why for a blocker with no task id. daily.pl ai builds a prompt from today's answers, metrics, flags and the last days' answers (banner included) and either writes it for pasting into your AI service (ai_backend = paste, default) or calls an OpenAI-style endpoint through Git's curl (curl). The reply's five fixed sections (HIGHLIGHTS / RISKS / STUCK / QUESTIONS FOR LEADS / PROGRESS) are parsed and appear in the status mail. Metrics never come from the AI; they come from the journal.

Shorthand is fine. People type the shortest line that carries the ids (Y B-2 T B-2 B none); the read-back shows them what the kit understood, and a thumbs-up closes it. That is the whole contract: they own the wording, you own the reading, and the reading is on the record in standups/<date>-<Team>-answers.txt and on the cockpit's Daily tab (Statuses today: one row per person, Y / T / B as parsed, ids emphasised).

Corrections go 1:1, not to the room. Teams lets you message any participant privately while the meeting runs (People → right-click → Chat, or a new chat from the main window), and only the two of you see it. --private on lint and propose writes a page with a private-chat deep link per person carrying the message; you click, glance, press Send. The meeting chat stays a clean record of statuses. Private chats are outside the meeting record but inside the org's retention and compliance rules, so don't say anything there you wouldn't say in the room. Guests without a Teams account can't be chatted 1:1; e-mail addresses come from today's meeting invitees and roster.txt (Name, email lines in the project).

What is checked: the three fields are present, in order, non-empty; lowercase y t b are accepted only when unambiguous (a second b -- "will b in the lab" -- is refused by name rather than mis-split); each of Y and T names a task id, and the id exists in the journal. Errors mean the answer cannot be used; warnings mean it parses but tells the kit little. The chat buffer highlights delimiters, ids and a stray lowercase delimiter, so most problems are visible before you lint.

Where the replies go: the meeting chat, which stays open after the meeting ends and is where people already are. Post the minutes (the status mail text, or the brief) there too, or in the meeting's Notes tab. If the townhall is a channel meeting the thread is visible to everyone in the channel and persists past recording/transcript retention -- the most dependable place for a group that changes over time. Only invited attendees see a private meeting's chat.

Memorize: the backlog and the people, carried in your head

For the meetings you attend with nothing but your mind. The drill turns the journal into question cards at every level, and you type terse answers: ids, epic codes and people's initials, in any order. Recalling is what builds the memory; reading the backlog again does not. The cards are generated fresh from the journal on every run, so there is no deck to keep up.

:SDrill [Team]   (\sm)   a sheet of the cards due today (reports/<date>-drill.txt); type after each '>', Enter jumps to the
                         next blank one, the last Enter (or :w) grades the sheet in place; on a miss write a mnemonic after
                         'hook:', Enter through them, and :w keeps them
daily.pl drill [Team] [-n 12]      the same in the terminal: question, answer, verdict, hook prompt on a miss; q stops
daily.pl drill --sheet [Team]      just write the sheet;   daily.pl drill --grade FILE   grade it (what :w runs)

Team Alpha: who? (initials)        AL BJ          Tome C Contracting: epics?   C1 C2
AL = ?  (full name)                Ann Lee        C2 Win Contracts: tome?      C
AL: team?                          Alpha          C2 Win Contracts: open tasks? (ids)    C-21 C-23
AL: in the sprint? (ids)           C-23           C-23 Negotiate & Close: who?           AL
AL: next up? (ids)                 C-11 C-12      C-23: what is it?            negotiate close
C-23 ...: blocked on?              legal review

Initials are the first letter of each word of the name (Archer, Sam is SA; a one-word name gives two letters, Bo). When two people share initials, letters of the last name are added to both: JCh and JCo. An id, code or initials in your answer that isn't in the right answer counts against you, because recalling the wrong thing is worse than a gap. For a "what is it" or "blocked on" card, half the title's words is enough, and a four-letter prefix counts as the word. ? means you don't know.

Progress uses the Leitner system, kept in drill.txt next to scrum.conf (one line per card: key | box | due | right | wrong | answer | hook; drill = FILE in scrum.conf moves it). A right answer moves the card up a box, due again in 1, 1, 3, 7, 14 and then 30 days. A miss puts it back in box 0, due tomorrow. The file remembers each answer, so a card whose answer changed in the journal comes first next time, marked changed, was: BJ: a reassigned task, a new task in an epic, a new blocker. Then come the due cards, lowest box first, then new ones taken in turn from each kind; a third of each day is kept for new cards, so a big deck is not starved by its own reviews. Drill one team's deck at a time (:SDrill Alpha): the whole program is hundreds of cards, more than a dozen a day can keep up with. The sheet lists them top-down: teams and people, tomes, epics, tasks. Hooks are yours: a miss shows the card's hook and the hooks of the people in the answer, and hook: - forgets one. The file is personal. Add it to the project's .gitignore if you'd rather not commit it.

Stress test: perl sim/drill-sim.pl [--days 60] [--n 20] [--team T|all] [--seed N] checks every card of the demo, the two-year history, the example and a hostile journal (Unicode and "Last, First" names, shared initials, titles with pipes and quotes): the right answer passes in any case, order or punctuation, a gap or a wrong id fails and is named, garbage never crashes, sheets and drill.txt round-trip. Then a simulated learner drills for weeks while tasks are reassigned, blocked and added; it checks the schedule, that changed cards come back first, that no card starves, and that accuracy climbs. The training replay (docs/TRAINING.html) shows the drill on Day 2 and Day 8.

Before the meeting: yesterday's status drafts today's

vim   :SPropose [Team]        one paste-ready line per person, from yesterday's answers and the journal:
                                Ann BMC2: Y B-121 done? T B-1222 Implement Engagement Planning B none  -- 👍 if right, or repost your own Y/T/B
shell perl daily.pl propose      post the block into the meeting chat at 0830; a thumbs-up is that person's status, a repost replaces it
after daily.pl answers --assume  the silent get their proposal on the record, marked (assumed)
private daily.pl propose --private  reports/<date>-propose.html: a 1:1 Teams link per person with their proposal pre-filled

Yesterday's T becomes today's Y ("done?"), today's T is the person's next committed task by priority, B carries a blocker that was live yesterday. Most people then only confirm, which is what makes 100 statuses a day feasible, and the wording converges on task ids because the proposals are written with them.

Silence is recorded, never rewarded. An assumed status is visible in the answers file and every report as ASSUMED, unconfirmed, amber the first day and red from the second, and it is the person's to correct the next morning. What it never does is move points: no task is marked done on an assumption, so velocity, predictability and the roadmap stay facts. If someone stays silent, the thing that grows is the flag on their name, not their done column -- that is the pressure, and it lands on the lead, where it belongs.

Votes and estimates from the Teams chat

No simple API reaches meeting chat on a managed tenant, so it is copy-and-paste: in the meeting type #est AUTH-104 and people answer with numbers, or #vote Ship Friday? y/n / #vote Name: A B C; afterwards select-all in the chat pane, copy, :SChat, paste, :STally. Each round is tallied (consensus or median with outliers; plurality/majority/tie), printed, and written into today's stand-up file as est ID N lines (ready when there was consensus, commented otherwise) and note vote … lines. chat.pl --est ID --since 09:07 file tallies without markers. Teams Polls are the alternative: results export to Excel from Forms.

Porting the legacy model: SysML v1 XMI and DOORS to SysML v2 text

bin/xmi2sysml.pl turns a Cameo/MagicDraw XMI export into SysML v2 text, one file per top-level package; bin/reqif2sysml.pl turns a DOORS ReqIF or CSV export into requirements carrying doorsId, and reports metrics C, F, G and I against the model. Nothing is dropped: whatever has no mapping becomes a // TODO line and is listed by --report. SYSML-PORT.html is the day-to-day guide.

perl bin/xmi2sysml.pl --report legacy.xmi                      ported vs remaining, and every element left as a TODO
perl bin/xmi2sysml.pl --out model --check legacy.xmi            model/<segment>/<Package>.sysml, grammar-checked
perl bin/reqif2sysml.pl --id-prefix SYS- --out model export.reqifz
perl bin/reqif2sysml.pl --report --model model export.reqif     linked / orphan / unverified

Halberd: the worked example

Halberd is a fictional, notional air and missile defense program used across the kit: an IDEF0 program model, a SysML v2 system model with planted traceability gaps, the 12-week port of its legacy model with a stand-up for every working day, and an FY27 funding journal with earned value. perl sim/halberd-gen.pl builds it as a real project in data/halberd; HALBERD.html shows the result without running anything (HALBERD.pdf is the same, typeset for print), and STATUS-DASHBOARD.html is the A-Z metric dashboard with Halberd's sprint 6 numbers.

Funding and earned value

The ledger tracks money as well as points. Date a budget (~ Monthly from 2026-10-05 to 2026-12-24), post labor against it, and:

perl bin/ledger.pl -f funding.ledger bal -M Expense --depth 3              spend per account, a column per month
perl bin/ledger.pl -f funding.ledger budget -M -b 2026-10-01 -e 2027-01-01 budget vs actual by month
perl bin/ledger.pl -f funding.ledger evm --now 2026-11-30 --complete-file complete-2026-11-30.csv
perl bin/ledger.pl -f funding.ledger forecast --now 2026-11-30 --months 2 Assets   funds left, burn, run-out date

Set funding = funding.ledger and complete = complete-*.csv in scrum.conf and the cockpit gains a Funding tab.

Marking (optional)

scrum.conf can set a banner (any text: INTERNAL, COMPANY CONFIDENTIAL, or whatever your organisation uses) and a marking block (Owner / Category / Handling / POC). Leave the banner empty and nothing is marked. When it is set, every output is marked the same way:

  • E-mail (status, brief, cards): banner as the first and last line of the body, the indicator block at the end, subject_prefix at the start of the subject.
  • HTML reports (dashboard, tree, status, brief, cards) and the simulated HISTORY.html: banner top and bottom, indicator block on the first page.
  • PDF (Print → Save as PDF from any of those): the banner is pinned to the top and bottom of every page, collapsed sections print expanded.
  • Text files (status, brief, cards): banner first and last line, indicator at the end.

daily.pl check validates the setup: with a banner set it warns when the owner, POC or subject_prefix are empty; with mail_domains set (a comma-separated list) every recipient in to/cc must belong to one of those domains. daily.pl draft, brief, cards --send and invite run the same check and refuse on an error (--force overrides). Marking is not transport: encrypt mail the way your organisation requires. reports/ is git-ignored; the journal and stand-up notes are committed, so treat the repository as marked when its content is. Lower-level scrum.pl output has no scrum.conf and is therefore unmarked: use daily.pl for anything that leaves your desk.

Operating model

WORKFLOW.html is the full operating model: hierarchy of work, the two-week tempo day by day, what each event feeds into the journal, the metrics with thresholds, outputs by audience, and the feedback loops. SCHEDULE.html turns that tempo into a suggested daily workflow and weekly calendar, backed by sim/daily-job-sim.pl, a time-accounting simulation of the role at scale. JOB_DESCRIPTION.html is the role written up as a job description. FOR_MANAGERS.html is the same operating idea in one non-technical page for a manager.

Project data (the journal, stand-up files, reports) lives in data/<project>/ — one directory per project, each its own git repo from daily.pl init, and ignored by the kit's own repo. data/demo is the DroneCorp demonstration (below); data/history is the two-year simulation further below.

The demo product is an IDEF0 model. tools/idef0/ is the IDEF0 toolkit (core Perl: idef0lint, idef2html, idef2svg, idef0 links) with the example model in tools/idef0/examples: DroneCorp, a notional racing-drone company (ten models, one per department — fictional, no real company data), which is the demo. sim/idef0-backlog.pl MODEL.md --cap N --commit derives the product backlog from it as a planning stand-up file the kit compiles: model → tome and team, level-1 activity → epic, leaf activity → task, and every cross-model interface link → an interface task owned by the destination team under the source epic — so integration work is explicit and the planning tree flags the epics that span teams. The training replay builds data/demo this way and renders the plates to reports/plates.html as the design the teams build to.

Training: perl sim/training.pl runs one complete sprint against data/demo for real — init, planning, ten townhall days (cards, the pasted chat, answers and flags, confirming suggestions, compile, report, brief, commit), refinement with an estimate round, review and close with a git tag — narrated step by step as an architect's day, paced in the terminal (--fast to skip the pauses). It records the whole run to TRAINING.html, a playable terminal replay: Play, or step with the arrow keys. It resets data/demo every time and refuses any other directory.

sim/history-gen.pl goes further: it simulates two years (52 sprints) of ten teams doing tasks by generating real stand-up files and compiling them through this kit's own pipeline, then renders HISTORY.html — a calendar of every sprint colored by the status that would have gone to leadership at each review, with trend and per-team tables. Every number in it is computed by the same Scrum.pm code that runs in production. It is print-ready: open it and use the browser's Print → Save as PDF (no install, offline) for an exit report or performance review.

Library use

Everything returns plain hashes and lists; perldoc lib/Scrum.pm (and Ledger, Standup, Prelude) has the API with examples. A report that doesn't exist is a few lines of Prelude over items($s).
