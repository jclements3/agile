Coding drills: the first 90 days

A solutions architect who stops writing code starts proposing pipelines he could not build. This kit keeps the hands on the keyboard with interview-style problems, solved in core Perl on a laptop that has only Git for Windows: its Perl, its Vim and Git Bash. There is nothing to install, no network and no admin right needed.

It implements the binder's chapter Coding drills: the ladder of small problems from trivial to hard, the habits every session trains, the phased drill in which the requirements change, the refresher plan and the drill log. It adds about 130 more problems in technique sections, the Perl toolbelt as a runnable file, and a Vim memory trainer.

  • drills/drill.pl lists the problems, starts the clock, runs the tests, gates the reference solutions, keeps the log and says what to do next. The logic is in lib/Drills.pm.
  • :DrillTrain in Vim is the memory game: type each solution from memory, with the hint fading rep by rep.
  • perl agile.pl practice 9 is a guided first run: start, solve, test and log one ladder problem.
  • The reference for every command, key and message is the kit's help: perl agile.pl help drills, or :help agile-drills in Vim (HELP.html).
Your work never goes into the kit. Your solutions, the attempts, the drill log and the trainer's progress are in the workspace: ~/drills-work, or $DRILLS_WORK, or --dir DIR on any command. Make it a git repository and commit after each session, as the binder says. Never use work data in a drill.

Session 0: set up and prove it

  1. In Git Bash, an alias saves typing (put it in ~/.bashrc): 
    alias drill='perl ~/projects/agile/drills/drill.pl'
mkdir -p ~/drills-work && cd ~/drills-work && git init
  2. Vim: the kit's vim/scrum.vim in ~/.vimrc loads the drill commands too (source ~/projects/agile/vim/scrum.vim). :help agile-drills proves it.
  3. Prove the runner on the first rung, then break it on purpose: 
    drill start p00            # the stub is ~/drills-work/p00-pong.pl; the clock starts
vim ~/drills-work/p00-pong.pl
drill test p00             # pass per case, "1/1 passed", exit 0
# break the file, run drill test p00 again: a FAIL line with expected and got, exit 1 (echo $?)
  4. Retype the toolbelt from memory until it runs: perl ~/projects/agile/drills/toolbelt.pl shows the idioms; every lookup you need is a line in the log.
  5. Read The habits below twice, the eight questions especially.

You are done when drill test p00 passes, a broken file fails, and the questions come out roughly in order.

The habits every session trains

  1. Questions before code. At least five before typing. When an answer is unknown, write # ASSUME: ... at the top of the file: that comment makes a changed requirement a one-line edit.
  2. Say it out loud. The pattern, the complexity and one edge case before the first line. Fifteen seconds of silence means you are stuck: say where.
  3. Small named functions: parse, validate, solve, report. A changed requirement then touches one.
  4. Tests first and often. drill test ID after every edit (\dt in Vim). Never eyeball output.
  5. Brute force first, then improve. A correct slow answer beats an elegant wrong one.
  6. Close properly: what you would do with more time, what you would test, where it breaks at scale.

The eight questions

  1. What is the input size: hundreds or millions? (Sets the complexity target; a small n licenses brute force.)
  2. Are the inputs non-empty, and are paired collections the same length? (The change most often planned.)
  3. Can there be duplicates? Must I keep the input order?
  4. What happens when there is no valid answer: a marker, an error, nothing?
  5. On ties, is any valid answer acceptable, or is there a tie-break?
  6. Are values bounded? Negatives, decimals, empty fields?
  7. Does it fit in memory, or is it a stream?
  8. Run once, or in a loop where I should precompute?

The 90 days

The binder's refresher block is a setup session and seven practice sessions. Run them one a week from the first week (or as seven days in a quiet week), with ten minutes of recall in Vim on two other days. After the block, keep the weekly cadence. drill next follows the same plan and always names one thing to do.

One session, step by step

  1. drill next: one problem and why (a failed one first, then the ladder in order, then the plan).
  2. drill show ID: read it twice. Ask the questions, write the assumptions as comments.
  3. drill start ID: the stub in the workspace, the clock on. In Vim, \do on the statement does the same.
  4. Edit, drill test ID (\dt), repeat. The first case is the sample; solve from it, then let the rest speak.
  5. Blow the timebox: drill solution ID, read it, close it, and re-solve from a blank file the next day (drill start ID --fresh).
  6. drill log ID "what was slow": minutes and result filled in.
  7. Five minutes of :DrillTrain.

An id can be shortened while it stays unique: p23, two-sum. Function problems are called directly: your file defines the sub named on the statement's Call: line and returns the answer. Stdin problems (the ladder) are scripts: the case goes to stdin and the output is compared ignoring trailing blanks. Each case has a five-second limit; a die, an exit or an endless loop fails that case and nothing more.

Each problem is a directory, drills/NN-SECTION/ID/: statement.txt (a header with the LeetCode pointer, the pattern, the timebox, the kind and the call, then the contract and examples), tests.pl (the cases, the sample first), solution.pl (the reference: its comment block gives the pattern, why it works, the time and space complexity, the edge cases and the Perl idioms) and stub.pl. A new problem is a new directory in the same format: write the tests before the solution, then drill test ID --ref.

The phased drill

One 60-minute problem that changes four times. It trains the hardest habit: absorbing a changed requirement with a refactor instead of a rewrite. Narrate the whole hour; read a phase only when the previous one passes.

ClockPhaseWhat you are doing
0-5AskFive questions, restate the problem, write assumptions as comments. No code.
5-10DeclareThe approach and its complexity, the function names, two tests.
10-25Phase 1Make it work, brute force allowed.
25-40Phases 2 and 3The requirements change: refactor, re-test after each edit. Say "that changes X, so I touch Y" before typing.
40-55Phase 4Edge and unsolvable cases. State the contract for "no answer".
55-60CloseMore time, more tests, where it breaks at scale.
drill phased                     # the plan and the scenarios
drill phased 1                   # phase 1's card; writes WORKSPACE/phased-sensors.pl (a solve sub), starts the clock
drill phased test 1              # correct and wrong pairs, unpaired counts, PASS or not yet; then phased 2 ...
drill phased solution            # the reference and what to say out loud, after an attempt
drill phased 1 --scenario payments    # the second run: orders and payments, same shape, fresh head
DRILL_SEED=99 drill phased test 2     # fresh sensor data

Commit after each phase: git diff --stat between phases should show edited functions, not a rewritten file. Phase 1 clean, narrated and preceded by questions is the bar; phases 1 to 3 is strong; reaching phase 4 is excellent. Write code that survives the changes: small named helpers (close_enough, validate, pair), the tolerances as named arguments with defaults (solve(\@a, \@b, t_tol => 0.75)), validation apart from solving, and a hash ref as the result ({ pairs, unpaired_a, unpaired_b, ok, reason }) so "also report the leftovers" needs no new signature.

The Vim trainer

The vanishing-cues memory game over the reference solutions. :DrillTrain opens it at the highest level you have unlocked. A card shows the first line of a solution, for example sub two_sum {, and you type the rest under the marker line. Each card is five reps: the first shows the whole solution to copy, each later one blanks out more of its words, the last shows nothing. Only the blind rep counts.

  • Check with \dc (or Ctrl-G Ctrl-G in insert mode). Right: straight on. Wrong: the solution appears under your answer; Space retries the rep.
  • \dg gives up: the solution is shown, and on the blind rep it is a miss.
  • A level is cleared only when every card's blind rep was right first try. That unlocks the next level; the progress is in WORKSPACE/trainer.txt.
  • Comments, blank lines, spacing and indentation are ignored; the code must match.
  • :DrillLevel N (\dl) replays any unlocked level, \dr replays this one, \dq quits, :DrillReset forgets the progress.
  • Settings: let g:drills_fade_steps = 3 for shorter cycles, g:drills_work for another workspace.

The same plugin carries the ladder keys: \do jumps between a statement and your file (making it, and starting the clock, the first time), \dt tests the problem in the buffer, \da checks everything you have. Results open in a split.

The drill log

WORKSPACE/log.txt, append-only plain text, one line per problem:

# drill log: date | problem | minutes | passed | notes
2026-10-12 | p11-most-common-char | 6 | pass | tie-break sort key said aloud first
2026-10-12 | p13-transpose | 9 | fail | parse the header before the rows

drill log ID "note" fills in the minutes since start and the last test's result. After each session, drill log --session N appends the binder's form to fill in with vim + log.txt: done, the slowest or weakest thing, the lookups you needed, the narration check, the questions check, and one thing to redo. Sessions 4 and 6 read it; drill next reads the attempts and puts a failed problem first.

The Perl toolbelt

drills/toolbelt.pl is the binder's toolbelt as a runnable file: every idiom with a check. Retype it from memory until one pass needs no lookups. The core of it:

use strict; use warnings;
use List::Util qw(sum max min first reduce);   # sum0 and uniq are newer than some Perls: write them by hand
chomp(my @lines = <STDIN>);                  # every line, newline removed
my ($n, $t) = split ' ', $lines[0];           # split ' ' trims and collapses blanks; split / / does not
my %count; $count{$_}++ for @x;               # count
my @top = sort { $count{$b} <=> $count{$a} or $a cmp $b } keys %count;   # by count down, then name up
my %seen; my @dedup = grep { !$seen{$_}++ } @x;   # first occurrences, in order
push @{ $group{$k} }, $v;                     # group into a hash of arrays
my @q = ($start); while (@q) { my $c = shift @q; ... push @q, $next }   # a queue (BFS)
printf "%.1f\n", $median;                     # fixed decimals: 5 prints 5.0
sub heap_push { ... } sub heap_pop { ... }    # no heap in core Perl: ten lines each, store -x for a max-heap
OperationCostSay
Hash lookup or insertO(1) averagea hash of seen keys replaces a search in a loop
SortO(n log n)Perl's sort is a merge sort; give a tie-break anyway
Binary searchO(log n)by hand, lo and hi, carefully
Heap push or popO(log n)written by hand
grep on a list inside a loopO(n2) totalthe accidental quadratic
BFS or DFSO(V + E)a grid has R times C cells
Memoized recursionstates times work per statecoins: amount times coins

Rule of thumb: n up to about 104 allows O(n2); n up to about 106 needs O(n log n) or better. Patterns and the words that trigger them: sort then greedy (arrange, pair up, minimize); a hash map (by category, duplicates, most common); two pointers (pair sum, merge, within tolerance); intervals (overlap, schedule); a heap (k largest, running median); a sliding window (contiguous, longest run, at most k); BFS (shortest path, reachable); memoized DP (count ways, can it be done); a stack (balanced, nested); a state machine over a stream (per client, rate, sessions).

Where the problems come from

The ladder is the binder chapter's, with its tests. The technique sections port a personal set of interview solutions grouped by technique, plus self-checking lessons and warm-up exercises written earlier in Python; all of them are rewritten here in Perl, with new statements, tests and notes. Problem statements are the kit's own words: a LeetCode number and title appear only as a pointer to the well-known problem a drill resembles, never its text.
