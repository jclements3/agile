Pilot plan: one team to ten

Debug the rhythm with a few people who will forgive you, grow only when the exit gate is met, keep every phase in its own project directory.

Principles

  • One project per phase. data/pilot1, data/pilot2… Each is its own journal and git repo (daily.pl init). A phase that goes wrong is deleted, not repaired; a phase that goes right is the template for the next.
  • Grow by gates, not by dates. The next phase starts when the current one has met its exit gate for three consecutive days, not on a calendar.
  • Features come on one at a time. Start with the minimum (Y/T/B in chat, answers, compile, report). lint, propose, --assume, ai and the mails switch on later, each once the phase below it is boring.
  • Measure the architect, not just the teams. Time yourself from "meeting ends" to "commit done" every day. That number is the real gate.

Phase 0 — you alone (2 days, already done in the training replay)

Run docs/TRAINING.html end to end once more, then a dry day against data/demo: paste a chat you wrote yourself, answers, compile, report, open the cockpit. Purpose: muscle memory for the two minutes after the townhall.

Phase 0b — the lab: rehearse the whole loop without a team

cd data/lab                                        # a two-team, seven-person project (Jim is on Alpha); re-create with daily.pl init if you break it
perl ../../sim/rehearsal.pl --seed 3 --mistakes 4 --silent 1     # writes standups/<today>-chat.txt: a realistic Teams paste with the usual mistakes, answer key on stderr
perl ../../bin/daily.pl lint | lint --reply | answers --guess --assume | compile | report ; perl ../../agile.pl data/lab

Change the seed for a different day. Every mistake in the generator is one you will see in week one; the answer key says what lint and answers should make of each, so you can check the tool and your own reflexes before a single colleague is involved. Run it under Git for Windows' Perl ("/c/Program Files/Git/usr/bin/perl.exe" from Git Bash is just perl) -- that is the target.

Phase 1 — one team, 4 to 6 friendly people (1 sprint, 2 weeks)

mkdir data/pilot1 && cd data/pilot1 && perl ../../bin/daily.pl init .      # scrum.conf: calendar = mock until Outlook is trusted
vim scrum.conf   roster.txt                                                # recipients, mail_domains; Name, email per person
# backlog: 10-15 real tasks from the team's actual work, typed once (new ID PTS title p: e: t: o:)
Switched onOff for now
Meeting chat Y/T/B (bare form: Y did B-11 T doing B-12 B none) · :SChat :SAnswers :SNew :SCompile :SReport · cockpit Daily/Sprint tabs · lint for yourself propose, --assume, --private, AI, status mails, cards, calendar attendance, brief

What you are debugging: the message format people actually type; the id discipline; whether answers splits the joint chat correctly; your own time budget. Post the format once at the top of the chat each morning; correct in the room, kindly, by reposting the good example.

Exit gate: three consecutive days with ≥80% of answers parsed with no lint error, every answer carrying a task id, and you done (compile+report+commit) within 10 minutes of the meeting ending.

Phase 2 — three teams, ~25 people (1 sprint)

Same file, three == Team sections. Add the first cross-team task (an interface epic spanning two teams) so the integration-point flag and the roadmap have something real.

Switch onWhy now
lint --reply during the meetingEnough volume that reading every line stops being viable; corrections need to be fast.
propose in the public chatProposals are neutral and cut typing; they teach the format better than a rule does.
Team leads type their own == Team sectionYour time budget will not survive ten teams otherwise. Start the habit at three.
Status mail to the three leads, cockpit Weekly/Backlog tabsFirst real readers; find the wording they skip.
Exit gate: three consecutive days with ≥90% parse rate, a lead's section compiled without your edits, one integration blocker raised and cleared through the journal, you done within 15 minutes.

Phase 3 — all ten teams, ~100 people (2 sprints)

Switch onWhy now
--private correctionsAt 100 people a public "did you mean" is noise; 1:1 is kinder and quieter.
answers --assume (after sprint 1 of this phase)Only once the format is settled — otherwise red flags measure the tool, not the people.
Leadership brief, calendar attendance, cards, AI summaryThe audience and the volume that justify them exist now.
Exit gate = go-live: a full sprint where the roadmap forecast moved for a reason you can name, the brief went out daily without edits, and the sprint review used only generated reports.

Daily debug log (keep it in the pilot's git repo)

standups/NOTES.txt      one line per day:  date | people | parse% | lint errors | minutes-to-commit | what broke | what changed

Every "what broke" that is the kit's fault becomes a test in tests/ before the fix; every one that is a habit becomes a line in TUTORIAL.html. The debug log is also your evidence at go-live that the rhythm was tested, not assumed.

Things that will go wrong, in the order they usually do

  • People type prose without ids → the "no task id" warning; fix with proposals, not reminders.
  • Names in the chat don't match owners in the journal (nickname, middle initial) → "unknown team for"; fix o: on the tasks to match how Teams displays them.
  • Someone answers for a colleague → flag "working X owned by Y"; decide the rule (allowed, note it) and write it down.
  • A lead's section rejected by compile → the error lists every line; teach :SDry.
  • Your own time creeps past 15 minutes → you are reading chat instead of flags; stop.
Do not run the pilot in data/demo: sim/training.pl wipes that directory.
