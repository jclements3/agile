== Sprint 2: Drop 1 on develop, every change gated {#sprint-2}

::: bridge
You know: the first delivery from a contractor, and the argument about where it lives.

Here it is called: the vendor branch and the first merge request into develop.

What is new: the prime's model arrives through a gate, and every change after it is checked.
:::

::: survival
What you have: a GitLab project with its rules, three working laptops, drop 1 converted on a laptop and measured, a
pipeline that runs only on Tom's machine, and a team still unconvinced.

What you need from this sprint: a runner, so the pipeline runs on the server for every change; the drop on the
integration branch through the vendor branch, in a folder layout that every future drop will land in; and the team's
decisions written down where the next person will find them.
:::

==== Thursday 22: the layout decision {#sprint-2-layout}

Bob's task #39 was the most consequential half-day of the sprint: deciding where the converted model would live in
the repository. The converter's default is one folder per v1 package, named after the package. The alternative is a
layered layout, with libraries, requirements, logical behavior, physical structure, analysis and verification in their
own folders and the packages placed in them by a *layout map* ([[repo-layout]]).

The thought process went like this.

- **Every future drop must land in the same folders.** The vendor branch works because git can compare the prime's
  new drop with the old one file by file. If a package moves between drops, git sees a deletion and an addition, and
  the merge with the government's edits becomes manual. So the layout chosen now is the layout for the life of the
  program.
- **The layers are how the team wanted to review.** A reviewer looking at a change to a requirement package wants to
  know immediately that it is a requirement change, and the code owners for requirements are not the code owners for
  physical structure ([[reviewing]]).
- **The layout map costs one file.** A text file that says which package goes in which folder, applied by the
  converter on every drop. Moving a package later means editing that file and re-importing on the vendor branch,
  which is possible but not something to do casually.

Bob chose the layered layout, and the team recorded the choice in the merge request that imported the drop.

==== Friday 23: the pipeline dies on its first line {#sprint-2-powershell}

Tom committed the pipeline that had run on Tom's laptop the Friday before, opened a first merge request with a real
pipeline, and watched it fail on every job:

{{include: docs/tidewater/sprints/02/pipelines/mr2-first-on-powershell-1.log}}

Read the errors. `The term 'FILES=$(find' is not recognized as the name of a cmdlet` is PowerShell talking. The
Windows runner's shell executor runs PowerShell by default, and the pipeline had been written in the Bash dialect that
Git Bash uses on Tom's laptop. `$(...)`, `||` and `$KIT` mean nothing to PowerShell. Tom's reaction is in the record:

> The first pipeline on the real runner died on line one. PowerShell. Nobody told me the runner speaks PowerShell.
> -- Tom, sprint 2

This is the lesson of the runners chapter ([[runners-pwsh]]), and the team took the fix described there: every job's
script became one line, `perl ci/job.pl NAME`, with the logic in a Perl script in the repository. Perl reads the same
under PowerShell, Git Bash, Linux and Docker. The second pipeline on the same merge request:

{{include: docs/tidewater/sprints/02/pipelines/mr2-job-pl-2.log | lines 1-6}}

Look at line five: `no .sysml files under model/ yet`. The pipeline is green because there is nothing in the
repository for it to check. That is worth saying out loud, because a green pipeline on an empty model proves the
plumbing, not the model. Jim approved the merge request on that understanding:

{{include-md: docs/tidewater/sprints/02/samples/mr-2.md}}

The simulation's GitLab still holds both pipelines. This is the failed one as GitLab lists it:

```sh run sandbox=tidewater expect="grammar\s+failed"
perl "$KIT/bin/gitlab.pl" --local gitlab --project tidewater/model pipeline show 1
```

and the first lines of its grammar job's log:

```sh run expect="is not recognized as the name of a cmdlet"
head -4 gitlab/pipelines/tidewater-model/1/grammar.log
```

The same afternoon Tom switched on "pipelines must succeed" and the merge request report widgets ([[tools]]). From
that moment no change could reach the integration branch without a green pipeline. Bob's conventions package, the
government's own library of level tags ([[repo-layout]]), was the first model change to go through the full gate,
and it passed on its first pipeline.

=== Week two {#sprint-2-week-2}

==== Monday 26: level tags and decision records {#sprint-2-adrs}

Bob named the level tags in `sysml.conf`, and Jim merged the team's decision records: the ten decisions drafted in
week zero, plus the scaffold's own, as numbered files under `docs/adr/` in the repository rather than slides in a
briefing ([[operating-model]]). The list is worth reading as a summary of how the team decided to work:

```sh run sandbox=tidewater expect="0004-data-handling-and-markings\.md"
ls work/jim/docs/adr
```

Each file is a page: the context, the decision, and its consequences. The point of keeping them in the repository is
that a decision is changed the same way a model element is, by a reviewed merge request, and the history shows when and
why.

==== Tuesday 27: the drop on the vendor branch {#sprint-2-vendor}

Tom imported drop 1 onto the vendor branch with `gitlab.pl flow vendor` ([[prime-changes]]). The vendor branch holds
nothing but the prime's deliveries, converted with the layout map, one commit per drop. Nobody edits it. The
government's work happens on the integration branch, and each drop reaches it through a merge request from a short
feature branch that merges the vendor branch in. That merge request was opened the same morning, and Jim said the
sentence the team remembers from the sprint:

> The model is on develop and nobody touched it with a mouse.
> -- Jim, sprint 2

It was not quite on develop yet. It was on its way through review, which is the point.

==== Friday 30: the demo that lost the room {#sprint-2-review}

The review was the low point of the twelve weeks, and it is in the record:

{{include: docs/tidewater/sprints/02/review.txt}}

Tom drove the demo, opened a terminal, scrolled through the pipeline file, explained the PowerShell problem, and
finished on a green pipeline, which on that day was the most impressive thing Tom had seen in a month. The deputy
program manager saw a terminal, a file full of words like `rules` and `artifacts`, and a green dot. The question at
the end was fair, and nobody had an answer ready:

> I did not follow the demo. What did we get for the two weeks?
> -- Deputy PM, sprint 2 review

What they had got was considerable: the prime's model under the government's configuration control, every change
checked and reviewed, the conversion debt counted, the decisions on record. The team knew that. They had not said it
in words the deputy could repeat to anyone else. The four headline numbers were at the bottom of the review record and
nobody read them out.

::: sidebar Why the demo failed, in one sentence
The team demonstrated the *machinery* to someone who had come to see the *result*. The fix ([[talking]]) is a
structure, not a talent: open with the question the sprint answered, show the output rather than the tool, give one
before-and-after number, make one safe change live, and close with what it means and what you need. The team used
exactly that structure in sprint 4, and it worked ([[sprint-4]]).
:::

=== What went wrong, and what the team did about it {#sprint-2-wrong}

- **The pipeline was written for the wrong shell.** Found on the first server run, fixed within the day, and the fix
  made the pipeline more portable than it would otherwise have been.
- **A green pipeline on an empty model.** Not wrong, but easy to misread. The team learned to ask what a green
  pipeline actually checked.
- **The demo.** The fix was a structure and a rehearsal, adopted at the retrospective and used from sprint 3.
- **Stand-up lines with no outcome.** Not caught by the lint, caught by the deputy's question. The team started
  writing outcome-first statuses in sprint 3, with drafts from `talk.pl` ([[talking]]).
- **The intake issue for the first drop left open.** Caught in the To-Do list at the review. Closing the intake issue belongs on the drop
  intake checklist ([[prime-changes]]).

=== You can now... {#sprint-2-can-now}

- read a pipeline log and tell a shell error from a model error;
- explain why every job runs `perl ci/job.pl NAME`, and what goes wrong without it;
- explain what a green pipeline proves and what it does not;
- import a prime drop onto the vendor branch and merge it through a feature branch;
- choose a repository layout with the next drop in mind, and record it in a layout map;
- write a request for enablers as dated asks with the cost of no;
- recognise a demo that shows machinery instead of results, and restructure it.

=== Applying this to your project {#sprint-2-applying}

- **Run the pipeline on the real runner as early as you can,** and expect the first run to fail for a reason that has
  nothing to do with the model.
- **Keep the pipeline's scripts shell-neutral** from the start: one command per job, logic in a script in the
  repository.
- **Decide the repository layout before the first drop is merged,** and write it down as a map the converter applies.
- **Bring the inherited model in through a vendor branch** and never edit it there. Record the inherited debt as the
  starting point of a ratchet.
- **Write your asks down** with dates and the cost of no. A memo gets decided; a remark in a meeting gets remembered
  differently by everyone who heard it.
- **Rehearse the demo** and say the result before the mechanism. The first time you get it wrong in front of
  management is the last time you will need to be told.
