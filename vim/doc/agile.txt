*agile.txt*	Offline help for the agile kit (Perl + Vim + Git, nothing to install)

The agile kit's help                                     *agile* *agile-help*

This is the kit's help. It works with nothing but Git for Windows: its Perl
and its Vim. The same text is in four places:

  In Vim               :help agile   :help :STown   :help agile-err-...
  On the command line  perl agile.pl help TOPIC
                       perl agile.pl help search WORDS
                       perl agile.pl help error "PASTED MESSAGE"
                       perl bin/daily.pl help compile   (also scrum.pl, ledger.pl)
  As a page            docs/HELP.html (open it in Edge; it prints well)
  Hands on             perl agile.pl practice

Moving around in Vim: put the cursor on a link (a word between bars) and
press CTRL-] to follow it, CTRL-O to come back. |agile-howto| lists the
runbooks.

First day after cloning the kit                       *agile-howto-first-day*

You need Git for Windows (Git Bash, its Perl and its Vim). Nothing else.

1. Get the kit. From a clone: >
    mkdir -p ~/projects && cd ~/projects
    git clone URL agile
<   or from a release zip (|agile-release|): unzip it, then check it: >
    sha256sum -c agile-v1.0.zip.sha256
<
2. Check that it works on this machine (each line ends "all N passed"): >
    cd ~/projects/agile
    for t in tests/*.t; do perl $t | tail -1; done
<
3. Set up Vim and a shell alias (|agile-vimrc|, |agile-alias|): >
    echo 'syntax on'                               >> ~/.vimrc
    echo 'source ~/projects/agile/vim/scrum.vim'   >> ~/.vimrc
    echo "alias daily='perl ~/projects/agile/bin/daily.pl'" >> ~/.bashrc
    source ~/.bashrc
<   Tell git who you are once, or daily.pl commit cannot commit: >
    git config --global user.name "Your Name"
    git config --global user.email you@example.com
<
4. Build the demo project and look at the cockpit (|agile-demo|): >
    perl sim/training.pl --fast
    perl agile.pl
<
5. Make your own project (|agile-first-project|): >
    daily.pl init ~/scrum/myprogram
    cd ~/scrum/myprogram
    vim scrum.conf
<
6. Do practice lesson 1 (|agile-practice-1|): >
    perl ~/projects/agile/agile.pl practice 1
<
You are done when: the tests all pass, `vim` then `:help agile` opens this
file, `perl agile.pl` opens the demo cockpit in the browser, and
`perl agile.pl practice check 1` says "lesson 1: done".

Run the daily townhall                                  *agile-howto-townhall*

One Teams call for every team, 08:30 to 08:45; people type Y/T/B in the
chat. The whole loop is in |agile-ytb|; the operating model is
docs/WORKFLOW.html section 4. Times are a suggestion.

1. 08:05, five minutes of recall (|agile-daily-drill|): >
    :SDrill            (or: daily.pl drill)
<
2. 08:10, draft today's statuses from yesterday's (|agile-daily-propose|): >
    daily.pl propose
<   Paste the block into the meeting chat when it opens.
3. 08:15, cards for each member, optional (|agile-daily-cards|): >
    daily.pl cards               (--send mails them through Outlook)
<
4. 08:30, attendance from the calendar, optional (|agile-daily-attend|): >
    daily.pl attend
<
5. 08:30-08:45, lint the chat while people are still on the call: >
    :STown                       (\sw)
<   In Teams: CTRL-A CTRL-C in the meeting chat. In Vim: \sp pastes and lints.
   \sy puts the replies on the clipboard; CTRL-V them into the chat.
   :SSend Name opens a 1:1 chat with that person's reply filled in.
6. 08:45, download the meeting's attendance report (Teams: Attendance tab)
   to standups/DATE-attendance.csv, then: >
    :SJoined                     (daily.pl joined)
<
7. After the call, the two minutes at the keyboard: >
    :SAnswers                    (daily.pl answers --assume)
    :STally                      only if there were #est or #vote rounds
<   Open today's stand-up file (:SNew), uncomment the suggested lines you
   accept (done, unblock, punt, hold, pass), add anything else, then: >
    :SDry                        (\sd) shows what compile would write
    :SCompile                    (\sc)
    :SReport                     (\sr)
    daily.pl health
    :SDraft                      or daily.pl brief, on mail days
    :SCommit
<   Or all of step 7 after the edits in one go: daily.pl all --draft
You are done when: `daily.pl status` says "no pending stand-up files", the
sprint line shows today's done points, and `git log -1` in the project says
"standup DATE".

See also: |agile-daily-lint|, |agile-daily-answers|, |agile-ack|,
|agile-howto-publish|.

Plan a sprint (Day 1)                                   *agile-howto-planning*

1. See what is ready: >
    daily.pl backlog TEAM        each team's backlog, by priority then age
    daily.pl velocity            what each team has been finishing
<
2. Make today's file and write the plan, one section per team: >
    :SNew
<   Under each "== Team" line: >
    sprint 7
    cap 24
    commit B-13 Ann Lee
    commit B-1221                last sprint's carryover comes back with commit
    new! B-16 2 Spike on track fusion p:1 e:"B1 Fire Control" o:"Cy Ray"
<   The sprint number can be on the second line of the file for all teams.
3. Check the plan before you write it: >
    :SDry
    daily.pl sprint 7            after compile: Load% per team
<   Load over 100% turns a team amber, over 110% red.
4. Write it and publish: >
    :SCompile
    :SReport
    :SCommit
<
You are done when: `daily.pl sprint` shows the new sprint with every team's
Load% at or under 100%, `daily.pl members` shows no "unassigned" line, and
`daily.pl status` says "sprint 7: 0/N ... done".

See also: |agile-verb-commit|, |agile-verb-cap|, |agile-verb-sprint|.

------------------------------------------------------------------------------
Close a sprint: review and report (Day 14)                *agile-howto-review*

1. See what is still open: >
    daily.pl sprint
    daily.pl blocked
<
2. After the demo, sweep every open task in today's file (:SNew), per team: >
    done B-11 B-121
    carry B-1221                 not finished: to next sprint's planning
    drop B-23                    out of the sprint
    redo B-101 demo found the reset mail unsent
    note retro: pair on the ICD next sprint
<
3. Compile and write the reports: >
    :SDry
    :SCompile
    daily.pl review              the sprint report, reports/sprint-N-report.*
    daily.pl report
    daily.pl rollup              on the first review of a month
<
4. Commit and mark the close: >
    daily.pl commit
    git tag sprint-7
<
You are done when: `daily.pl sprint 7` shows Open 0 for every team,
reports/sprint-7-report.html exists, and `git status` in the project is
clean.

See also: |agile-daily-review|, |agile-daily-velocity|, |agile-howto-planning|.

------------------------------------------------------------------------------
Refine the master backlog (Day 9)                     *agile-howto-refinement*

1. Intake new work to the master backlog, in today's file: >
    == Master
    new M-2 8 Cross-segment timing budget p:1 e:"E1 Engineer" t:"E Systems"
<
2. Hand tasks to teams, retire stale ones: >
    == SEI
    refine M-1                   master backlog -> SEI's backlog
    prune E-12223 merged into E-12222
<
3. Size them in the townhall with #est rounds (|agile-est-vote|), then: >
    :STally                      writes est lines into today's file
<   Uncomment the est lines you accept, then :SDry and :SCompile.
You are done when: `daily.pl backlog` (the master backlog) holds only what
you mean to keep, and `daily.pl backlog TEAM` lists the refined tasks with
sizes.

Add a person or a team                                    *agile-howto-people*

1. A person, name exactly as Teams shows it: >
    daily.pl roster add "Lee, Ann" ann.lee@example.com Alpha Lead ACME
    daily.pl roster              lists and checks against the journal
<
2. A team appears when a task is filed under it: a "== Gamma" section with a
   new line, compiled. Give it a capacity with cap at the next planning.
3. Add the new people to the townhall invitation: >
    daily.pl invite --dry        then without --dry to open it in Outlook
<
You are done when: `daily.pl roster` ends ", roster and journal agree".

Write the weekly A-Z metrics report               *agile-howto-metrics-weekly*

The 26 status metrics (A to Z) of a SysML v2 model under the pipeline,
collected from the model's git repository and its exports
(|agile-status-metrics|; definitions in docs/STATUS-METRICS.html). To see
it work first: perl sim/status-metrics-sim.pl ~/sm-demo builds the 12-week
Halberd example (repo, exports, metrics.json, history.jsonl).

1. Once: write metrics.json (repo, exports, segments, totals; Appendix A of
   docs/STATUS-METRICS.html, or copy the one the simulation writes) and
   freeze the denominators from the legacy exports: >
    perl bin/status-metrics.pl init --config metrics.json --xmi legacy.xmi --reqif export.reqif
<
2. Every working day, after the day's merges (a scheduled task or by hand): >
    perl bin/status-metrics.pl collect --config metrics.json --history history.jsonl
<   One snapshot is appended to history.jsonl. --as-of DATE collects a past
   day.
3. Friday, the report: >
    perl bin/status-metrics.pl report --config metrics.json --history history.jsonl --out report
<   It writes report/status-weekly.md (the A-Z table), report/status-daily.csv
   (open in Excel) and report/dashboard.json.
4. The dashboard: open docs/STATUS-DASHBOARD.html in Edge, paste
   dashboard.json into the "Data (JSON)" panel and press Apply.
5. For the status memo, paste rows of status-weekly.md into memo.md
   (|agile-howto-memo|).
You are done when: report/status-weekly.md has this week's column, the
dashboard shows today's date, and history.jsonl has one line per working day.

Port one segment from SysML v1 to v2                *agile-howto-port-segment*

The legacy model is a Cameo/MagicDraw XMI export; the target is SysML v2
text under model/SEGMENT/ in the model's git repository. The full guide is
docs/SYSML-PORT.html; the tools are |agile-xmi2sysml|, |agile-sysml| and
|agile-model-pl|. Practice it: |agile-practice-8|.

1. Export from Cameo: File > Export To > Eclipse UML2 (v5.x) XMI File, with
   stereotype applications included; save it as
   exports/DATE-legacy.xmi, outside the model repo.
2. Read the mapping report first (unmapped types, stereotypes not
   converted, type references not resolved): >
    perl ~/projects/agile/bin/xmi2sysml.pl --report exports/DATE-legacy.xmi
<
3. Convert into a branch, grammar-checked: >
    cd model-repo
    git switch -c port/SEGMENT
    perl ~/projects/agile/bin/xmi2sysml.pl --out ../scratch --check ../exports/DATE-legacy.xmi
    cp -r ../scratch/SEGMENT model/
<   (Convert into a scratch directory and copy only the segment being ported:
   a re-run overwrites hand edits. Requirements come out as one-line
   requirement usages, the form status-metrics counts; --req-style def
   writes requirement def blocks instead.)
4. Work the TODO lines (each names the v1 type and xmi:id): >
    :vimgrep /TODO/ model/SEGMENT/**/*.sysml
    :copen
<
5. Check it: >
    perl ~/projects/agile/tools/sysml/sysml.pl check model/SEGMENT/*.sysml
    perl ~/projects/agile/tools/sysml/model.pl lint
    perl ~/projects/agile/tools/sysml/model.pl check
<   In Vim: \mx this file, \ml the model, \mk the outline (|agile-vim-sysml|).
6. Commit the segment and merge through the gate: >
    git add -p model/SEGMENT
    git commit -m "port: SEGMENT from legacy.xmi DATE"
<
You are done when: sysml.pl check and model.pl lint exit 0 ("errors=0"),
:vimgrep /TODO/ finds none you have not accepted, and the segment is
committed.

------------------------------------------------------------------------------
Import a DOORS export                                      *agile-howto-doors*

DOORS requirements become SysML v2 requirements carrying their doorsId
(|agile-reqif2sysml|; details in docs/SYSML-PORT.html).

1. Export from DOORS: File > Export > ReqIF (a .reqif or .reqifz) with
   Object Heading, Object Text, the absolute number and the verification
   method. CSV is the fallback (columns Object Identifier, Object Level,
   Object Heading, Object Text, Verification Method).
2. Look first: >
    perl ~/projects/agile/bin/reqif2sysml.pl --report exports/DATE-system.reqif
<
3. Convert into the model repo; DOORS drops the module prefix from the
   absolute number, so put it back with --id-prefix: >
    perl ~/projects/agile/bin/reqif2sysml.pl --id-prefix SYS- --out model --layout "_reqs/{pkg}.sysml" --check exports/DATE-system.reqif
<   From CSV: add --csv and --col id="ID" --col text="Requirement" for
   columns with other names.
4. The trace against the model (metrics C, F, G, I: linked, orphans,
   unverified, completeness): >
    perl ~/projects/agile/bin/reqif2sysml.pl --report --model model exports/DATE-system.reqif
<
5. Commit the requirements files.
You are done when: the requirement files pass sysml.pl check, and the
--report --model run lists the orphans and unverified ids you will work.

Write a status memo                                         *agile-howto-memo*

1. Gather the facts (each prints text you can paste): >
    daily.pl status
    daily.pl quad
    daily.pl health
<
2. Write memo.md in Vim: one paragraph per point, lists for sub-points,
   "# SUBJECT" for a centred heading. Mark portions if your program does:
   {CUI}phrase{/}. In Vim, :r !daily.pl quad pulls text into the buffer.
3. Render it (|agile-memo|): >
    perl ~/projects/agile/tools/memo/md2memo.pl memo.md > memo.pdf
    perl ~/projects/agile/tools/memo/md2memo.pl --plain memo.md > memo.txt
<   From Vim: :!perl ~/projects/agile/tools/memo/md2memo.pl % > memo.pdf
You are done when: memo.pdf opens in Edge with numbered paragraphs (1. a.
(1)) and, when marked, the banner on every page.

Track funding and earned value                          *agile-howto-funding*

The funding journal is a separate ledger file (not the scrum journal),
read by ledger.pl (|agile-ledger|). The Halberd example has one: run
perl sim/halberd-gen.pl, then look at data/halberd/funding.ledger and its
complete-DATE.csv files.

1. Write funding.ledger in Vim: book the funds under Assets (so the funding
   side of a budget is not reported as a budget row), the time-phased
   budgets, and the spending, e.g. weekly labor: >
    2026-10-01 Funding received
        Assets:Funding:Halberd      $500,000.00
        Income:Contract
    ~ Monthly from 2026-10-01 to 2027-01-01
        Expense:Labor:Halberd        $120,000.00
        Assets:Funding:Halberd
    2026-10-09 Labor week 1
        Expense:Labor:Halberd         $28,000.00
        Assets:Funding:Halberd
<   ("until" works as well as "to"; a budget is prorated by day at the
   window edges.) Check it: perl bin/ledger.pl -f funding.ledger check
2. Spending month by month, and against the budget: >
    perl bin/ledger.pl -f funding.ledger bal -M Expense --depth 3
    perl bin/ledger.pl -f funding.ledger budget -M -b 2026-10-01 -e 2027-01-01
<
3. Earned value: write the percent complete per account in a CSV
   (complete-DATE.csv, lines "account,pct"), then: >
    perl bin/ledger.pl -f funding.ledger evm --now 2026-10-31 --complete-file complete-2026-10-31.csv
<   or give it inline: --complete Expense:Labor:Halberd=40 (repeatable).
4. When does the money run out: >
    perl bin/ledger.pl -f funding.ledger forecast --now 2026-10-31 --months 2 Assets
<
5. Put it on the cockpit: in scrum.conf set funding = funding.ledger and
   complete = complete-*.csv (|agile-conf-funding|), then perl agile.pl
   PROJECT and open the Funding tab.
You are done when: `ledger.pl check` prints "ok", evm shows a CPI and SPI
for every account (no "without a percent complete" line), forecast gives a
run-out date for the funding account, and the cockpit's Funding tab shows
the chart.

See also: |agile-ledger-evm|, |agile-ledger-forecast|, |agile-ledger-monthly|.

Recover from a bad compile                           *agile-howto-bad-compile*

A stand-up file with a mistake is rejected whole, every error listed:
nothing is half-applied. Fix the lines and compile again.

1. Before compile: :SDry (daily.pl --dry compile) is free. Use it until it
   prints no errors. Each error names the file and line; look the message
   up with: >
    perl ~/projects/agile/agile.pl help error "PASTED MESSAGE"
<
2. Compiled, but one line was wrong: never edit the journal's history.
   Post the correction as a verb in a new file: carry what you wrongly
   marked done, est to the right size, commit what you dropped.
3. Compiled, and the whole file was wrong, not yet committed: >
    git diff scrum.txt            what the compile appended
    git checkout -- scrum.txt
<   then delete the "# compiled ..." first line of the stand-up file, fix
   it, and compile again.
4. Compiled and committed: >
    git revert HEAD
<   then as in step 3: remove the "# compiled" line, fix, compile.
5. The journal itself will not load (you edited it by hand): >
    daily.pl status               the first error, with its line number
    perl ~/projects/agile/bin/ledger.pl -f scrum.txt check
<
You are done when: `daily.pl status` loads without an error and says "no
pending stand-up files", and `git status` is clean after `daily.pl commit`.

See also: |agile-err-not-applied|, |agile-err-already-compiled|.

Back up and commit the project data                      *agile-howto-backup*

Each project is its own git repository (daily.pl init made it). The kit's
own repository never holds journal data: data/ is ignored.

1. Every day, after compile: >
    daily.pl commit              git add -A and commit "standup DATE"
<
2. Once: a second copy on approved storage, a bare repository on a share: >
    git init --bare //server/share/scrum/myprogram.git
    git remote add origin //server/share/scrum/myprogram.git
    git push -u origin HEAD
<   then after each commit: git push
3. Or a single file you can copy anywhere: >
    git bundle create ../myprogram-DATE.bundle --all
<   Restore with: git clone myprogram-DATE.bundle myprogram
4. Before a big change (a hand edit of scrum.txt): >
    git tag before-edit
<
You are done when: `git status` is clean, `git log -1` shows today, and
`git push` (or the bundle) is up to date. Remember the marking: the
repository is marked whenever its content is (|agile-conf-banner|).

Practise coding for an interview                *agile-howto-practice-coding*

One session (30 to 60 minutes), from Git Bash in the kit, all offline. The
full plan for the first 90 days is docs/DRILLS.html; the commands are in
|agile-drills|.
1. Ask what is next: >
    perl drills/drill.pl next
<   It names one problem (the first unsolved ladder rung, a failed one to
   finish, a phased drill, or the weakest section) and why.
2. Read it, ask the eight questions, start the clock: >
    perl drills/drill.pl start p12-dedup
<   Your file is ~/drills-work/p12-dedup.pl. Write the assumptions as
   comments first; say the pattern, the complexity and one edge case aloud.
3. Edit and test, again and again (in Vim: \do opens your file, \dt tests): >
    vim ~/drills-work/p12-dedup.pl
    perl drills/drill.pl test p12-dedup
<4. Log it before you stop (minutes and the result are filled in): >
    perl drills/drill.pl log p12-dedup "hash of seen tokens; forgot //="
<5. Only after an honest attempt, compare: perl drills/drill.pl solution
   p12-dedup.
6. Five minutes of recall in Vim: :DrillTrain (|agile-drills-trainer|).
You are done when: drill.pl test passes, the log has the line, and you could
say the pattern and its complexity without the page.

==============================================================================
2. GETTING STARTED                                               *agile-start*

The kit is plain text and core Perl: the journal is a ledger file you edit
in Vim, and Perl compiles and reports it. Nothing is installed and nothing
needs the network. docs/README.html is the overview, docs/WORKFLOW.html the
operating model, docs/TUTORIAL.html the editing walkthrough, and
docs/TRAINING.html a replay of one whole sprint.

------------------------------------------------------------------------------
Getting the kit                                                  *agile-clone*

Clone it anywhere (nothing depends on the location), or unzip a release
(|agile-release|). Git Bash is the shell for everything here. Run the tests
once to know this machine's Perl is fine: >
    cd ~/projects/agile
    for t in tests/*.t; do perl $t | tail -1; done
<
Layout: bin/ (the commands), lib/ (the modules), vim/ (Vim support and
this help), tests/, docs/, sim/ (simulations and generators), tools/ (IDEF0,
memo, SysML), data/ (your projects, never committed to the kit).

------------------------------------------------------------------------------
Setting up Vim                                                   *agile-vimrc*

Add to ~/.vimrc (Git Bash: vim ~/.vimrc): >
    syntax on
    source ~/projects/agile/vim/scrum.vim
    let g:markdown_fenced_languages = ['idef0']
<
The source line adds the :S commands and \s keys (|agile-vim|), the file

A shell alias                                                    *agile-alias*

The help writes "daily.pl"; with an alias you can type it that way.
In ~/.bashrc: >
    alias daily='perl ~/projects/agile/bin/daily.pl'
    alias agile='perl ~/projects/agile/agile.pl'
<
daily.pl finds the project's scrum.conf by searching upward from the
current directory, so `cd` into the project first.

------------------------------------------------------------------------------
Your first project                                       *agile-first-project*

One directory per program, its own git repository: >
    daily.pl init ~/scrum/myprogram
    cd ~/scrum/myprogram
<
init writes scrum.conf, an example scrum.txt (all comments), standups/,
reports/, .gitignore and .gitattributes, and runs git init. Then:
1. Edit scrum.conf: recipients, the townhall time, facilitator (your Teams
   display name), the marking (|agile-conf|).
2. Add people: daily.pl roster add "Lee, Ann" ann@example.com Alpha Lead ACME
3. Seed the backlog: daily.pl new, then new lines under "== Team"
   (|agile-verb-new|), then compile. The first file says "sprint 1"; tasks
   you commit there start the sprint.
Keep projects anywhere; under the kit, data/NAME is ignored by the kit's git.

3. DAILY.PL, THE DAY-TO-DAY DRIVER                               *agile-daily*

    daily.pl [OPTIONS] COMMAND [ARGS]       (no command: status)

Every command finds scrum.conf upward from the current directory.

Each day            new  compile  report  draft  brief  commit  all  status
Before the call     drill  propose  cards  attend  invite  meetings
During the call     lint
After the call      answers  chat  joined  ai  post
Views               sprint  velocity  backlog  members  epics  roadmap
                    blocked  quad  health
Reports             review  rollup  csv
Setup and checks    init  check  roster  help

One command's help: daily.pl help COMMAND (or :help agile-daily-COMMAND).

------------------------------------------------------------------------------
Options for every command                                *agile-daily-options*

--today YYYY-MM-DD   act as if it were that day (catch up, replay, rehearse)
-c FILE, --conf FILE use that scrum.conf instead of searching upward
--dry                compile: show what would be written, write nothing;
                     invite: show the invitation, create nothing
--team T             cards, drill: one team
--to A --cc B --subject S   draft, brief: override scrum.conf
--force              draft, brief, cards, invite: go on despite marking errors
--send / --draft     cards: send the mails / open them as drafts; post: send
--reply --confirm --private --table      lint (|agile-daily-lint|)
--guess --assume     answers (|agile-daily-answers|)
-n N --sheet --grade FILE                drill (|agile-daily-drill|)
--until YYYY-MM-DD   invite: the last day of the series

------------------------------------------------------------------------------
The commands                                           *agile-daily-commands*

daily.pl help                                               *agile-daily-help*
daily.pl help COMMAND, daily.pl --help, daily.pl -h
Prints this chapter, or one command's section. Works outside a project.

daily.pl init [DIR]                                         *agile-daily-init*
Make a project in DIR (default: here): scrum.conf, scrum.txt, standups/,
reports/, .gitignore, .gitattributes, and git init. Existing files are kept.
Prints the next steps. See |agile-first-project|.

daily.pl new [TEAM...]                                       *agile-daily-new*
Create (or just name) today's stand-up file standups/DATE.txt: the date, the
current sprint, and a "== Team" section per team with its open tasks listed
as comments. Prints "created" or "exists" and the path. Vim: :SNew (\sn).

daily.pl status                                           *agile-daily-status*
The journal at a glance: tasks, current sprint, teams, pending (not yet
compiled) stand-up files, and the sprint's done points. The default
command. It also proves the journal loads: an error here names the line.

daily.pl compile                                         *agile-daily-compile*
daily.pl --dry compile
Apply every pending stand-up file, oldest first: validate every line,
append the ledger entries to the journal, and mark the file "# compiled".
A file with any error is NOT applied (every error is listed) and compile
stops there. --dry prints what would be appended and writes nothing.
Vim: :SCompile (\sc), :SDry (\sd). Errors: |agile-err-not-applied|.

daily.pl report                                           *agile-daily-report*
Write every report into reports/: dashboard.html, tree.html, roadmap.html,
cockpit.html, DATE-status.html/.txt, DATE-brief.html/.txt,
DATE-quad.html/.txt, sprint-N-report.*, MONTH-rollup.*, and the CSVs.
Marked when scrum.conf sets a banner. Vim: :SReport (\sr).

daily.pl draft [--to A] [--cc B] [--subject S] [--force]   *agile-daily-draft*
The status mail as an Outlook draft (classic Outlook on Windows): metrics,
blockers, today's notes, flags, the AI summary if any. You review and send.
Refuses on a marking error unless --force. Vim: :SDraft.

daily.pl brief [--to A] [--cc B] [--subject S]              *agile-daily-brief*
The short leadership mail (one sentence and up to five bullets), as an
Outlook draft. Same marking gate as draft.

daily.pl commit                                           *agile-daily-commit*
git add -A and commit "standup DATE" in the project. Prints "committed" or
"nothing to commit". Vim: :SCommit.

daily.pl all [--draft]                                       *agile-daily-all*
compile, report, (draft with --draft), commit. Stops after compile if a file
was rejected. Vim: :SAll (\sa).

daily.pl check                                             *agile-daily-check*
Load the journal and check the marking set-up: "ok: N tasks, teams ...,
sprints ..." and "marking: ok/off" or the problems. Exit 1 on a marking
error. Run it after editing scrum.conf.

daily.pl drill [TEAM] [-n 12]                              *agile-daily-drill*
daily.pl drill --sheet [TEAM]     daily.pl drill --grade FILE
The memory drill: question cards from the journal and roster (teams and
initials, tomes, epics, who owns what, blockers); you type terse answers
(ids, codes, initials, any order; ? for don't know, q to stop). Progress is
kept in drill.txt (Leitner boxes). --sheet writes reports/DATE-drill.txt to
answer in Vim; --grade grades it (what :w does). Vim: :SDrill (\sm).

daily.pl propose [TEAM...] [--private]                   *agile-daily-propose*
Today's status for each person, drafted from yesterday's answers and the
journal, one paste-ready line each. Writes standups/DATE-proposals.txt so a
"+1" in the chat accepts the line (|agile-ack|). --private writes
reports/DATE-propose.html with a 1:1 Teams link per person. Vim: :SPropose.

daily.pl cards [--team T] [--send | --draft]               *agile-daily-cards*
Each member's card (their sprint tasks, blockers, the Y/T/B reminder) to
reports/DATE-cards.txt and .html (with Teams 1:1 links). --send mails them
through Outlook, --draft opens them as drafts. Vim: :SCards.

daily.pl attend                                           *agile-daily-attend*
Attendee responses of today's stand-up meetings (Outlook calendar, or the
mock fixture) into today's stand-up file as comments and suggested absent
lines, and into attendance.csv.

daily.pl invite [--dry] [--until YYYY-MM-DD] [--force]    *agile-daily-invite*
The recurring weekday townhall in Outlook/Teams, the roster as attendees,
at townhall_start for townhall_minutes, the Y/T/B rules in the body. Opens
it for you to review and send. --dry prints it only. Refuses an attendee
outside mail_domains unless --force.

daily.pl meetings                                       *agile-daily-meetings*
Today's calendar: time, subject, Teams or not, number invited.

daily.pl lint [FILE | -] [--reply] [--confirm] [--private] [--table]
                                                            *agile-daily-lint*
Check every Y/T/B status in a pasted chat (default: today's chat files)
while people are still on the call. One line per person:
FILE:LINE: ERROR|warn|ok Name: reason. "-" reads standard input:
powershell Get-Clipboard | daily.pl lint -
--reply      only the lines to paste back into the chat
--confirm    also a read-back for clean statuses (until readback_clean_days)
--private    reports/DATE-lint.html: a Teams 1:1 link per person
--table      what the parser understood: state, who, Y, T, B, note
Exit 1 when any status has an ERROR. Vim: :SLint (\sl), :STown, :SLintReply.
The messages: |agile-err-lint-no-ytb|, |agile-err-lint-dup-delim|.

daily.pl answers [--guess] [--assume]                    *agile-daily-answers*
Parse today's chat files for Y/T/B answers: write
standups/DATE-Team-answers.txt, raise flags (silent, blocked N days, same
plan N days, unknown ids, done claims), log attendance, and append
suggested lines (done, unblock, absent, punt, hold, pass, all commented for
you to confirm) to today's stand-up file. --guess accepts the lint's
"did you mean" reading where the strict one failed; --assume records the
silent with their proposal, marked assumed (never moves points).
Vim: :SAnswers.

daily.pl chat [FILE]                                        *agile-daily-chat*
Tally #est and #vote rounds in today's chat (|agile-est-vote|) and append
est lines (commented unless there was consensus) and vote notes to today's
stand-up file. Vim: :STally (\st).

daily.pl joined [FILE...]                                 *agile-daily-joined*
Teams attendance-report downloads (standups/DATE[-Team]-attendance.csv)
into attendance.csv with join, leave and minutes. Vim: :SJoined.

daily.pl ai                                                   *agile-daily-ai*
Build the prompt for your approved AI service from today's answers, flags,
metrics and history. With ai_backend = paste it writes
reports/DATE-ai-prompt.txt: paste it into the service, save the reply as
reports/DATE-ai-response.txt, then daily.pl report includes it. Metrics
never come from the AI. Vim: :SAi, :SAiPrompt, :SAiResponse.

daily.pl post [--send]                                      *agile-daily-post*
Today's metrics text into each stand-up meeting's body in Outlook; --send
also sends the update to the attendees.

daily.pl roster                                           *agile-daily-roster*
daily.pl roster add "Name" email Team "Role" "Org"
List the people by team and check them against the journal (owners not in
the roster, team mismatches, missing e-mail). add adds or updates a person;
the name must be exactly what Teams shows.

daily.pl health [TEAM]                                    *agile-daily-health*
Every metric of the operating model against its threshold: blocked age,
load, done by day 8, velocity, predictability, carryover, bus factor,
unassigned, on-time, punt rate, backlog depth and age, intake, epic targets,
consensus, declines, silence. One line per signal with what to do. Exit 1
on a red.

daily.pl review [N]                                       *agile-daily-review*
The sprint report (Day 14) for sprint N (default: current): per team commit,
done, carry, load, velocity, predictability, punts, interrupts; printed and
written to reports/sprint-N-report.txt and .html.

daily.pl rollup [YYYY-MM]                                 *agile-daily-rollup*
The monthly roll-up (epics, intake vs done, backlog age, attendance),
printed and written to reports/MONTH-rollup.txt and .html.

daily.pl csv [TABLE]                                         *agile-daily-csv*
TABLE is items, sprints, epics, intake or health: one table to the screen.
No TABLE: all of them to reports/TABLE.csv (UTF-8 with a BOM, for Excel).

daily.pl quad [TEAM]                                        *agile-daily-quad*
The weekly quad: Technical Priorities (TODO, OPEN, DONE, WAIT, HOLD, PUNT,
DROP with REDO, PASS, SYNC marks), Watch Items, 30/60/90 Milestones,
Accomplishments, and the punt-rate table. Vim: :SQuad.

daily.pl sprint [N]                                       *agile-daily-sprint*
Per team: capacity, committed, done, open, carryover, removed, done %,
load %; then each team's open tasks. Vim: :SSprint.

daily.pl velocity                                       *agile-daily-velocity*
Committed and done per sprint per team, and the average done.

daily.pl backlog [TEAM]                                  *agile-daily-backlog*
The master backlog, or one team's: id, points, priority, epic, owner, age,
title. Vim: :SBacklog.

daily.pl members [TEAM]                                  *agile-daily-members*
Each owner's work in progress, done this sprint and queued, and committed
tasks with no owner. Vim: :SMembers.

daily.pl epics                                             *agile-daily-epics*
Roll-up by tome and epic: tasks, points, done, in sprint, backlog, done %.

daily.pl roadmap                                         *agile-daily-roadmap*
Epics by tome across sprints, with a forecast from velocity. Vim: :SRoadmap.

daily.pl blocked                                         *agile-daily-blocked*
Blocked tasks, oldest first, with days blocked: over 3 "escalate", over 5
"yours". Vim: :SBlocked.

4. THE STAND-UP FILE AND ITS VERBS                    *agile-standup* *agile-verbs*

standups/DATE.txt is where you type. One verb per line under a "== Team"
header; ; or # starts a comment. A file with any error is rejected whole.
More files on one day are fine: DATE-b.txt. Example: >
    2026-10-05
    sprint 7
    == Alpha
    done A-11 A-12
    block A-13 waiting on the ICD from SEI
    new A-14 5 Login MFA p:1 e:"A1 Access" t:"A Platform" o:"Lee, Ann"
    note Bob out Friday
<
Verb                   Does                                  Points move
done ID...             finished (passed the Definition of Done)
                                                   Committed -> Done
carry ID...            not finished; to next sprint  Committed -> Carryover
drop ID...             out of the sprint             Committed -> Removed
commit ID [OWNER]      into this sprint     backlog/carryover -> Committed
new ID PTS TITLE [p:N e:EPIC t:TOME o:OWNER]   intake  -> Backlog:Team
new! ID PTS TITLE ...  intake straight into this sprint    -> Committed
refine ID              master (or another team's) backlog -> this team's
prune ID REASON        retire a backlog task           Backlog -> Removed
est ID PTS             re-estimate (posts the difference)
assign ID OWNER        change the owner
block ID REASON        blocked (WAIT on the quad) until unblock ID
hold ID REASON         interrupted (HOLD) until resume ID
punt ID REASON         too hard as written          Committed -> Backlog
redo ID REASON         found wrong after the demo     Done -> Committed
pass ID TEAM           another team should do it   -> TEAM's Committed
sync ID ID...          coordinated across teams; they share DONE
cap N                  the team's capacity this sprint
note TEXT  risk TEXT  absent NAME...                  report only
sprint N               the sprint (top of the file, or in a section)

------------------------------------------------------------------------------
The rules of the file                                     *agile-standup-rules*

- The date comes from the file name (standups/2026-10-05.txt) or a
  YYYY-MM-DD line at the top.
- "== Team" starts a team's section; "== Master" is the master backlog
  (new lines there go to Backlog:Master); "==" alone ends a section.
- Quote values with spaces: o:"Bob Ray", e:"B1 Fire Control". commit and
  assign take the rest of the line as the owner: commit A-1 Bob Ray.
- Owner names must be spelled exactly as Teams shows them; "Last, First"
  works everywhere.
- Ids are any word without spaces (A-11, HAL-3). Several ids on one done,
  carry, drop, unblock or resume line are fine.
- A first line "# compiled DATE" means the file was applied; compile skips
  it. Never remove that line unless you have taken its entries out of the
  journal (|agile-howto-bad-compile|).
- In Vim, CTRL-X CTRL-K completes a task id from the journal.

------------------------------------------------------------------------------
The verbs one by one                                       *agile-verb-list*

done ID...                                                  *agile-verb-done*
Committed -> Done in this sprint, for each id. The task must be committed in
this sprint for this team (|agile-err-not-committed|).

carry ID...                                                *agile-verb-carry*
Committed -> Carryover: not finished. The next sprint's planning brings it
back with commit ID.

drop ID...                                                  *agile-verb-drop*
Committed -> Removed: out of the sprint and out of scope. For a task still
in a backlog use prune.

commit ID [OWNER]                                         *agile-verb-commit*
Into this sprint's commitment, from the team's backlog, the master backlog
or last sprint's carryover; the owner is optional (the rest of the line).

new ID PTS TITLE [p:N] [e:EPIC] [t:TOME] [o:OWNER]           *agile-verb-new*
new! ID PTS TITLE ...                                       *agile-verb-new!*
Intake: a new task into the team's backlog (or, under "== Master", the
master backlog). new! puts it straight into this sprint and tags it
interrupt: 1, so interrupts are measurable. p: priority (lower first), e:
epic, t: tome, o: owner. The id must be new (|agile-err-task-exists|).

refine ID                                                 *agile-verb-refine*
From the master backlog (or another team's backlog) into this team's.

prune ID REASON                                            *agile-verb-prune*
Retire a backlog task: to this sprint's Removed; the reason is kept on the
posting. For committed work use drop.

est ID PTS                                                   *agile-verb-est*
Re-estimate to PTS wherever the task's points are: the difference is posted,
history stays. #est rounds in the chat write these lines (|agile-est-vote|).

assign ID OWNER                                           *agile-verb-assign*
Change the owner (the rest of the line).

block ID REASON                                            *agile-verb-block*
unblock ID                                               *agile-verb-unblock*
Mark a task blocked, with the reason; it shows in every report, aging,
until unblocked. Over 3 days: escalate; over 5: yours (|agile-daily-blocked|).

hold ID REASON                                              *agile-verb-hold*
resume ID                                                 *agile-verb-resume*
Interrupted by higher-priority work: stays committed, HOLD on the quad.

punt ID REASON                                              *agile-verb-punt*
Too hard as written (any reason): Committed -> the team's backlog (TODO) for
replanning. Counted in the punt rate.

redo ID REASON                                              *agile-verb-redo*
Found wrong after the demo: last sprint's Done -> this sprint's Committed.

pass ID TEAM                                                *agile-verb-pass*
Started it, another team should do it: the whole task to TEAM's Committed in
the same sprint; that team assigns an owner.

sync ID ID...                                               *agile-verb-sync*
Tasks coordinated across teams this sprint: they share DONE (none counts
until all are done).

cap N                                                        *agile-verb-cap*
The team's capacity this sprint (load = committed / cap).

note TEXT                                                   *agile-verb-note*
risk TEXT                                                   *agile-verb-risk*
absent NAME...                                            *agile-verb-absent*
Report-only lines: they appear in the status mail and reports, move no
points. "note retro: ..." records a retro action.

sprint N                                                  *agile-verb-sprint*
The sprint the file (or the section) belongs to. Without it, the journal's
current sprint. The first file of a project says sprint 1.

5. THE JOURNAL (SCRUM.TXT)                                     *agile-journal*

A double-entry ledger in ledger-cli format. A task's points move between
accounts, and the account they sit in is the task's state: >
    Backlog:Master -> Backlog:TEAM -> Sprint:N:TEAM:Committed -> Done
                                                    -> Carryover
                                                    -> Removed
<   Equity:Intake balances new tasks. Points are conserved; history is never
rewritten. Compile writes almost everything; you read it (:SJournal, \sj).

An entry is a date, a payee, and postings that sum to zero: >
    2026-09-23 Intake B-11 Define Software Requirements
        Backlog:BMC2       5 SP   ; id: B-11, epic: B1 Fire Control, owner: Ann, prio: 1
        Equity:Intake
<
A capacity block: >
    ~ Sprint 7
        Alpha    24 SP
<
------------------------------------------------------------------------------
Task metadata                                             *agile-journal-meta*

On a posting comment, "key: value" pairs after "; ". Later values override
earlier ones.
id        the task id (required on every posting that moves a task)
title     from the payee after the id, or title:
prio      priority, lower first
epic      the epic ("B1 Fire Control"); tome  the tome above it
owner     the owner (Teams display name)
team      the team
blocked   the blocker reason; empty = unblocked
hold      the hold reason; empty = resumed
punt redo pass sync    set by those verbs
interrupt 1 on new! tasks
target    YYYY-MM-DD: the epic's target date (on any of its tasks)

------------------------------------------------------------------------------
Editing the journal by hand                               *agile-journal-edit*

Only three safe cases, none of which move points: metadata fixes (owner,
epic, tome, prio on an intake line; :%s works for a renamed tome), bulk
intake at program start (better: sim/idef0-backlog.pl, |agile-idef0-backlog|),
and capacity blocks. After any hand edit: daily.pl status (it re-reads the
journal and reports the first error with a line number), then commit. Never
renumber or delete postings: corrections are new postings.

6. SCRUM.CONF                                                     *agile-conf*

key = value lines; # starts a comment; paths are relative to the file.
daily.pl init writes a commented one. daily.pl check validates it.

------------------------------------------------------------------------------
The keys                                                     *agile-conf-keys*

journal                                                   *agile-conf-journal*
The journal file. Default scrum.txt.

standups                                                 *agile-conf-standups*
The stand-up directory. Default standups.

reports                                                   *agile-conf-reports*
Where report writes. Default reports (keep it out of git).

unit                                                         *agile-conf-unit*
The unit of the points: SP by default (Halberd uses items).

to                                                             *agile-conf-to*
cc                                                             *agile-conf-cc*
Recipients of draft and brief (comma-separated).

subject_prefix                                     *agile-conf-subject_prefix*
Put at the start of every mail subject, e.g. INTERNAL.

banner                                                     *agile-conf-banner*
The marking banner (INTERNAL, COMPANY CONFIDENTIAL, ...). Empty: nothing is
marked. When set, every report, mail and printed page carries it, and the
marking gate runs before mail (|agile-err-marking-refused|).

marking_owner                                       *agile-conf-marking_owner*
marking_category                                 *agile-conf-marking_category*
marking_handling                                 *agile-conf-marking_handling*
marking_poc                                           *agile-conf-marking_poc*
The marking block under the banner: who owns the material, its category,
handling, and who to ask. check warns when owner or POC is empty.

mail_domains                                         *agile-conf-mail_domains*
Comma-separated domains; mail may only go to them (check, draft, brief,
cards, invite refuse otherwise).

history_days                                         *agile-conf-history_days*
Previous days of answers used for "stuck" and "blocked N days". Default 5.

default_team                                         *agile-conf-default_team*
The team of standups/DATE-chat.txt when the file name has no team.

facilitator                                           *agile-conf-facilitator*
Your Teams display name (; between several): your own chat lines are not
linted as statuses.

readback_clean_days                           *agile-conf-readback_clean_days*
After this many clean statuses in a row a person gets a read-back only on
errors (lint --confirm). Default 5.

townhall_subject                                 *agile-conf-townhall_subject*

7. THE CHAT: Y/T/B STATUSES, #EST AND #VOTE                        *agile-ytb*

People post one line in the meeting chat, capital Y T B as separators, task
ids in it: >
    Y did B-11   T doing B-12   B none
<   Also accepted: "Y: ... / T: ... / B: ..." on separate lines, yesterday:
today: blockers:, and 1/2/3. A name before the Y is ignored. Lowercase y t b
work only when unambiguous. A person's last message wins, so a repost
replaces the first.

What lint checks: the three fields are there, in order, not empty; Y and T
each name a task id; the ids exist in the journal. ERROR means the status
cannot be used; warn means it parses but says little.

The replies (lint --reply) go back into the chat, or 1:1 with --private:
"Did you mean: ...?" for an error, "Got it. Add the task id next time" for
a warning, and with --confirm a read-back "I read your status as: ...".

Acknowledging a proposed status                                    *agile-ack*
After daily.pl propose, a person accepts their proposed line by typing +1,
y, ok or a thumbs-up. answers and lint read standups/DATE-proposals.txt.

#est and #vote rounds                                         *agile-est-vote*
In the meeting type "#est B-104"; people answer with numbers. "#vote Ship
Friday? y/n" or "#vote Name: A B C" for a vote. After the meeting paste the
chat (:SChat) and run :STally (daily.pl chat): each round is tallied
(consensus, or median with outliers; plurality, majority or tie) and written
into today's stand-up file as est lines (ready when there was consensus,
commented otherwise) and note vote lines. Without markers:
chat.pl --est ID --since 09:07 FILE (|agile-chat-pl|).

xmi2sysml.pl                                                 *agile-xmi2sysml*
    perl bin/xmi2sysml.pl --report FILE.xmi
    perl bin/xmi2sysml.pl --out DIR [--layout '{seg}/{pkg}.sysml'] [--check] FILE.xmi

A SysML v1 XMI export (Cameo / MagicDraw) to SysML v2 text, one file per
top-level package (DIR/SEGMENT/PACKAGE.sysml). --report: elements in by

reqif2sysml.pl                                              *agile-reqif2sysml*

DOORS requirements (ReqIF, zipped ReqIF, or a CSV export) to SysML v2

The SysML views toolkit                                    *agile-sysml-views*

tools/sysml/views/ holds standalone core-Perl tools that read any SysML v2
text model (a directory or files) and draw or check it. Each one runs on
its own (perl tools/sysml/views/TOOL.pl ...); model.pl draw, plates, diff,
threats and gate run them on the current project's model/ and pass every
other option through (a --root after the command is the tool's, not the
project's). Diagnostics are GNU format, FILE:LINE: error|warning|note: ...;
exit 0 clean, 1 findings, 2 usage or input error. Outputs are deterministic:
pin dates with --today / --date.
The security checks read the SecMeta library (tools/sysml/views/library/
SecMeta.sysml; copy it into model/): @Marking { level = Level::U; } on every
root package, @TrustZone { zone = Zone::dmz; } on parts at a boundary,
@SecurityRequirement and @Mitigates { threat = "t"; } on requirements, and
threats as metadata t : Threat { stride; capec; asset; mitigation; } lines
(or @Threat on an element). DrawingMeta.sysml beside it adds @Drawing for
plates. The binder scripts sysml-gate.pl and sysml-trace.pl (text checks,
satisfied + verified leaves) are in views/binder/. Golden harness: bash
tools/sysml/views/tests/run.sh (tests/sysml-views.t runs it). Usage of every
tool: tools/sysml/views/README.txt. A live view beside Vim:
|agile-sysml-view|.

model.pl diff                                               *agile-model-diff*
                                                            *agile-sysml-diff*
    perl tools/sysml/model.pl diff [-o PREFIX] [--changed] OLD_DIR [NEW_DIR]
    perl tools/sysml/model.pl diff [-o PREFIX] --git OLD[..NEW] [PATH...]

A model change as a review: PREFIX-tree.svg and PREFIX-trace.svg colored by
change (added green, changed amber, removed red), PREFIX-packages.svg and

model.pl threats                                         *agile-model-threats*
                                                         *agile-sysml-threats*
    perl tools/sysml/model.pl threats [--today YYYY-MM-DD]

The threat table (threat, STRIDE, CAPEC, mitigated by, status), then the
checks: every threat has one of the six STRIDE categories and a CAPEC-n id
(SEC-2); every threat is named by a @Mitigates on a requirement that is
satisfied and verified (SEC-3); a current @RiskAcceptance (approver set,
expires >= today) turns an open threat into a listed warning; a threat's
mitigation attribute must match its @Mitigates. Exit 1 on errors.

16. PRACTICE LESSONS                                          *agile-practice*

Hands-on lessons in sandbox projects under data/practice/ (ignored by git;
throw them away any time). Each lesson sets up a fresh project, prints the
task, and checks your result: >
    perl agile.pl practice                list the lessons
    perl agile.pl practice 1              set up lesson 1, print the task
    perl agile.pl practice check 1        what is done, what is missing
    perl agile.pl practice reset 1        remove the sandbox
<   Work inside the sandbox (cd data/practice/lesson1). The task text below
says daily.pl for perl KIT/bin/daily.pl (|agile-alias|). Each check prints
"lesson N: done" when everything is right.

------------------------------------------------------------------------------
Lesson 1: the first stand-up file and compile               *agile-practice-1*

Sandbox: a new, empty project (daily.pl init).
Task:
1. Make today's file: daily.pl new (or :SNew in Vim).
2. Under its "sprint 1" line add a team and three tasks, and commit two of
   them with a capacity: >
    == Alpha
    cap 10
    new AL-1 3 Set up the build p:1 e:"A1 Tooling" o:"Ann Lee"
    new AL-2 5 Write the ICD p:2 e:"A1 Tooling" o:"Bob Ray"
    new AL-3 2 Draft the test plan p:3 e:"A1 Tooling" o:"Ann Lee"
    commit AL-1 Ann Lee
    commit AL-2 Bob Ray
<
3. daily.pl --dry compile until it is clean, then daily.pl compile.
4. daily.pl status, daily.pl sprint, then daily.pl commit.
Check: three or more tasks in the journal, two or more committed in sprint
1, a capacity for sprint 1, no pending stand-up file, and a git commit.

------------------------------------------------------------------------------
Lesson 2: carry, block and unblock                          *agile-practice-2*

Sandbox: a copy of the Halberd project, mid-sprint, compiled up to
yesterday.
Task:
1. daily.pl sprint: note the open tasks of the current sprint.
2. In today's file (daily.pl new), block the oldest open task with a
   reason: block HAL-N waiting on the shared runner. Compile.
3. Make a second file for today, standups/DATE-b.txt, with the same first
   two lines (the date, sprint N) and "== Halberd". In it: unblock that
   task, and carry another open task. Compile.
4. daily.pl blocked (now empty), daily.pl commit.
Check: today a task was blocked with a reason and unblocked again, a task
went to Carryover today, nothing pending, and a commit after the set-up.

------------------------------------------------------------------------------
Lesson 3: close the sprint and report                       *agile-practice-3*

Sandbox: a copy of the Halberd project, mid-sprint.
Task: close the current sprint as on Day 14 (|agile-howto-review|).
1. daily.pl sprint: every open task.
2. In today's file mark each one done or carry, compile.
3. daily.pl review, daily.pl report, daily.pl commit.
Check: no open points left in the current sprint,
reports/sprint-N-report.txt and reports/DATE-status.html exist, nothing
pending, a commit after the set-up.

Lesson 4: the townhall chat lint                            *agile-practice-4*

3. For each ERROR, add a corrected repost at the end of the chat file, as

4. daily.pl lint again until there is no ERROR, then daily.pl answers.
Check: lint finds no ERROR in today's chat, and today's answers file exists.

1. perl KIT/drills/drill.pl show p12-dedup --dir SANDBOX: read it twice.
2. perl KIT/drills/drill.pl start p12-dedup --dir SANDBOX
3. Write the solution in SANDBOX/p12-dedup.pl (vim; a hash of seen tokens).
4. perl KIT/drills/drill.pl test p12-dedup --dir SANDBOX until it passes.
5. perl KIT/drills/drill.pl log p12-dedup --dir SANDBOX "what was slow"
Check: p12-dedup was started, the file is no longer the stub, a passing test
is recorded, and the drill log has p12-dedup as passed.

18. TROUBLESHOOTING                                         *agile-trouble*

Every message the kit prints on an error is in the catalog, |agile-errors|
(vim/doc/agile-errors.txt), with what it means and the fix. Paste one: >
    perl agile.pl help error "PASTED MESSAGE"
<
When there is no message:
- A :S command does nothing or says scrum.conf is missing: you are not in a
  project directory. :pwd, then :cd to the project (|agile-err-no-scrum-conf|).
- :help agile says "Sorry, no help": the source line is not in ~/.vimrc, or
  vim/doc is not writable so :helptags could not run; run
  :helptags ~/projects/agile/vim/doc once.
- A report looks stale: daily.pl report rewrites reports/; press F5 in the
  browser; agile.pl rebuilds ./dashboard.html.
- Numbers look wrong: the journal is the truth. daily.pl sprint, then
  :SJournal and * on the task id to walk its postings.
- Mail does not open: draft, brief, cards and invite need classic Outlook on
  Windows (|agile-err-powershell|). Everything else works without it.

20. CODING DRILLS                                              *agile-drills*

Interview-style coding practice in core Perl, offline, with nothing but Git
for Windows: a ladder of 29 problems from trivial to hard (the binder's
"Coding drills" chapter), about 130 more in technique sections (hashing, two
pointers, sliding window, stacks, binary search, linked lists, trees, graphs,
backtracking, dynamic programming, intervals, heaps), a four-phase drill in
which the requirements change, the drill log, the refresher plan, and a Vim
memory trainer. docs/DRILLS.html is the 90-day guide. >
    perl drills/drill.pl next              what to do next, and why
    perl drills/drill.pl start ID          your file from the stub, clock on
    perl drills/drill.pl test ID           pass/fail per case, minutes so far
    perl drills/drill.pl log ID NOTE       one line in the drill log
<Your files, the log and the trainer's progress live in the workspace:
~/drills-work, or $DRILLS_WORK, or --dir DIR on any command. drill.pl never
writes inside the kit. An ID can be shortened while it stays unique: p12 for
p12-dedup, two-sum. Statements are written for this kit; a LeetCode line in
each names the classic problem it resembles, as a pointer only.

------------------------------------------------------------------------------
The commands                                          *agile-drills-commands*

drill.pl help [COMMAND]                                    *agile-drills-help*
perl drills/drill.pl help, drill.pl --help
This chapter, or one command's section.

drill.pl list [SECTION]                                    *agile-drills-list*
Every problem by section (a section is also a trainer level): its id, the
pattern, the timebox in minutes and your status (-, started, failed,
passed). SECTION is a name (ladder, graphs), a prefix or a level number.

drill.pl show ID                                           *agile-drills-show*
Print a problem's statement: the contract, the input and output, the edge
cases worth asking about, the examples.

drill.pl start ID [--fresh]                               *agile-drills-start*
Copy the problem's stub (the signature and an empty body) to the workspace
as ID.pl, record the start time, print the statement. An existing file is
kept; --fresh moves it to old/ and starts again from the stub (the binder's
"solve it again cold").

drill.pl test ID [FILE] [--ref]                            *agile-drills-test*
Run the problem's tests against your file (default: the workspace's ID.pl):
pass or FAIL per case with the expected and actual values, the run time and
the minutes since start against the timebox. Exit 0 when every case passes.
Each case has a time limit (5 s); a die, an exit or an endless loop in your
code fails that case, nothing more. --ref tests the reference solution.
Function problems are called directly (your file defines the named sub);
stdin problems run as a script with the case on stdin, and the output is
compared ignoring trailing blanks, as the binder's check.sh does.

drill.pl check [SECTION | tN | ID-PREFIX] [--ref]         *agile-drills-check*
Test every file you have in the workspace (all of them, a section, a ladder
tier such as t2, or ids starting with p2): one line each, then "N passed, M
failed, K not started". The binder's ./check.sh.

drill.pl solution ID [--force]                         *agile-drills-solution*
Print the reference solution with its notes: the pattern, why it works, the
time and space complexity, the edge cases and the Perl idioms. Only after an
attempt was recorded (start or test); --force overrides. The log counts
every look (the "peeked" column of stats).

drill.pl log [ID [MINUTES] [pass|fail] [NOTES]]             *agile-drills-log*
drill.pl log --session N
With no arguments, print the drill log. With an ID, append one line
"date | problem | minutes | passed | notes" to log.txt in the workspace;
MINUTES defaults to the time since start, pass/fail to the last test.
--session N appends the binder's session form (done, slowest thing,
lookups, narration check, questions check, one thing to redo) for you to
fill in with Vim. The log is append-only plain text.

drill.pl stats                                            *agile-drills-stats*
Per section: problems, started, passed, peeked, minutes logged; the weakest
section you have started; the log's days.

drill.pl next                                              *agile-drills-next*
The refresher plan as one suggestion: a problem whose last test failed
first; then the ladder in order (t0 and t1 in session 1, t2 in session 2, t3
in session 4, t4 in session 5) with the phased drill after t2 (session 3)
and again after t4 (session 5); then the field drills (t5); then the
weakest section; when everything passes, the problem passed longest ago, to
re-solve cold (start --fresh).

drill.pl phased [N | test N [FILE] | solution] [--scenario S]
                                                         *agile-drills-phased*
The four-phase drill: one problem whose requirements change three times in
an hour. With no argument, the clock plan. phased 1 prints phase 1's card,
starts the clock and writes phased-SCENARIO.pl (a solve sub to fill in);
read phase N+1 only when phase N passes "phased test N". phased solution is
the reference, after an attempt. Scenarios: sensors (pair two sensor
feeds) and payments (match orders to payments); a second run uses the
other, or DRILL_SEED=99 for fresh sensor data.

drills/NN-SECTION/ID/statement.txt   header lines (Title, LeetCode, Origin,
                                  Pattern, Timebox, Kind, Call), then the

------------------------------------------------------------------------------
The Vim trainer                                        *agile-drills-trainer*

The "vanishing cues" memory game over the reference solutions. Each section
is a level and each solution a card. A card shows the first line of a
solution (sub two_sum {) and you type the rest. Every card is a cycle of
g:drills_fade_steps reps (default 5): rep 1 shows the whole solution to
copy, each later rep blanks out more of its words, the last rep shows
nothing. Only that blind rep counts. A wrong answer repeats the rep; giving
up on a hinted rep fades it further. A level is cleared only when every
card's blind rep was right first try, which unlocks the next level; the
highest unlocked level is kept in WORKSPACE/trainer.txt. Comments, blank
lines, spacing and indentation are ignored when checking; the code must
match. Between cards: Space or Enter continues, l chooses a level, r
replays, n starts again, q quits. Settings: g:drills_work (the workspace),
g:drills_fade_steps, g:drills_shuffle (0 keeps the cards in order).

:DrillTrain [N]                                                  *:DrillTrain*
Open the trainer at the highest unlocked level, or at level N.

:DrillLevel [N]                                                  *:DrillLevel*
\dl                                                                      *\dl*
Choose any unlocked level (asks when N is not given).

:DrillAnswer                                                    *:DrillAnswer*
\dc                                                                      *\dc*
Check the answer typed under the marker line (in insert mode: CTRL-G
CTRL-G). Right: straight on to the next rep or card. Wrong: the solution is
shown under your answer.

:DrillGiveUp                                                    *:DrillGiveUp*
\dg                                                                      *\dg*
Show the solution. On the blind rep it counts as a miss.

:DrillNext                                                        *:DrillNext*
\dn                                                                      *\dn*
After a miss or a level result: retry the rep, the next rep, the next card,
the level result or the next level (Space and Enter do the same).

\dr                                                                      *\dr*
Replay the current level from its first card.

:DrillQuit                                                        *:DrillQuit*
\dq                                                                      *\dq*
Leave the trainer. Cleared levels are already saved.

:DrillReset                                                      *:DrillReset*
Forget all progress: only level 1 is unlocked again (asks first).

:DrillOpen                                                        *:DrillOpen*
\do                                                                      *\do*
Jump between a problem's statement (drills/.../statement.txt) and your file
in the workspace. The first time, drill.pl start makes the file and starts
the clock.

:DrillTest                                                        *:DrillTest*
\dt                                                                      *\dt*
Save and run drill.pl test on this problem; the result opens in a split.

:DrillTestAll [SECTION | tN]                                   *:DrillTestAll*
\da                                                                      *\da*
drill.pl check: every file you have in the workspace, in a split.
