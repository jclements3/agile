== Answers to the exercises {#answers}

Every exercise in the book has an answer here, in book order. Where an exercise asks you to run something, the answer
runs it, and the output shown is what the kit really prints; the blocks are tested like every other command in the
book, so if your output differs, the difference is worth a look. Where an exercise asks for judgement, the answer is
a model answer: one good response, the reasoning behind it, and what any good answer must contain. Your answer can
differ from a model answer and still be right; it cannot leave out what the "must contain" lines name.

Many exercises ask about *your own* program. Those answers show what a good response looks like for Tidewater, so you
can see the shape, and then say what to look for in yours.

The commands below run in three places. A scratch folder holds drops, small models and offline GitLab projects
made for the answer. The `tidewater` folder is the simulation's state after sprint 6, the same one the sprint
chapters use. A few answers read the kit itself. Each block says which.

=== Part I: where they start {#answers-part-1}

::: answer [[documents--ex-1]]: Count the copies
A typical result for one interface requirement on a document-era program: the system specification (owned by the
systems engineering lead, updated at the last revision), the interface control document (owned by the interface
lead, two revisions behind), the requirements database export (owned by the requirements manager, refreshed monthly),
the verification matrix spreadsheet (owned by the test lead), and two briefings. Six places; on most programs two or
three agree word for word.

You cannot find out without reading them all, which is the point of the exercise. A good answer names the one tool
that would answer it mechanically: a comparison of the text with the same identifier in each place. In this book that
is the trace job's *drift* list, which compares DOORS text with the model's text for every requirement on every
change ([[pipeline]]).

Must contain: every place, an owner for each, a date for each, and an honest "I could not check this one" where that
is true.
:::

::: answer [[documents--ex-2]]: Reconstruct a change
Lay the change out as dated events: request raised, impact assessment started and finished, board scheduled, board
held, document updated, document re-baselined, downstream documents updated. Then mark each interval *deciding* (a
person working on it) or *waiting* (in a queue, an inbox, a calendar). On most programs the waiting is well over half
the elapsed time; the chapter's example was mostly waiting for the next board and for the document owners.

Must contain: the elapsed time, the decided time, the fraction waiting, and the one queue that held it longest.
That queue is the first thing a merge request with automatic checks removes.
:::

::: answer [[documents--ex-3]]: The five virtues
A model answer for Tidewater's document era:

- **Readable by anyone:** a Word file opens everywhere. Cost: anyone can read it, nobody can check it mechanically.
- **Contractually meaningful:** the specification is a deliverable with a signature. Cost: changing it takes a board.
- **Reviewed:** every revision went through a review meeting. Cost: weeks of calendar time per review.
- **Baselined:** revision letters and a document register. Cost: the register and the documents drift apart.
- **Traced:** a verification matrix spreadsheet. Cost: two days to rebuild it before every review.

Keep the page. After [[scorecard]], each line should have a GitLab counterpart: a text file anyone can read, a merge
request with approvals, review in hours, a protected tag, a trace job.
:::

::: answer [[cameo--ex-1]]: Measure it yourself
Generate drop 1 and search it:

```sh run sandbox=scratch expect="(?s)name=\"Battery\".*name=\"Battery_old\""
perl "$KIT/sim/tidewater-v1.pl" --drop 1 drop1 > /dev/null
grep -n -o 'name="Battery[^"]*"' drop1/tidewater.xmi
```

There are two: `Battery` and `Battery_old`. The real battery is the one something uses. A block is real if another
element has it as a type:

```sh run expect="(?s)Battery used 1 time.*Battery_old used 0 time"
for n in Battery Battery_old; do
  id=$(grep -o "xmi:id=\"[^\"]*\" name=\"$n\"" drop1/tidewater.xmi | sed 's/xmi:id="\([^"]*\)".*/\1/')
  echo "$n used $(grep -c "type=\"$id\"" drop1/tidewater.xmi) time(s)"
done
```

`Battery` is the type of the power system's battery part; `Battery_old` sits in the "Legacy Import" package and
nothing refers to it. Deciding by use, not by name, is the habit to keep.
:::

::: answer [[cameo--ex-2]]: Read the manifest
```sh run expect="tidewater.xmi: OK"
cd drop1
grep 'tidewater\.' MANIFEST.txt | tr -d '\r' | sed 's/^ *//' | sha256sum -c
```

The checksums match. If one did not, the file you hold is not the file the prime's build recorded: corrupted in
transit, edited by someone, or from a different build. Do not import it. Call the prime's modeler (the contract's
named technical contact) and ask for the drop to be sent again; record the event on the Prime Drop issue
([[prime-changes]]).
:::

::: answer [[cameo--ex-3]]: Belief and fact
A model answer sorts each belief into one of three columns:

- **About the language:** "SysML cannot express our constraints" (it can, with constraint blocks; the team never used
  them), "a requirement must be a diagram element" (it is an element; diagrams are views of it).
- **About the tool:** "the model is the diagrams", "you cannot merge two people's work", "you need a seat to read the
  model". These are Cameo's file format and licensing, not SysML.
- **About how the team was asked to work:** "the model must contain every document paragraph", "every slide needs a
  diagram", "nobody may delete anything". These came from how the port was ordered.

Must contain: at least one belief in each column. Most teams find the third column is the longest, which is good news:
it is the one they can change.
:::

::: answer [[directive--ex-1]]: Read your own directive
Three columns: what it says (quote it), what it requires (the minimum that would satisfy an auditor), what it leaves
open (everything else). For Tidewater's directive ([[directive]]), "adopt DevSecOps practices" *says* a lot and
*requires* little: a version-controlled model, automated checks, a demonstration within twelve weeks. It leaves open
the tools, the branching model, the measures and the team's pace.

The open items belong to the person who will be held to the result, which for an MBSE team is the model lead, with
the program manager's concurrence. Write them down as decisions ([[operating-model]]) so they stop being open.
:::

::: answer [[directive--ex-2]]: Write down the objections
The exercise is the method; a good result looks like Tidewater's list in [[directive]]: nine objections in the
speakers' words, each with a column "answered where, with what evidence". Typical entries: "we will lose the
diagrams" (answered by generated views, [[diagrams]]); "nobody will read text" (answered by the model site the program
office reads, [[tools]]); "this is a software process" (answered by the systems engineering share of the work,
[[bluf]]).

Must contain: the speaker's own words, not a paraphrase, and a planned date for each answer. An objection without a
date is a promise nobody is held to.
:::

::: answer [[directive--ex-3]]: Pick your measures
Five that work for most ports, each computable without judgement:

1. TODO lines left after conversion, from the pipeline's `todo` job; target zero; old-way baseline: none (nobody
   counted).
2. Requirements with a verification case, from the trace job; target: every requirement the government owns; old-way
   baseline: the last verification matrix, counted by hand.
3. Merge requests that went through a green pipeline and an approval, from GitLab; target: all of them after the
   first sprint; old-way baseline: changes made without a recorded review.
4. Change lead time, from GitLab analytics ([[analytics]]); target: days, not weeks; old-way baseline: the board cycle.
5. The team's pulse survey; target: rising; old-way baseline: the first retrospective.

The skeptic usually rejects the pulse survey ("feelings are not data") and the lead time ("you are comparing a typo
fix with a board decision"). Both objections are fair. Answer the first by keeping the survey anonymous and the
questions fixed; answer the second by comparing like with like, and by saying so on the slide.
:::

::: answer [[ex-vee-map]]: Map your program's Vee
A good answer names every rung on the right arm, puts "nobody" or "a person, before each review" against at least
one of them, and circles a rung below system verification: those are the repetitive ones. Tidewater's answer
circles the verification matrix, which used to take two people a week before each review.
:::

::: answer [[ex-vee-three]]: Find the three Vees
A merge request's Vee: any change into `develop`, with the ten jobs `gitlab.pl ci --list --event
merge_request_event --target develop` shows. A baseline's Vee: a `baseline-N` tag, with the thirteen jobs `--event
tag --tag baseline-N` shows, three of them the release jobs. The program's Vee: the next technical review, which
reads the latest baseline's release package.
:::

::: answer [[ex-vee-link]]: Break and mend a horizontal line
The job reports `orphans 2 -> 3 (new: ...)` and fails. Two sentences for the program manager: "The check stops a
change that breaks a link between a requirement and the design that meets it. The nine gaps already in the model are
the prime's, reported to the prime, and they are counted every day instead of blocking our work."
:::

::: answer [[ex-vee-twin]]: The thread before the twin
Most programs moving from documents have none of the four on day one; a good answer says so and names the first
step, usually stable ids from the prime and `doorsId` on every requirement. The decision a twin would change must
come with a number, for example "how many buoys to recover before winter, worth one vessel day each".
:::

::: answer [[devsecops--ex-1]]: Make your own list
A starting list, with the systems engineering term beside each:

|| DevSecOps term | Closest SE / CM term ||
| repository | controlled document library |
| commit | a change to a controlled item, with author and date |
| branch | a working copy for one change |
| merge request | engineering change request with its review |
| pipeline | configuration audit plus review checklist, run by machine |
| tag | baseline |
| release | published baseline with its release notes |
| runner | the machine the audit runs on (no equivalent) |
| artifact | review package, generated |
| code owner | approval authority for an item |

"Runner" and "pipeline schedule" usually have no equivalent; that is fine. Compare with the translation table in
[[devsecops]] and keep the words your team already uses for the rest.
:::

::: answer [[devsecops--ex-2]]: Which idea first?
For Tidewater the time-saver was automatic checks on every change (the grammar and lint jobs found in minutes what
review meetings found in weeks) and the most resisted was small changes reviewed one at a time ("we will drown in
reviews"). They are usually *different* ideas, and that matters: lead with the time-saver, because it pays for the
patience the resisted idea needs. A good answer names both and says which one you will introduce first.
:::

::: answer [[devsecops--ex-3]]: Follow a change
Write your change against the ten steps (issue, branch, edit, local check, commit, push, merge request, pipeline,
review and approval, merge). In a document-era process, steps 1, 7 and 9 usually exist (a change request, a review,
a signature), steps 4 and 8 do not exist at all (no automatic check), and step 10 is a person re-typing the change
into the master document. The time goes into the review queue and into re-typing. A good answer marks each step
"existed / missing / done by hand" and puts a duration on each existing one.
:::

::: answer [[sysmlv2--ex-3]]: Find a hidden error
```sh run expect="^1$"

```

There is only one, the energy balance. A discrepancy report for it: "The constraint `balance` on `EnergyBalance`

::: answer [[sysmlv2--ex-4]]: Write a state machine
```sh run expect="0 error"
cat > modes.sysml <<'EOF'
package ModesExample {
    state def BuoyModes {
        entry; then observing;
        state observing;
        state degraded;
        state maintenance;
        state recovered;
        transition observing_to_degraded first observing accept LowBattery then degraded;
        transition degraded_to_observing first degraded accept Charged then observing;
        transition to_maintenance first observing accept CrewOnSite then maintenance;
        transition degraded_to_maintenance first degraded accept CrewOnSite then maintenance;
        transition back_to_service first maintenance accept CrewDeparts then observing;
        transition lifted first maintenance accept LiftedAboard then recovered;
    }
    attribute def LowBattery;
    attribute def Charged;
    attribute def CrewOnSite;
    attribute def CrewDeparts;
    attribute def LiftedAboard;
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check modes.sysml
```

One new line, named so it reads as a sentence, reusing the existing `CrewOnSite` event.
:::

::: answer [[ex-recipe-decompose]]: Decompose by hand, then check
By hand: classification (missing; Tidewater is unmarked, so optional here), state and trigger (missing), specification
target "the power system", operative verb "shall", target verb "report", precise object "the battery state of charge",
modifier and modification (missing), reference (missing), exceptions (missing), ID TW-SEG-003. All required parts are
present. A test engineer needs the optional parts the sentence lacks: *to whom* it reports, *how often*, and *how
accurately*. Without them the requirement cannot fail a test.

```sh run expect="'report' with no measurable threshold"
perl "$KIT/tools/sysml/req-recipe.pl" --only TW-SEG-003 drop1/tidewater.reqif
```

The checker agrees: every required part found, one minor finding, no threshold.
:::

::: answer [[ex-recipe-split]]: Split TW-SYS-001
```sh run expect="requirements=2 findings=0 missing=0"
cat > split.txt <<'EOF'
(U) While in observing mode, each station shall measure wind speed, wind direction, air pressure and air temperature at least once every 10 minutes. (TW-SYS-001a)

(U) While in observing mode, each moored buoy shall measure wave height and wave period at least once every 30 minutes. (TW-SYS-001b)
EOF
perl "$KIT/tools/sysml/req-recipe.pl" --strict --require classification split.txt
```

What you had to decide: how often each quantity is measured (the original had no rate), whether waves are measured
only by buoys (the original said "each buoy shall *also*"), and in which mode the requirement applies. The rates
above are notional; on a real program they come from the stakeholder need, and asking for them is a discrepancy report
to whoever owns the wording.
:::

::: answer [[ex-recipe-stakeholder]]: A need that can be traced
"Mariners shall be able to obtain the latest marine bulletin and the latest observation from every station through a
public service, at any time, without an account." It stays a stakeholder need (it names the mariner and the outcome,
not a system element) and becomes verifiable by demonstration: the program office watches a mariner, with no account,
read the latest bulletin and observations. The evidence is the demonstration record. The weak verb "be able to read"
is replaced by an outcome someone can watch happen.
:::

::: answer [[ex-recipe-sysml]]: Add a constraint
```sh run expect="0 error"
cat > recipe-seg.sysml <<'EOF'
package RecipeSeg {
    private import ISQ::*;
    private import SI::*;
    part def PowerSystem { attribute socReportPeriod : DurationValue; }
    requirement def StateOfChargeReporting {
        doc /* The power system reports the battery state of charge at least once per reporting period. */
        subject power : PowerSystem;
        attribute reportingPeriod : DurationValue;
        require constraint { power.socReportPeriod <= reportingPeriod }
    }
    requirement tw_seg_003 : StateOfChargeReporting {
        attribute doorsId = "TW-SEG-003";
        doc /* (U) While in observing mode, the power system shall report the battery state of charge to the data logger every 10 minutes with an accuracy of 5 % of rated capacity, except during maintenance mode. */
        attribute :>> reportingPeriod = 10 [min];
    }
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check recipe-seg.sysml
```

```sh run expect="TW-SEG-003\s+score 100"
perl "$KIT/tools/sysml/req-recipe.pl" recipe-seg.sysml
```

The sentence carries the recipe for people; the constraint carries the same rule for the tools.
:::

::: answer [[ex-recipe-dr]]: Write the DR
One screen: a title ("DR-6: thirteen DOORS requirements do not meet the requirement recipe"), a table of the thirteen
IDs with one-line findings (TW-STK-001 weak verb "provide"; TW-STK-003 and TW-STK-004 "be able to"; TW-SYS-001 two
operative verbs; TW-SYS-012 "be serviceable"; the rest "no measurable threshold"), and the suggested wording for the
five in `recipe-rewrites.txt`.

Ask the prime to fix TW-SYS-001 and TW-SYS-012 first: TW-SYS-001 is two requirements in one sentence, so one of them
cannot be verified separately, and TW-SYS-012 has no satisfy in the model and no verifiable verb, so it blocks both
traceability and verification. The "no threshold" findings matter too, but they can wait for the wording owner's
next revision.
:::

=== The SysML v2 workbook {#answers-workbook}

Each answer below writes its snippet into the scratch folder and checks it. The snippets are complete files, so you
can run any one of them on its own.

::: answer [[ex-wb-loop]]: Break it three ways
```sh run expect="(?s)fixed.sysml.*0 error.*m1.sysml:3:5: error: unexpected 'part'.*m2.sysml:4:1: error: unexpected end of file.*m3.sysml:3:26: error: unexpected 'ballast'"
cat > fixed.sysml <<'EOF'
package Stations {
    part def Ballast;
    part def Hull { part ballast : Ballast; }
}
EOF
sed 's/part def Ballast;/part def Ballast/' fixed.sysml > m1.sysml
sed '$d' fixed.sysml > m2.sysml
sed 's/part ballast/prat ballast/' fixed.sysml > m3.sysml
for f in fixed m1 m2 m3; do echo "== $f.sysml"; perl "$KIT/tools/sysml/sysml.pl" check $f.sysml | head -1; done
```

Only the misspelled `prat` is reported on the line that is actually wrong (line 3, at the word after `prat`, because
the checker read `prat` as a name and then found another name). The missing `;` is reported one line *later*, where
the next statement starts. The missing `}` is reported at the end of the file, wherever that is. The two rules from
[[workbook]] in action: fix the first error first, and look one line up.
:::

::: answer [[ex-wb-packages]]: Narrow the imports
```sh run expect="0 error"
cat > packages.sysml <<'EOF'
package Stations {
    private import Types::StationMode;
    public import Interfaces::ObservationPort;
    part def Hull;
    part def Mooring { attribute mode : StationMode; }
}
package Types { attribute def StationMode; }
package Interfaces { port def ObservationPort; }
package Fourth {
    private import Stations::*;
    part def Check { part hull : Hull; port p : ObservationPort; }
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check packages.sysml
```

`Fourth` sees `Hull` and `Mooring` (Stations' own public members) and `ObservationPort`, because Stations imports it
*publicly* and so re-exports it. It does not see `StationMode`, which Stations imports privately. A public import is
a promise to every package that imports you; make imports private unless you mean that promise.
:::

::: answer [[ex-wb-names]]: Document a decision
```sh run expect="0 error"
cat > names.sysml <<'EOF'
package 'Data Center' {
    part def QualityControl {
        doc /* Checks each observation and sets its quality flag. */
    }
    comment about QualityControl
        /* Decision 2026-11: flag, do not delete. A deleted observation cannot be reviewed later, and the archive
           keeps every record with its flag (TW-SYS-005). */
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check names.sysml
```

The forecaster's document wants the `doc`: what quality control *is*. The decision belongs in review and in the
decision log; if it matters for years, it belongs in a decision record ([[operating-model]]), and the comment points
to it.
:::

::: answer [[ex-wb-parts]]: A shore station
```sh run expect="0 error"
cat > parts.sysml <<'EOF'
package Parts {
    part def SensorSuite;
    part def Battery;
    part def Cell;
    part def Mast;
    part def ObservingStation {
        part sensors : SensorSuite;
        part battery : Battery { part cells : Cell[4]; }
    }
    part def MooredBuoy :> ObservingStation;
    part def ShoreStation :> ObservingStation { part mast : Mast; }
    part def StationSegment {
        part buoys : MooredBuoy[1..*];
        part shoreStations : ShoreStation[1..*];
    }
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check parts.sysml
```

A cell in a buoy in the segment is four levels down from the segment: segment, buoy, battery, cell. The buoy inherits
the battery from `ObservingStation`, so the depth is the same in a shore station.
:::

::: answer [[ex-wb-redefinition]]: A shore-station suite
```sh run expect="0 error"
cat > redefinition.sysml <<'EOF'
package Redefinition {
    private import ISQ::*;
    private import SI::*;
    part def Sensor { attribute samplePeriod : DurationValue; }
    part def SensorSuite {
        part sensors : Sensor[1..*];
        attribute samplePeriod : DurationValue = 10 [min];
    }
    part def Barometer :> Sensor;
    part def ShoreSensorSuite :> SensorSuite {
        part barometer : Barometer :> sensors;
        attribute :>> samplePeriod = 5 [min];
    }
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check redefinition.sysml
```

Now without the `:>>`, in a lint project:

```sh run expect="errors=0 warnings=0"
mkdir -p lintdemo/model && printf 'title = Lint demo\n' > lintdemo/sysml.conf
sed 's/attribute :>> samplePeriod/attribute samplePeriod/' redefinition.sysml > lintdemo/model/Redefinition.sysml
perl "$KIT/tools/sysml/model.pl" --root lintdemo lint
```

Lint says nothing, and that is the lesson. Without `:>>` the suite declares a *second* attribute with the same name
that hides the inherited one; it is legal text and the kit's lint does not flag the shadowing. A full SysML v2 tool
with semantic checks (the OMG pilot implementation, `model.pl validate` with Java) reports it. Until then, reviewers
look for the same name declared twice in a specialization ([[reviewing]]).
:::

::: answer [[ex-wb-ports]]: A health interface
```sh run expect="0 error"
cat > ports.sysml <<'EOF'
package Ports {
    item def ObservationRecord;
    item def HealthReport;
    port def ObservationPort { out item observation : ObservationRecord; }
    port def HealthPort { out item health : HealthReport; }
    interface def ObservationLink { end transmitter : ObservationPort; end receiver : ~ObservationPort; }
    interface def HealthLink { end transmitter : HealthPort; end receiver : ~HealthPort; }
    part def TelemetryUnit { port obsOut : ObservationPort; port healthOut : HealthPort; }
    part def IngestService { port obsIn : ~ObservationPort; port healthIn : ~HealthPort; }
    part def Network {
        part telemetry : TelemetryUnit;
        part ingest : IngestService;
        interface link : ObservationLink connect transmitter ::> telemetry.obsOut to receiver ::> ingest.obsIn;
        interface health : HealthLink connect transmitter ::> telemetry.healthOut to receiver ::> ingest.healthIn;
    }
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check ports.sysml
```
:::

::: answer [[ex-wb-flows]]: Two flows
```sh run expect="0 error"
cat > flows.sysml <<'EOF'
package Flows {
    item def ObservationRecord;
    item def HealthReport;
    part def DataLogger { out item record : ObservationRecord; out item health : HealthReport; }
    part def TelemetryUnit { in item record : ObservationRecord; in item health : HealthReport; }
    part def Station {
        part logger : DataLogger;
        part telemetry : TelemetryUnit;
        connection toTelemetry connect logger to telemetry;
        flow of ObservationRecord from logger.record to telemetry.record;
        flow of HealthReport from logger.health to telemetry.health;
    }
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check flows.sysml
```

One connection is enough: the connection says the two parts are joined, and each flow says what crosses. Two flows on
one connection is usually clearer to a reviewer, because it mirrors the hardware (one cable, two kinds of traffic). A
second connection is right only when there really are two physical paths.
:::

::: answer [[ex-wb-values]]: A power budget's inputs
```sh run expect="errors=0 warnings=0"
cat > values.sysml <<'EOF'
package Values {
    private import ISQ::*;
    private import SI::*;
    private import ScalarValues::*;
    attribute def Power :> PowerValue;
    part def Battery {
        attribute stateOfCharge : Real;
        assert constraint socRange { stateOfCharge >= 0.0 and stateOfCharge <= 1.0 }
    }
    part def Station { attribute averageLoad : Power; }
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check values.sysml
mkdir -p lintvalues/model && printf 'title = Lint demo\n' > lintvalues/sysml.conf && cp values.sysml lintvalues/model/
perl "$KIT/tools/sysml/model.pl" --root lintvalues lint
```

A fraction from zero to one, constrained, is the simplest honest "percentage". Reading the library turns up
dimensionless ratio types too; use whichever your team agrees on, once, in the library package, so every model says
it the same way.
:::

::: answer [[ex-wb-expressions]]: A reserve
```sh run expect="0 error"
cat > expressions.sysml <<'EOF'
package Expressions {
    private import ISQ::*;
    private import SI::*;
    private import ScalarValues::*;
    part def Battery {
        attribute capacity : EnergyValue = 400 [W*h];
        attribute stateOfCharge : Real = 0.8;
        attribute usable : EnergyValue = capacity * stateOfCharge;
    }
    part def Station {
        part batteries : Battery[2];
        attribute total : EnergyValue = sum(batteries.usable);
        attribute reserve : EnergyValue = total - 15 [W] * 24 [h];
        constraint reservePositive { reserve > 0 [W*h] }
    }
}
EOF
perl "$KIT/tools/sysml/sysml.pl" check expressions.sysml
```

The English: "The usable energy of the station's batteries shall exceed one day of a 15 W load." The text form is
exact about units and arithmetic; the English is what a reviewer checks against intent. Keep both: the sentence in the
`doc`, the expression in the constraint.
:::

::: answer [[ex-wb-requirements]]: The battery requirement
```sh run expect="0 error"
cat > requirements.sysml <<'EOF'
package Reqs {
    private import ISQ::*;
    private import SI::*;
```

::: answer [[ex-git-practice]]: The practice afternoon
The recoveries, each as one command:

|| Mistake | Recovery ||
| broke a file you had not committed | `git restore FILE` |
| staged a file by mistake | `git restore --staged FILE` |
| wrong commit message on the last commit | `git commit --amend -m "..."` (only before pushing) |
| a commit that should not have happened, already shared | `git revert COMMIT` |
| a merge that went wrong, still in progress | `git merge --abort` |

The one to remember: on anything already pushed, use `revert`, never `amend` or `reset`. [[rescue]] has each one
played out.
:::

::: answer [[ex-git-conflict]]: A conflict with three sides
Two conflicts, one per merge: the first branch conflicts with the change on `main`, and after you resolve it the second
branch conflicts with the result. `git log --oneline --all --graph` shows two merge commits on `main`, each with two
parents. Resolve each so the line says what you mean, not by keeping both versions side by side; with
`merge.conflictstyle diff3` set, the middle section shows the original line, which tells you what each side changed.
:::


::: answer [[ex-vim-break]]: Break it three ways
- **Misspelled type:** the grammar check passes; lint reports `unresolved type` on the line of the usage.
- **Missing semicolon:** the grammar check reports it, on the *next* line, where the following statement starts.
- **Level tag on the wrong level:** the grammar check and lint both pass; `model.pl check` reports a level-tag
  mismatch on the part def. A misspelled tag name such as `@L1Netwrk;` passes all three, which is why the practice
  lesson's own check exists ([[vim]]).
:::

::: answer [[ex-vim-conflict]]: Resolve with the ancestor
For a single conflict, the marker search (`/^<<<<<<<` then `]c`-style editing) is faster: you see the three versions
in place and edit one line. For ten conflicts, `git mergetool` with Vim's three-way diff is better, because it walks
you from conflict to conflict and shows the base beside each side. Either way, the `diff3` middle section (the
ancestor) is what tells you who changed what.
:::

::: answer [[ex-stories-split]]: Split a story
By requirement group and by investigation versus result ([[stories-splitting]]):

1. "Stakeholder needs in the model" (the DOORS stakeholder module converted and merged): the `grammar` and `lint`

2. "System requirements in the model": the trace job shows every system requirement linked.
3. "Segment requirements in the model": the same for the segment module.

::: answer [[ex-setup-refuse]]: Make it refuse you
```sh run expect="(?s)not allowed to push code to protected branches.*-> develop.*not allowed to push code to protected branches.*-> main.*not allowed to create this tag as it is protected"
G="$PWD/gl"
gl() { perl "$KIT/bin/gitlab.pl" --local "$G" --project tidewater/model "$@"; }
git clone -q gl/repos/tidewater/model.git refuse-demo 2> /dev/null && cd refuse-demo
```

::: answer [[ex-setup-owners]]: Redraw the signature page
A specification's signature page usually reads: prepared by (author), reviewed by (subsystem leads), approved by
(chief engineer), CM release (CM lead). As a CODEOWNERS file over a folder of text files:

```text
[Systems lead]
/model/requirements/   @jim
[Interfaces] @jim
/model/library/Interfaces.sysml
[Segments]
/model/physical/stations/     @bob
/model/physical/datacenter/   @bob @tom
```

The CM release is not a code owner: it is the protected `baseline-*` tag. Signatures with no clear owner are usually
"reviewed by" lines that list a role nobody holds; those become an open question for the lead.
:::

::: answer [[ex-setup-branching]]: Defend a branching strategy
GitLab flow: `main` is the integration branch and the published model, releases are tags on `main`, and there is no
`develop`. In `project.conf`: set `default_branch = main`, remove the `develop` line from `[branches]` (and make `main`
`merge:developer`), and drop the `vendor/prime` line, since there are no drops. Monthly versions become tags without a
release branch.
:::

::: answer [[ex-layout-map]]: Place a new package
With Tidewater's map, an unlisted package lands under `unsorted/` (the map's `* = unsorted/` line), and the converter
says so in its report: "layout map: Drifters is not listed; written to unsorted/...". The `delta` job's report on the
drop merge request shows the same. In one merge request, before anyone edits it: add the package to the layout map in
the right layer, move the file there on the vendor branch by re-importing the drop with the new map, and add the folder
to CODEOWNERS (and to `layers` in `sysml.conf` if it is a new layer).
:::

::: answer [[ex-layout-layers]]: Spot the upward import
It breaks the layering rule: requirements are a lower layer than the physical architecture, and lower layers never
import higher ones. It is a smell because a requirement should not depend on a design; that is how the spider web
starts. The file is generated from the prime's export, so do not hand-edit it: the complexity job reports upward
imports in generated files instead of failing on them, and the fix goes to the prime (or to the converter's layout, if
the import is the converter's own) as a discrepancy report ([[no-spider-web]]).
:::

::: answer [[ex-tools-rule]]: Apply the rule
A model answer:

|| Problem today | GitLab tool | The problem it creates if turned on too early ||
| nobody knows which version of the ICD is current | protected tags and releases | ceremony around every small change before anyone has felt the version problem |
| reviews happen in e-mail threads nobody can find | merge requests with approvals | approvals queue up behind one reviewer if code owners are drawn too narrowly |
| status slides take a day each week | the model site on Pages, analytics | a dashboard nobody asked for, numbers nobody trusts yet |

The rule in [[tools]]: a tool appears when the team has felt the pain it removes.
:::

::: answer [[ex-tools-widget]]: Read a widget
The JUnit report (`lint.xml`) has one `testcase` per check with a `failure` element carrying the message; GitLab
shows that message in the merge request's test widget as one failed test. The Code Quality report (`lint-cq.json`)
has one finding with `description`, `location.path` and `location.lines.begin`; GitLab shows it in the code quality
widget and on the diff line. The line to look for in both: the `unresolved type` message with its file and line.
:::

::: answer [[ex-tools-token]]: Choose the token
- (a) A personal access token with `read_api`, owned by the person who runs the script, with an expiry date.
- (b) No stored token at all: the pipeline's `CI_JOB_TOKEN`, which exists only while the job runs.
- (c) A project access token with `read_api` only, stored as a masked, protected CI/CD variable, with an owner and an
  expiry in the token inventory ([[admin]]).
:::

::: answer [[ex-tools-off]]: Argue for one left-off tool
For merge trains: "Twice this month two merge requests were green alone and red together on `develop`, and `develop`
was red for half a day each time. A merge train tests each merge request on top of the ones queued before it, so
`develop` stays green." The evidence needed: the count of red `develop` pipelines caused by two green merge requests,
from analytics ([[analytics]]). Without that evidence, Tom is right to leave it off.
:::

::: answer [[ex-ai-request]]: Write the approval request
A complete request names one runtime (Ollama, a specific version), one model family and size from an allowed
developer, where it runs (three laptops, or one approved server), the data rule ("only information our marking rules
allow on that machine"), and that the model's origin and license were checked. The office that approves model origin
is usually the one that approves software intake, with the ISSM concurring; find out by asking both, in writing.
:::

::: answer [[ex-ai-bakeoff]]: Run a three-task bake-off
The answer is your scoresheet. A good one has, per task: the prompt written in advance, the number of tries, whether
the result passed the gates (grammar, lint, the recipe for text), and the minutes to a mergeable result, with and
without the model. A typical finding: the model helps on the helper script and the discrepancy report text, and
loses on SysML v2 text, where its first draft fails the gates.
:::

::: answer [[ex-ai-gate]]: Make the gates catch a hallucination
The grammar check passes: invented names such as `ISQ::SolarPowerValue` are perfectly good grammar. Lint catches
them, as `unresolved type` errors on the lines that use them, because lint resolves names against the model and the
library and the grammar check does not. With the model's own `Power` and `Energy` types both gates pass.
[[local-ai-energy]] shows the real runs.
:::

::: answer [[ex-ai-vim]]: The scratch-buffer loop in Vim
With `cat` standing in for the model, the loop is: select the TODO line and the XMI fragment, `:'<,'>w !cat > /tmp/prompt`,
`:new`, `:r !cat /tmp/prompt`, `:w answer.sysml`, `\mx`. Most people time it at a minute or two once the keys are
familiar; the time is in reading the answer, not in the keys.
:::

::: answer [[ex-ai-dr]]: Check a draft for added facts
Typical added facts: a date the defect was found, a test that "failed", a section number in a document the prompt
never named, and a severity. The one that would embarrass you in front of the prime is any invented reference, such as
"per SRS paragraph 3.2.1": the prime will look it up. Delete every added fact or verify it before sending.
:::

::: answer [[ex-pipeline-events]]: Which jobs, which event
Running `gitlab.pl ci --list` for each event reproduces the table in [[pipeline]]. The rule that usually surprises
people: a job with no `rules:` does not join merge request pipelines at all, on GitLab and locally. Every check job in
the template has an explicit merge-request rule for that reason.
:::

::: answer [[ex-pipeline-ratchet]]: Turn the ratchet
After fixing one violation the `outline` job passes and says "fewer violations than allowed: lower .ci/outline-max to N
in this MR". Lower the number in `.ci/outline-max` in the same merge request and run it again: it passes with the new
allowance, and nobody can add a violation back without the job failing.
:::

::: answer [[ex-pipeline-ratchet-yours]]: Find your ratchet
Example: "every requirement has a verification method". Counted: requirements with an empty method in the DOORS
export. The allowed number lives in a one-line file in the repository, like `.ci/outline-max`. Anyone may lower it in
a merge request that fixes some; only the lead may raise it, and only with a recorded reason, enforced by a CODEOWNERS
line for that file.
:::

::: answer [[ex-pipeline-stale]]: Stale documents
The `docs` job fails: it regenerates the documents and finds the committed ones differ ("docs are stale"). Fix it by
running `model.pl docs` and committing the result. The team commits generated files so a reviewer sees, in the merge
request diff, what the change does to the documents people read, and so a baseline's checksum covers the documents
as well as the model.
:::

::: answer [[ex-pipeline-weaken]]: Review a pipeline change
"Request changes. `allow_failure` on lint means a model with unresolved names can merge, and nobody will notice until
the next release. If lint is noisy, that is information: which messages are noise? Let's fix those (or ratchet the
count, as we do for the outline) and keep lint blocking." The alternative: a ratchet on the lint warning count, with
errors still blocking.
:::

::: answer [[ex-cicd-break]]: Break it and watch it fail
The `lint` job fails and its log names the file and line with `unresolved type 'NAME'`. In Vim, `:make lint` fills
the quickfix list from the same message, `:cnext` jumps to the line, the fix is the correct type name, and the job
passes on the next run.
:::

::: answer [[ex-cicd-semicolon]]: One line up
The error names the line *after* the one missing the semicolon (the workbook answer above shows it: `m1.sysml:3:5`,
when the semicolon was missing on line 2). In one sentence: "The checker only notices a statement did not end when the
next one starts, so it points at the start of the next statement."
:::

::: answer [[ex-cicd-add]]: Add a job
```yaml
todo:
  stage: check
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH'
  script:
    - perl -e 'my $n = 0; for my $f (@ARGV) { open my $h, "<", $f or next; $n += grep { m{// TODO} } <$h> } print "todo_lines $n\n"' model/*/*.sysml
```

To show the count on the merge request page, write it to a metrics file and declare it as `artifacts: reports:
metrics:`; GitLab then shows it in the metrics widget, with the change since the target branch ([[tools]]).
:::

::: answer [[ex-cicd-allow]]: Allowed to fail
The pipeline becomes "passed with warnings" and the merge request can merge. That is a bad idea for lint because lint
errors are real defects (unresolved names), and a warning icon is easy to ignore; a broken model would reach
`develop`. The team first made `trace` allowed to fail because its gaps were the prime's, inherited and outside the
team's control, so failing on them would block every merge. The ratchet replaced it because it separates what the team
inherited (reported) from what a change adds (blocked).
:::

::: answer [[ex-cicd-manager]]: The manager's question
On a merge request: "The automated checks found a problem in a proposed change before it was accepted. Nothing in the
model is affected. The author is fixing it today."

On the integration branch: "The accepted model currently fails a check, so every new change is on hold. We know the
cause and expect it green by this afternoon. The last good baseline is unaffected."
:::

::: answer [[ex-runners-pending]]: Make a job pend
GitLab shows the job as *pending* with "This job is stuck because you don't have any active runners online or
available with any of these tags assigned to them: does-not-exist". Locally, `gitlab.pl ci --list` still lists the job
(the local runner ignores tags), which is itself the lesson: tags are a property of the server's runners. Fix it by
removing the tag, or by registering (or editing) a runner with that tag.
:::

::: answer [[ex-runners-pwsh]]: Translate a line
In PowerShell: `if (-not $env:KIT) { Write-Output "KIT is not set"; exit 1 }`. The team chose `perl ci/job.pl NAME`
because a Perl command line is the same in PowerShell, cmd, Git Bash and Docker, so one pipeline file works on every
runner, and the logic lives in one script that has its own tests instead of two shell dialects to keep in step.
:::

::: answer [[ex-runners-isso]]: Write the runner's security description
One page, in this order: the machine (a dedicated Windows VM, its name and network segment), the account (a service
account with no interactive login and no administrator rights), what it can reach (the GitLab server only, outbound),
the credentials on it (the runner token, stored by the runner service; no personal tokens), what runs on it (the
model project's pipeline jobs only, through a project runner with tags), who maintains it (Tom, patched monthly with
the runner version kept in step with GitLab's), and how it is cleaned (build folders removed after each job).
[[runners-account]] is the model.
:::

::: answer [[ex-review-find]]: Review a change
The pipeline catches the removed import: lint fails with unresolved names (`ObservationIF`, `HealthIF`) on the port
lines. Only a reviewer catches the `doc` change, because it is valid text with a different meaning; the generated
documents in the diff make it visible, and the review checklist asks whether each changed `doc` still says what the
element is ([[reviewing]]).
:::

::: answer [[ex-review-rewrite]]: Rewrite a finding
- (a) "This satisfies TW-SYS-003 with the archive, but the requirement is about ingest. Should it be `IngestService`?"
- (b) "TW-SYS-013 has no verification case after this change; the trace job will flag it. Can you add the case here,

- (c) "The package has two cycles and a duplicated block (see the pkg view). Could we take the cycle in this merge

Each says what, where, why it matters, and asks for a specific action.

::: answer [[ex-journal-split]]: Where does it go?
- (a) GitLab: a task, under one week, closed by a merge request.
- (b) The journal *and* GitLab: a story in the journal (points, sprint), its tasks in GitLab.
- (c) The journal: an epic, as the `e:` tag on its stories.
- (d) Neither: hours stay in the team's own time records (GitLab's `/spend` if the team uses it); the journal never

The longest stage is *issue created to first commit*, about four days at the median. That is not a problem: the

commit (opening the merge request, review, merge) take hours, and they are the ones that measure the flow.

::: answer [[analytics--ex-2]]: Translate a DORA measure
- **Deployment frequency:** "How often the published model is updated: the model site rebuilt, or a baseline
  released."
- **Lead time for changes:** "How long a change takes from the first edit to being part of the accepted model."
- **Change failure rate:** "How often an accepted change had to be corrected or undone."
- **Time to restore:** "When the accepted model fails its checks, how long until it passes again."

Leave out deployment frequency, because it mostly counts the nightly schedule, and change failure rate, because at
zero it says nothing yet. Keep lead time and time to restore: they answer "how fast" and "how safe".
:::

::: answer [[analytics--ex-3]]: Find the trap
The final version is right. The draft's line, "6.7% verified (VCRM) (down 63.3 from 70)", compares two different
measures: the VCRM's *verdict recorded* against the trace's *case exists*. Read out, it would have told the program
manager that verification collapsed in sprint 6, when nothing got worse: a stricter measure appeared. The review
record keeps verify coverage at 70% and reports the VCRM separately.
:::

::: answer [[proving--ex-2]]: Explain a difference
Two folds from drop 1's map:

- **The multiplicity of a part** (a `LiteralInteger` and a `LiteralUnlimitedNatural`, two v1 elements) folds into
  the `[4]` on the usage: v2 writes the bounds inline, so nothing is lost; there are just fewer elements.
- **A generalization** folds into the `:>` of the definition, for example `attribute def Power :> PowerValue`. v1
  stores the inheritance as its own element; v2 writes it as part of the declaration.

The test of a fold is the same each time: can you point at the v2 text that carries the information? If so, it is
not a loss.
:::

::: answer [[ex-memo-mfr]]: Record a decision
The memo for record is signed, dated and addressed to a reader outside the team: it is what an auditor or the
contracting officer files. The ADR lives beside the model, is versioned with it, and is read by the next engineer. The
memo carries authority; the ADR carries context and is easy to supersede. Keep both for decisions that bind the
program (the branching model), and only the ADR for decisions that bind the team.
:::

::: answer [[ex-memo-vim]]: Build from Vim
Yes: the `.txt` diff shows the changed paragraph as a few changed lines, with the rest unchanged, because the build
wraps text the same way every time. The PDF diff is binary and unreadable. That is why the team commits the `.txt`
beside the PDF.
:::

From the pipeline: TODO lines, trace numbers, pipelines passing. From GitLab: stories done, merge requests, review

baselines. A memo with more of the third kind than the first two needs more evidence before it goes out.

::: answer [[ex-dil-own-day]]: Write your own two-column day
Rows that change most: waiting for a review (hours instead of weeks), finding the current version (the branch, not

::: answer [[ex-documents-grade]]: Grade a document both ways
The pipeline is right about what it can check (references resolve, nothing is missing, the text matches DOORS); the
hand grade is right about what it cannot (whether the design is good, whether the reader understands it). Where they
disagree on something the pipeline checks, trust the pipeline and find out why the hand grade missed it.
:::

::: answer [[ex-lead-first-win]]: Choose the first win

requirements file). The trace is the one for sprint 1: it needs only the drop and the converter, and the skeptic who
has answered it by hand for years is the right person to run it.

::: answer [[ex-admin-roles]]: Assign the roles
- **Model lead: Maintainer.** Owns protections and baselines; the only one who can change who approves what.
- **Two modelers: Developer.** They push branches and open merge requests, but cannot merge into protected branches

- **CM engineer: Maintainer**, for tags and releases, with the protections still requiring another person's approval

::: answer [[ex-admin-restore]]: Plan a restore test
The checklist: import the export into a scratch group; check the repository, branches and tags; issues, merge
requests and comments; labels and milestones; the wiki; then re-create what an export leaves out on purpose. An

group-level settings, and no container or package registry contents. Those items fail on any server, by design;

::: answer [[ex-admin-tiers]]: Make the tier case
