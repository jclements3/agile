== A twelve-week study plan per role {#study-plan}

::: bridge
You know: a training plan with courses and dates.

Here it is called: a twelve-week study plan per role.

What is new: the learning time is budgeted on the team's board, not taken from evenings.
:::

This book is long because it is a reference as well as a story. Nobody should read it front to back before doing
anything. This appendix is the order the Tidewater team read it in, week by week, with the practice lessons and
the exercises that go with each week, and the learning time the plan budgeted for it. Use it as a starting point
for your own team: the roles matter more than the names.

The three roles:

- **The lead (Jim).** Owns the model, the backlog's tomes and epics, the change board and the conversation with
  management. Reads for decisions and for the case to make; types fewer commands than the others.
- **The modeler (Bob).** Does most of the model work: closing TODO lines, writing behavior by hand, reviewing.
  Reads for SysML v2 and Vim, and practises the most.
- **The pipeline owner (Tom).** A systems engineer who took on the GitLab project, the runner and the pipeline.
  Reads for setup, CI/CD and administration.

=== Where the hours come from {#study-plan-hours}

Learning time is planned work, not evenings and weekends ([[lead]], [[stories]]). On Tidewater it is a
`work::learning` story every sprint, with a task per person, sized like any other task (one point is one ideal
day, about eight hours). The plan file is the source; print each person's learning tasks from it:

```sh run sandbox=kit expect="Practice lessons 10-11"
perl -e 'require "./sim/tidewater-plan.pl";
  for my $s (grep { $_->{n} <= 6 } @{ tw_plan() }) {
    for my $st (grep { $_->{work} eq "learning" } @{ $s->{stories} }) {
      printf "S%d %-4s %4.1f h  %s\n", $s->{n}, $_->{who}, 8 * $_->{p}, $_->{t} for @{ $st->{tasks} } } }'
```

The learning share falls as competence rises: see the sprint-by-sprint split in [[bluf]]. Reading this book's
chapters and doing the practice lessons is what those hours buy. The practice lessons are offline, run on the
laptop against the kit's GitLab stand-in, and take about forty-five minutes each (`perl agile.pl practice N`;
`perl agile.pl practice check N` says what to do next).

=== Week zero: everyone {#study-plan-week0}

Before sprint 1, all three read the same short list, so the team starts with one vocabulary. The list climbs the
ladder in the preface ([[preface-ladder]]): what you know first, then what is new.

- [[bluf]] and [[preface]]: what the twelve weeks are, and what they cost.
- [[directive]]: what management asked for, and the scorecard that will measure it.
- [[vee]]: the systems-engineering Vee you already know, and where each piece of it lives in GitLab.
- [[devsecops]]: every DevSecOps term in systems-engineering words.
- [[survival]], up to the end of the laptop checks; then `perl "$KIT/tools/gitlab/kickoff.pl" doctor` on each
  laptop.

The lead also reads [[operating-model]] and [[playbook]], because week zero is when the scorecard, the exchange
agreement with the prime and the first meeting with the security officer happen.

=== Check yourself {#study-plan-check}

At the end of each sprint, each person should be able to say yes to that sprint's "You can now..." list in the
sprint chapter ([[sprint-1]] to [[sprint-6]]). If the answer is no for two sprints running, the learning budget is
too small or the backlog too full; that is a conversation for the retrospective, not a private worry.

::: exercise Build your own plan
Copy the three tables into your team's wiki, rename the roles to your people, and move rows to match your program
(a team with no supplier drops can skip the drop-loop rows until it has one). Then print your own plan's learning
tasks the way the block above does, and check that the hours in the tables match what the backlog actually
reserves.
:::
