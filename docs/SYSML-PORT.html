Porting SysML v1 and DOORS to SysML v2 text

One-sheet quick reference (print both sides): SYSML-PORT-QRG.pdf.

Two tools in this kit move a legacy model into SysML v2 textual notation under Git:

  • bin/xmi2sysml.pl reads a SysML v1 XMI export from Cameo Systems Modeler or MagicDraw. It writes one .sysml file per top-level package.
  • bin/reqif2sysml.pl reads a DOORS module as ReqIF (.reqif or .reqifz) or as CSV. It writes the requirements with their doorsId, plus the trace report behind status metrics C, F, G and I.

Both are core Perl 5. They run on the Perl that ships with Git for Windows, so the work laptop needs nothing beyond Git for Windows, Vim and Perl. They never touch the network, and they write only where you point --out. The output feeds the A to Z status metrics (STATUS-METRICS.html, collected by bin/status-metrics.pl).

The converters give you a starting point, not a finished model. Every element they cannot map becomes a // TODO line with its xmi:id, and the report lists each one. Nothing is dropped silently, but a person still has to review each segment before it is committed.

The daily loop

  1. Export the current model from Cameo and the requirements from DOORS (sections below). Put them outside the model repo, for example in exports/, with the date in the name.
  2. Read the mapping report before you convert anything: 
    perl bin/xmi2sysml.pl --report exports/2026-10-05-legacy.xmi
perl bin/reqif2sysml.pl --report exports/2026-10-05-system.reqif
    Check three things in the XMI report: the unmapped list, stereotypes not converted, and type references not resolved. Real exports vary with the tool version, the profiles in use and the export settings. If something you care about shows up there, fix the export first.
  3. Convert into a branch of the model repo: 
    cd model-repo
git switch -c port/structure
perl ../agile/bin/xmi2sysml.pl --out model --check ../exports/2026-10-05-legacy.xmi
perl ../agile/bin/reqif2sysml.pl --out model --layout "_reqs/{pkg}.sysml" --check ../exports/2026-10-05-system.reqif
  4. Review the result in Git. Run git status and git diff --stat, then read the diff segment by segment (git diff model/structure, or git difftool with Vim as the diff tool).
  5. Work the TODO lines in Vim. List them all in the quickfix window: 
    :vimgrep /TODO/ model/**/*.sysml
:copen
    Move with :cnext and :cprev. Each TODO line gives the v1 type and the xmi:id, so you can find the element in Cameo.
  6. Commit one segment at a time. Stage it with git add -p model/structure, commit it with a message such as port: structure from legacy.xmi 2026-10-05, and merge through the normal gate (lint, then review).
  7. Run the metrics: perl bin/status-metrics.pl collect ... (see Feeding the metrics).

Regenerating without losing hand edits

The output is deterministic: the same export gives the same bytes, in the model's own order. Re-running after a new export therefore changes only what changed in Cameo. A re-run also overwrites your hand edits in those files. Two rules keep that safe:

  • Once a segment is ported and hand-fixed, stop regenerating it. Convert into a scratch directory (--out ../scratch) and copy over only the segments still being ported.
  • Use --report to count what remains. Its "ported vs remaining" line uses the same type filter as metric A.

Exporting from Cameo / MagicDraw

  • Cameo Systems Modeler 19.0 and later (2021x, 2022x, 2024x): File > Export To > Eclipse UML2 (v5.x) XMI File. Older MagicDraw: File > Export To > UML 2.1 XMI File. Menu names move between versions; pick the plain UML/XMI export, not a "MagicDraw native" or "mdzip" format.
  • Export the whole project, or the packages that form the segments. Each top-level package becomes one file and one segment folder (model/<segment>/<Package>.sysml). Change that with --layout, for example --layout "{pkg}.sysml".
  • Settings that matter:
    • Stereotype applications must be included. Without them, Blocks are plain Classes and requirements have no id or text. They appear at the end of the file as <sysml:Block base_Class="..."/>. The prefix may also be SysML:, Blocks: or MD_Customization_for_Requirements...:; the tool matches on the local name, so any of these works.
    • Used projects and libraries. Types from a used project, such as SI value types, export as href references to another file. UML and SysML primitives (Real, Integer, Boolean, String) map to ScalarValues::*. Anything else is listed under "type references not resolved"; export the library with the model, or fix those types by hand.
    • Diagrams export as xmi:Extension blocks. They are counted and skipped.
  • The Eclipse export may write several files: the model plus profile files. Give the converter the model file, the one with <uml:Model> in it.

Exporting from DOORS

  • ReqIF (preferred). DOORS 9: File > Export > ReqIF, using a ReqIF definition that includes the module and its link modules. DOORS Next: Export > ReqIF from the module or a ReqIF definition. Both may write a .reqifz (a zip), which the tool reads directly. If a Perl ever lacks IO::Uncompress::Unzip, unzip the file and give it the .reqif inside. Both Git for Windows' Perl and Linux Perl ship it.
  • Include these attributes: Object Heading and Object Text (ReqIF.ChapterName and ReqIF.Text), the absolute number (ReqIF.ForeignID), and your verification method attribute. DOORS exports the absolute number without the module prefix, so add the prefix back with --id-prefix SYS-. If your id lives in another attribute, name it with --id-attr "Object Identifier". Any attribute whose name contains "verif" is taken as the verification method; override that with --vm-attr.
  • CSV is the fallback. Export a view with the columns Object Identifier, Object Level, Object Heading, Object Text and Verification Method. Columns with those names are found automatically. Name other columns with --col: 
    perl bin/reqif2sysml.pl --csv --col id="ID" --col text="Requirement" --col level="Level" --col vm="V Method" --out model module.csv
    Comma, semicolon or tab separators are detected. Quoted fields may span lines, as DOORS writes multi-line text.

An object with a heading and no text becomes a nested package (a section). An object with text becomes a requirement. An object with neither becomes a TODO line and is counted. Objects that appear in no module hierarchy go to a separate ... unplaced package, so you can see them.

The commands

CommandWhat it does
perl bin/xmi2sysml.pl --report FILE.xmiMapping summary: elements in by xmi:type (mapped / folded / TODO), ported vs remaining for metric A, stereotypes, SysML v2 elements out, the unmapped list.
perl bin/xmi2sysml.pl --out DIR FILE.xmiWrites the files (default layout {seg}/{pkg}.sysml) and prints a one-line summary to stderr.
--stdoutWrites every file to stdout, each after a // file: path line. Useful for a quick look in Vim: perl bin/xmi2sysml.pl --stdout x.xmi | vim -.
--req-style usage|defusage (the default) writes one-line requirement NAME { ... } usages, the form bin/status-metrics.pl counts and the Halberd example uses. def writes requirement def blocks.
--name PKGThe package for elements that sit outside any package (default: the model's name, else the file name).
--checkAlso runs tools/sysml/sysml.pl check (the SysML v2 grammar checker) over the files written, when it is in the kit.
perl bin/reqif2sysml.pl --report FILE.reqifRequirements, verification methods, headings, orphan headings, empty objects and links.
perl bin/reqif2sysml.pl --report --model DIR FILE.reqifAdds the trace against existing SysML v2 text: C linked, F orphans, G unverified, I completeness, with the ids of each.
--attr NAME (repeatable)Copies a DOORS attribute onto each requirement, for example --attr Priority.

Both tools exit 0 when all is well, 1 when the structural self-check (or --check) finds a problem, and 2 on bad usage or an unreadable file. A malformed XML file stops the tool with file:line: message.

Requirements are named from their id (CD-101 becomes CD_101) in both tools. A requirement ported from Cameo and the same requirement read from DOORS therefore get the same name, and satisfy/verify lines written by one tool resolve against definitions written by the other. Other names keep their v1 spelling, quoted ('serial number') when they are not plain identifiers or when they are SysML v2 reserved words.

Feeding the metrics

  • A, % under configuration control. status-metrics.pl init --xmi legacy.xmi freezes the denominator with the filter uml:(Class|Port|Property|Connector|Activity). The xmi2sysml report's "ported vs remaining" line counts the same set, so the two agree on what "all of it" means.
  • C, requirements linked. The total is the <SPEC-OBJECT> count of the ReqIF export, the first line of the reqif2sysml report. "Linked" is a doorsId found in model/. reqif2sysml.pl --report --model model export.reqif gives both, plus the ids that are missing.
  • F, G and I. These are the orphan (no satisfy), unverified (no verify) and complete counts from the same --model report, with the ids to send to the owners.
  • Which requirement style to commit. bin/status-metrics.pl counts requirements written as one-line usages (requirement r1 { attribute doorsId = "..."; }), which is what both tools write by default. Use --req-style def only if you report from the Appendix A grep fallbacks, which count requirement def. The --model trace reads both.

Checked against the status-metrics simulation (sim/status-metrics-sim.pl): on its exports and final model, reqif2sysml.pl --report --model gives C = 1450 of 1450, F = 3 and G = 4, the same values the collector records.

Checking the output

  • Every run does a structural self-check. It looks for balanced braces, terminated comments and strings, and checks that every type, specialization, satisfy/verify target, connect end and import names something declared in the output or in the standard library (ScalarValues, ISQ, SI, RequirementDerivation and so on). The check is by name, not by scope.
  • --check also runs the kit's SysML v2 grammar checker (tools/sysml/sysml.pl check). The test suites run it over every fixture output in both requirement styles.
  • Neither is a full semantic validator. When you can, open a segment in a SysML v2 tool (the Pilot implementation or a vendor tool) before you baseline it.

Limits

  • Diagrams and layout are not converted. SysML v2 views are defined separately; draw them again from the text.
  • Behaviour is a skeleton. Activities keep their parameters, call actions and control flows. Decision, merge, fork and join nodes, object flows and pins become TODO lines. State machines, interactions (sequence diagrams) and operations become TODO lines.
  • Constraints and parametrics. OCL and opaque-expression constraints become TODO lines with the expression text. Constraint blocks become an empty constraint def with a TODO line. Parametric bindings other than plain binding connectors are not converted.
  • Profiles. Only the SysML 1.x stereotypes listed in the mapping table are understood. Other stereotypes (company profiles, UAF, MARTE and so on) appear as a TODO line on the element they were applied to, and the report counts them.
  • Units. A ValueType's unit is kept as a comment. Specialize the matching ISQ quantity by hand.
  • Containment. Nested requirements are written after their parent, not inside it. Their derivation links are kept.
  • Satisfy and verify targets with --req-style def name a definition. That parses, but strict SysML v2 semantics want a requirement usage there. The default, usage, avoids the issue.
  • DOORS. OLE objects and images in requirement text become [image]. Tables are flattened to a | b rows. Links whose ends are not both requirements, such as a link to a heading, become TODO lines. Link types are classified by name: derive/refine, satisfy, verify/test; anything else is a trace.
  • Size. The XML is read in 1 MB chunks, but the model is held in memory. A 22 MB XMI with 160,000 elements converts in about 20 seconds and 700 MB on WSL Perl, and in under a minute on Git for Windows' Perl.
