::: bridge

What is new: the baseline rebuilds identically, on demand, with its evidence attached.

::: survival
What you have: a model whose structure is almost closed, a trace that defends itself ([[sprint-5]]), a recipe-graded
set of requirements, and a team that has rehearsed a release in a sandbox.

What you need from this chapter: how a three-person team finished its first twelve weeks with something management
could hold -- a tagged, reproducible baseline, a generated table of what crosses each interface, a verification
matrix -- and how it handled the sprint's real events: a failed nightly pipeline, a token committed by mistake, a
review comment that blocked a merge, a story that could not finish, and a number that almost told management the
wrong thing.

=== The question this sprint answered {#sprint-6-question}

Sprint 6 ended with the twelve-week briefing to program management. The question behind every story in it was
the one a program manager asks at any milestone: *can you hand me something I can rely on?* In the document era the
answer was a set of documents with signatures. For this team it had to be three things:

1. **A baseline**: a tagged, reproducible version of the model, approved by the CCB, that can be rebuilt byte for
   byte and named in a contract letter.
2. **An answer to "what crosses each interface?"** -- the question every interface control working group asks --
   generated from the model, not typed into a spreadsheet.
3. **An honest answer to "which requirements are verified, and how?"**, in the form a test organization uses: a
   verification cross-reference matrix (VCRM).

The pulse at the sprint 5 retrospective was {{value: docs/tidewater/sprints/05/morale.json mean}}. Nobody on the team
would have predicted that number in week one. The risk now was the opposite of discouragement: a team pleased with
itself, with a short sprint, holidays, and an audience waiting.

=== Week 1: the quiet days and the busy one {#sprint-6-week-1}

==== Monday to Wednesday: Operations closed, verdicts signed {#sprint-6-mon}

Jim spent Monday morning on the last learning task of the twelve weeks: the memo and briefing chapters of this book
([[memos]], [[briefing]]), because the briefing was Jim's to give in ten days.

Tom's !21 closed the level-tag TODO lines in the Operations package. Its first pipeline was green. By sprint 6 a green
first pipeline on a structure change is unremarkable, which is the point: the team had stopped noticing the checks
on routine work, the way an engineer stops noticing a calculator.

On Wednesday Jim opened !22, *Inspection verdicts, signed*. Some Tidewater requirements are verified by inspection --
someone looks at the thing and signs that it complies -- and the results schema the team adopted in week zero
(ADR 0003) puts those verdicts in a file in the repository, with the name of the person who signed. A signed
verdict is a configuration item like any other: it goes through a merge request, it has an author and an approver,
and it is in the baseline. Jim's merge request entered the verdicts Jim could sign from the drop-1 evidence; the
VCRM job, later in the sprint, reads them. Here is the file, in Tom's clone of `develop`:

```sh run sandbox=tidewater cwd=work/tom expect="TW-SYS-010,DemonstratePublication,passed"
git checkout -q develop
cat verification/results-gov.csv
```

Each row is one verdict: the requirement, the verification case, the verdict, the commit of the model it was judged
against, how it was judged, when, and who signed. Read the `commit` column twice. It is what turns a signature into
evidence: years from now, anyone can check out exactly the model Jim inspected. In the document era an inspection
record named a document revision, and the revision named nothing that could be rebuilt.

The file is named `results-gov.csv` because it holds the government's own verdicts. When the prime's test results
arrive with later drops ([[verification]]), they land in a sibling file in the same schema, and the VCRM reads both.
One schema for every source of verdicts is ADR 0003's whole point.

==== Friday 18 December: the table, and a token {#sprint-6-friday}

Tom's !25 generated the data exchange table: for each interface, the flows, their direction, their type, their
fields, and the notes from the model's doc text. Its first pipeline failed -- not on the model, on the `secrets`
job:

```sh run sandbox=tidewater cwd=. expect="possible secret committed"
tail -3 gitlab/pipelines/tidewater-model/95/secrets.log
```

Tom had pasted a personal access token into a helper script to test it, and committed the script. The pipeline
stopped it before it reached `develop`. What Tom did next is the whole procedure for a leaked credential, and its
order matters:

{{include-md: docs/tidewater/sprints/06/samples/mr-25.md}}

Revoke first, because the token may already have been copied from the branch. Replace it with a narrower one
stored as a masked, protected CI/CD variable ([[tools]]). Then rewrite the branch so the token is in no commit.
Deleting the line in a new commit is not enough: the old commit still holds it ([[rescue]]).

The table itself is a generated document in `docs/`, committed with the model and rebuilt by the pipeline. Here it
is in the sandbox, as of the end of the sprint:

```sh run sandbox=tidewater cwd=work/tom expect="HealthIF \| health"
git checkout -q develop
head -12 docs/data-exchange.md
```

Look at the `HealthIF` row: the assumption from Thursday's review is in the table, labeled as an assumption to
confirm with the prime. In the document era, that assumption would have lived in someone's head or in a comment on
a PDF. Here it is part of the deliverable, and it will stay visible until the prime answers.

==== Monday 21 December: the VCRM job {#sprint-6-vcrm}

Tom's !26 added the `vcrm` job and the baseline jobs to the pipeline. The VCRM reads every requirement, its
verification method, the verification cases that claim to verify it, and the verdicts in the results files, and
writes `vcrm.html` and `vcrm.csv`. In the sandbox:

```sh run sandbox=tidewater cwd=work/tom expect="VCRM: 30 requirements, 2 verified"
perl ci/job.pl vcrm | tail -1
```

Read that line carefully, because the team almost did not. Hardly any requirement is *verified*, most are *not
run*, and some have no case at all. That sounds like a disaster. It is not: it says something different from the
trace.

==== The number that almost misled management {#sprint-6-number}

The trace measure the team had reported for twelve weeks -- *verify coverage* -- asks: **does every requirement have
a verification case that claims to verify it?** For Tidewater that was
{{value: docs/tidewater/sprints/06/scorecard.json 5_trace.C}} linked requirements with
{{value: docs/tidewater/sprints/06/scorecard.json 5_trace.G}} unverified, the same as at the drop-1 import, because
the gaps are the prime's.

The VCRM asks a different question: **has the verification actually been done, with a recorded verdict?** In a
program that has not reached test, almost nothing has been. The verified ones are the inspection verdicts Jim signed in
!22.

When Jim drafted the review script with `talk.pl review`, the tool did what tools do: it found a newer
verification measure and used it.

{{include: docs/tidewater/sprints/06/review-script.md | lines 1-12}}

*Verify coverage: 6.7% verified (VCRM) (down 63.3 from 70).* Read naively, that line tells the program manager
that verification collapsed in the last sprint. It did not collapse; a second, stricter measure appeared. The
draft was corrected before the meeting -- the review record uses the measure the program had been seeing all along:

{{include: docs/tidewater/sprints/06/review.txt}}

This is the most important lesson about drafting tools in this book ([[talking]]): **read every number before you
say it, and never compare two measures as if they were one.** The fix is not a better tool; it is a person who
knows what each number means.

The kit's `talk.pl` was changed after this sprint, because of exactly this near miss: it now keeps the two measures
apart and labels the second one as a different measure. Run it on the same sprint in the sandbox and compare its
lines with the draft above:

```sh run sandbox=tidewater cwd=. expect="Requirements with a verification case"
perl "$KIT/tools/gitlab/talk.pl" --local gitlab --project tidewater/model review --sprint 6 | sed -n 7,11p
```

That is how a tool should improve: a person caught a misleading number, and the tool was changed so the next person
does not have to.

::: sidebar The decision: an interim baseline, now
The plan called for the first real baseline -- baseline-1, the port's acceptance -- in sprint 20. Jim proposed an
interim *baseline-0* for the twelve-week review, and the reasoning is worth copying.

**Against:** the model was not finished. BuoyModes was still a TODO line, the trace still had the prime's gaps, the
package view still showed a cycle. A baseline of an unfinished model, the argument went, would look like a claim
that it was finished.

**For:** a baseline is not a claim of completeness; it is a claim of *identity*. Baseline-0 says: *this* is the
model on 24 December, these are its known gaps (the release notes and the VCRM list them), and anyone can rebuild it
exactly. That is precisely what a program needs before a review -- a fixed point to discuss -- and it is what the
document era could never provide: the "baseline" was a set of PDFs whose source nobody could reproduce. The other
reason was practice. The release path has steps that only run on a tag: the baseline audit, the toolchain inventory,
the release. Running them first in December, with nothing riding on them, was cheaper than running them first for
baseline-1.

The CCB agreed on the second argument. The deputy program manager's concurrence comment on !27 says what the board
reviewed: the change list and the pipeline.
:::

=== Thursday 24 December: baseline-0 {#sprint-6-baseline}

The interim baseline is the first time the team's work went out under the CCB's name. Tom had rehearsed the path in
sprint 5 in a sandbox project. The real path, on the real project:

1. A `release/baseline-0` branch from `develop`, with the CHANGELOG section and regenerated docs.
2. A merge request into `main`, !27, with the release template's checklist and one line the CCB writes itself.
3. The deputy program manager's concurrence, recorded as a comment on the merge request -- the CCB's approval, in
   the same place as the engineering approvals:

{{include-md: docs/tidewater/sprints/06/samples/mr-27.md}}

4. The merge into `main`, the annotated tag `baseline-0` whose message carries the sha256 of the generated docs, and
   the back-merge into `develop`.
5. The tag pipeline: it regenerates the docs from the tagged model, checks the hash against the tag message, writes
   the toolchain inventory, rebuilds the VCRM and publishes the release.

The tag in the sandbox:

```sh run sandbox=tidewater cwd=work/tom expect="sha256=[0-9a-f]+ \(docs/ at [0-9a-f]+\)"
git tag -n4 -l 'baseline-*'
```

And the end of the tag pipeline's `baseline` job:

{{include: docs/tidewater/sprints/06/pipelines/tag-baseline-0-108.log | lines 489-498}}

*baseline-0 rebuilds identically.* That one line is a physical configuration audit, done by a machine in a minute,
on every baseline, forever. The toolchain lines below it say which kit, Perl and git produced the baseline, so
the audit can be repeated years from now with the same tools.

=== Reading the sprint's own numbers {#sprint-6-analytics}

The sprint-end analytics ([[analytics]]) tell the story of the busy Thursday in four lines:

{{include: docs/tidewater/sprints/06/analytics.txt | lines 12-22}}

**Time to restore** is no longer empty, as it was in sprint 5: `develop` was red once, from the 02:00 nightly failure
to the green rerun. That is the disk-full incident, and the number is honest about it -- the nightly failed at 02:00
and nobody looked until the stand-up. A team that wants that number smaller has two choices: a runner that cannot
fill its disk (the fix Tom made), or a notification that wakes someone up. For a model repository, the first is the
right answer; nobody's model needs to be green at 03:00.

**Pipeline success rate** dropped from sprint 5. Look at the job failures line before worrying: the `secrets`
failures are Tom's token (the merge request pipeline, a rerun, and the push to the branch), and the other single
failures are the nightly run, where every job failed for the same disk-full reason. Not one failure was a model
error that reached `develop`. A falling success rate with that explanation is a sign the checks are working; the same
number without the explanation would worry a manager for nothing. Always bring the explanation.

**Change failure rate** is still zero. Seven merges to `develop`, none reverted or fixed forward.

=== What went wrong, and what the team did about it {#sprint-6-wrong}

- **The runner's disk filled up.** Fixed the same morning; the runner now cleans up after each job. The lesson for
  administration is in [[admin]]: a runner is a server, and servers need the same care as anything else.
- **A personal access token was committed.** Caught by the pipeline before it reached `develop`; revoked, replaced
  with a masked project token, history rewritten. The retrospective made it a rule: no tokens in scripts, even
  test ones ([[security]]).
- **A story was committed that could not finish.** BuoyModes, planned across Bob's leave ([[sprint-6-carry]]).
- **A drafting tool nearly misreported a measure to management.** Corrected before the review
  ([[sprint-6-number]]).
- **A requirement's text was changed by accident.** Bob's edit to TW-SYS-007 in !23, caught by the trace ratchet
  in a draft merge request, before any reviewer saw it.

None of these reached the model on `develop`. In the document era, the same five mistakes -- a lost day of work, a
leaked credential, an over-committed plan, a misleading slide, an altered requirement -- would have surfaced, if at
all, at the next milestone review.

=== You can now... {#sprint-6-can}

::: note You can now...
- Cut a baseline through a release branch, record the CCB's concurrence on the merge request, tag it, and read the
  pipeline's proof that it rebuilds identically.
- Tell verify coverage (a case exists) from verification status (a verdict exists), and keep them apart in a
  briefing.
- Respond to a committed credential in the right order: revoke, replace, rewrite.
- Generate a document -- the data exchange table -- from the model, with its assumptions visible.
- Read a sprint plan and spot the task that cannot finish before the sprint starts.
:::

=== Applying this to your project {#sprint-6-apply}

- **End your first twelve weeks with a baseline.** A tagged, reproducible, CCB-approved version is the thing
  management can hold; everything else is a promise.
- **Put the CCB's approval where the engineering approvals are.** A comment on the release merge request is a
  record nobody can lose and everybody can find.
- **Introduce a new measure next to the old one, never in its place.** Name both; explain the difference once.
- **Make assumptions part of the generated documents.** An assumption in the model's doc text shows up in every
  table the pipeline builds, until somebody confirms it.
- **Plan around leave and holidays before the sprint, not at the review.** A carryover you could see on day one is a
  planning error, not bad luck.
