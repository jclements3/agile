# Halberd -- a notional SysML v2 example model

**Halberd is fictional, notional and unclassified.** It is an interceptor program (an integrated
air and missile defense capability) used across this kit as the running example: the IDEF0
program model in `tools/idef0/examples/halberd/halberd.md`, the 12-week port in
`docs/STATUS-METRICS.html` (Appendices C and D), and this SysML v2 text model. It contains no
performance parameters, no design data and no real program information; every value is structural.
Names are generic on purpose.

The model exercises every tool in the kit that reads SysML: `tools/sysml/model.pl`,
`tools/sysml/sysml.pl`, the IDEF0 toolkit (through the generated `docs/idef0/`), the planning
bridge `sim/idef0-backlog.pl`, the status-metrics collector `bin/status-metrics.pl`, and the
XMI/ReqIF importers `bin/xmi2sysml.pl` / `bin/reqif2sysml.pl`.

## Layout

    examples/halberd/
      sysml.conf        the roots of the noun and verb trees and the IDEF0 settings (tools/sysml/README.md)
      CODEOWNERS        one line per segment folder, a generic role handle each
      model/<segment>/  the model: one folder per segment, one top-level package per file
      docs/             generated by 'perl tools/sysml/model.pl docs' -- do not edit by hand

One segment folder per Halberd organization (the seven models of `halberd.md`):

| folder | letter | organization | what it holds |
|---|---|---|---|
| `model/program/` | G | Government Program Office | the enterprise (top of the part tree) and what each segment satisfies; the stakeholder needs |
| `model/engineering/` | E | Systems Engineering & Integration | conventions (level tags), the SecMeta security library (markings, zones, threats), the system context and allocations, ports and interface definitions, system requirements, the sensor segment, the threat register |
| `model/interceptor/` | V | Interceptor Development | the interceptor segment, the round and its assemblies, interceptor requirements |
| `model/firecontrol/` | B | Battle Management & Fire Control | the fire control segment and software, the kill chain (the verb tree) and its flows, fire control requirements |
| `model/test/` | T | Test & Evaluation | the test and training segment, test requirements, and every verification case |
| `model/production/` | M | Manufacturing & Production | the launch segment (launchers and canisters), production requirements |
| `model/sustainment/` | L | Logistics & Sustainment | the support segment, sustainment requirements |

What is in it: 29 files, 36 packages (one is the SecMeta security library); a 6-level part tree (65 part defs, 2 to 9 children at every
level, each tagged `@L1Enterprise` ... `@L6Component`); the kill chain -- detect, track, identify,
decide, engage, assess -- as 22 action defs, 4 levels deep, each with one `out result`; 21 flow
items; 5 port and 4 interface definitions; 66 requirements (8 stakeholder needs, 29 system,
29 segment), each with a DOORS id (`HAL-STK-001`, `HAL-SYS-001`, `HAL-BMF-001`, ...); 63 satisfy
and 62 verify relationships; 15 verification cases owned by Test & Evaluation; 6 segment-boundary
crossings with their security zones; 7 threats with their mitigations.

**Gaps planted on purpose,** so the trace and the status metrics have something to show:

- 3 requirements nothing satisfies (orphans, metric F): `sysX07` common time, `prdR05`
  counterfeit-part prevention, `susR05` field reliability data;
- 4 requirements no verification case verifies (metric G): `sysL06`, `fcR08`, `intR06`, `tstR03`;
- 1 zone crossing with no security requirement covering it (metric Q): the link to the adjacent
  defense unit;
- 2 threats without a mitigation (metric R): counterfeit part, insider misuse.

## Running the tools on it

From the kit root (or `cd examples/halberd` and drop `--root examples/halberd`: model.pl finds the
project upward from any folder inside it).

**Syntax, against the official grammar**

    $ perl tools/sysml/sysml.pl check examples/halberd/model/*/*.sysml
    sysml: 29 file(s), 0 error(s)

**Lint and the outline rule**

    $ perl tools/sysml/model.pl --root examples/halberd lint
    lint: 29 file(s), 0 error(s), 0 warning(s)
    elements=226 errors=0 warnings=0

    $ perl tools/sysml/model.pl --root examples/halberd check

    == Level tags ==
    @L tag mismatches         0

    == Outline (2..9 children per parent) ==
    violations                0

`stats` adds the counts and both trees' depth (nouns: `HalberdEnterprise > InterceptorSegment >
InstrumentedTestRound > KillVehicle > Seeker > SeekerOptics`, L1=1, L2=6, L3=13, L4=30, L5=8, L6=3;
verbs: `DefendAgainstThreat > Engage > GuideInterceptor > UplinkTrackUpdates`).
`nouns --plain` and `verbs --plain` print the trees.

**Traceability**

    $ perl tools/sysml/model.pl --root examples/halberd trace
    trace: 66 requirements (66 leaf), 3 not satisfied, 4 not verified -> docs/Traceability.md
      HAL-SYS-016: not satisfied
      HAL-SYS-035: not verified
      HAL-BMF-008: not verified
      HAL-INT-006: not verified
      HAL-PRD-005: not satisfied
      HAL-SUS-005: not satisfied
      HAL-TST-003: not verified

`trace --strict` exits 1 on those gaps (for a CI gate once they are closed).

**Generated documents and the IDEF0 set**

    $ perl tools/sysml/model.pl --root examples/halberd docs
    wrote docs/Nouns.md (64 lines)
    wrote docs/Verbs.md (22 lines)
    wrote docs/idef0/KillChain.md
    1 file(s): 0 error(s), 0 warning(s), 6 model(s), 15 activities, 7 link(s)
    wrote docs/idef0/plates.html
    wrote docs/idef0/INTERFACES
    wrote docs/idef0/svg/plate-D0.svg  (and T0, I0, C0, E0, A0)
    trace: 66 requirements ...

`docs/idef0/KillChain.md` is the kill chain as a literate IDEF0 model set, one model per step
(D Detect, T Track, I Identify, C Decide, E Engage, A Assess, per `steps` in `sysml.conf`):
boxes are the action defs, inputs and controls their parameters (`control_types`), outputs their
results, mechanisms the parts the `allocate` statements in `engineering/Context.sysml` name, and
hand-offs between steps cross-model links. The kit's IDEF0 toolkit reads it directly:

    $ perl tools/idef0/idef0.pl lint examples/halberd/docs/idef0/KillChain.md
    1 file(s): 0 error(s), 0 warning(s), 6 model(s), 15 activities, 7 link(s)
    $ perl tools/idef0/idef0.pl text  examples/halberd/docs/idef0/KillChain.md    # plates as text
    $ perl tools/idef0/idef0.pl links examples/halberd/docs/idef0/KillChain.md    # the 7 hand-offs
    $ perl tools/idef0/idef0.pl dump  examples/halberd/docs/idef0/KillChain.md    # the numbered tree

**The planning backlog**

    $ perl tools/sysml/model.pl --root examples/halberd backlog --date 2026-10-05
    2026-10-05
    sprint 1

    == Assess
    new A-1 8 Judge Engagement p:1 e:"A1 Judge Engagement" t:"A Assess" o:"Ann Assess"
    ...
    == Engage
    new IF-2 5 Interface: Engagement Plan from Decide to Engage p:1 e:"C3 Schedule Engagements" ...

That is `sim/idef0-backlog.pl` on the IDEF0 set: one team per step, an epic per function, a task
per leaf, and an interface task in the receiving team for every hand-off -- a stand-up file the kit
compiles into a journal (`daily.pl compile`).

**Security markings, trust zones, threats -- and the gate**

`model/engineering/SecMeta.sysml` is the security vocabulary the views toolkit reads (`tools/sysml/views/`, a copy of
its `library/SecMeta.sysml` with the status-metrics threat attributes). Every root package carries
`@Marking { level = Level::U; }`, except `SystemVerification` and `AcceptanceTests`, marked `CUI` -- notional labels
only, everything here is notional and unclassified -- so the no-write-down check has something to check (no U package
depends on them). `@TrustZone` sits on the parts at a boundary: the enterprise (trusted), the launcher (dmz), the round
in flight, the higher command, the adjacent unit and the threat (untrusted). The security requirements `secR01`-`secR07`
carry `@SecurityRequirement`, and five of them `@Mitigates { threat = "..."; }`; each crossing names its covering
requirement in `secReq`; each threat line has a STRIDE category and a CAPEC id.

    $ perl tools/sysml/model.pl --root examples/halberd draw ibd       # ibd.svg; also tree, trace, pkg
    $ perl tools/sysml/model.pl --root examples/halberd threats --today 2026-10-05
    $ perl tools/sysml/model.pl --root examples/halberd gate --today 2026-10-05
    ...
    check: 5 check(s) run, 10 error(s), 0 warning(s) -> FAIL

The gate fails on exactly the planted gaps: 7 trace errors (the 3 orphans and 4 unverified requirements above), 1 zone
crossing (`ifcAdjacentUnit`), 2 open threats (`counterfeitPart`, `insiderMisuse`); markings and text are clean. The
four views are committed as `docs/img/halberd-{tree,trace,ibd,pkg}.svg` in the kit (`perl sim/halberd-views.pl`).

**Vim**

Open any `.sysml` file under `examples/halberd/`: `:make lint` / `:make check` fill the quickfix
list; `\ml \mk \mx \mv \md \mr \mn \mb \mt` run lint, check, this file's syntax, validate, docs,
trace, nouns, verbs and tags; `\mw \mq \mi \mp` draw the views, `\mg` runs the gate, `\mW` opens the live viewer. Run `perl tools/sysml/model.pl --root examples/halberd tags` once
(it writes `examples/halberd/tags`), then Ctrl-] on any name or DOORS id jumps to it.

**Full compile (optional, needs Java)**

    $ perl tools/sysml/model.pl --root examples/halberd validate
    validate: compiling 29 files with the Pilot engine (...-all.jar) ...
    validate: 29 file(s), 0 error(s), 0 warning(s)

With Java and the SysML v2 Pilot jar the whole model, names and types included, compiles clean.
Without them `validate` says what is missing and exits 3; `lint` covers the same ground offline.

**The status-metrics collector**

The model follows the line conventions `bin/status-metrics.pl` reads (Appendix A of
`docs/STATUS-METRICS.html`): one-line `requirement name { attribute doorsId = "..."; ... }`,
`satisfy name by ...;` and `verify name;` on their own lines, one-line
`interface name { ... attribute fromZone = "..."; attribute toZone = "..."; attribute secReq = "..."; }`
crossings, one-line `metadata name : Threat { asset = "..."; mitigation = "..."; }` threats,
`model/<segment>/` folders and a `CODEOWNERS` line per folder -- all of it valid SysML v2. To run it,
the example has to be a git repository with the exports beside it:

    mkdir -p /tmp/hal/exports && cp -r examples/halberd /tmp/hal/repo
    git -C /tmp/hal/repo init -q -b main && git -C /tmp/hal/repo add -A && git -C /tmp/hal/repo commit -qm 'Halberd'
    # exports/export.reqif (the DOORS export) and exports/legacy.xmi (the v1 model) set C's and A's denominators
    # metrics.json: "repo": "repo", "exports": "exports", "segments": 7,
    #               "lint_cmd": ["perl", "<kit>/tools/sysml/model.pl", "lint"], ...
    perl bin/status-metrics.pl init    --config /tmp/hal/metrics.json --xmi /tmp/hal/exports/legacy.xmi --reqif /tmp/hal/exports/export.reqif
    perl bin/status-metrics.pl collect --config /tmp/hal/metrics.json --history /tmp/hal/history.jsonl
    perl bin/status-metrics.pl report  --config /tmp/hal/metrics.json --history /tmp/hal/history.jsonl --out /tmp/hal/report

With a ReqIF export holding exactly the model's 66 DOORS ids and a 300-element legacy XMI, the
model's rows of the weekly table read:

    | A | % under configuration control | 75 |       226 elements of 300
    | B | Segments gated (of 7) | 7 |
    | C | Requirements linked (of 66) | 66 |
    | E | Lint errors / warnings | 0/0 |
    | F | Orphan requirements | 3 |
    | G | Unverified requirements | 4 |
    | I | Trace completeness % | 89 |
    | Q | Uncovered zone crossings | 1 of 5 |
    | R | Unmitigated threats | 2 of 7 |

**The XMI and ReqIF importers**

`bin/xmi2sysml.pl` turns a SysML v1 XMI export into `model/<segment>/<Package>.sysml` files of
this shape (`--req-style usage` for the one-line requirements above, `--check` runs `sysml.pl` on
the output); `bin/reqif2sysml.pl` does the same for a DOORS ReqIF export, and with
`--report --model examples/halberd/model` it reports which DOORS ids of an export the model links,
leaves orphaned or unverified (metrics C, F, G, I).

## Changing it

Edit a `.sysml` file, then `model.pl lint`, `model.pl check`, `model.pl docs` and commit the
regenerated `docs/` with the change (`tests/sysml.t` fails if `docs/` is stale; in a project of
its own, `model.pl install-hooks` makes git refuse stale docs). `model.pl new part NAME --in
PARENT` and `model.pl new verb NAME --in PARENT --takes 'x:T' --returns T` scaffold; `model.pl
rename OLD NEW --write` renames everywhere.
