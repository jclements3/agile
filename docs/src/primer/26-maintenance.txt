== Maintenance through the life cycle {#maintenance}

::: survival Staying current for eighteen months
What you have: a SysML v2 model under configuration control, a pipeline that checks every change, an interim
baseline, and a prime contractor who will keep delivering changes to the old SysML v1 model for as long as the
contract runs.

What you need: a routine that takes each new drop in without drama, cuts baselines on a schedule, fixes an urgent
error in a released baseline without waiting for the next one, and keeps the change board, the discrepancy reports
and the archive in order -- until the day the model is retired.
:::

The first twelve weeks were a port. Everything after them is maintenance: the steady work of keeping the
government's SysML v2 model equal to the system the prime is building, while the engineering on top of it grows.
On Tidewater that is thirty-three more sprints, six more prime drops, three baselines and one hotfix. This chapter
is the routine for that period, shown end to end on real drops in a sandbox you build yourself.

::: note What is evidence and what is plan in this chapter
Sprints 1 to 6 of Tidewater have been simulated and their evidence is in `docs/tidewater/`. Sprints 7 to 39 have
not run yet. In this chapter the prime's drops are real (each one is generated by `sim/tidewater-v1.pl`, with its
manifest and change requests), and every command runs on them. What the team does in sprints 7 to 39, and when, is
taken from the team's plan, `sim/tidewater-plan.pl`, and is marked **From the plan**. A later edition replaces those
passages with the simulated sprints' evidence.
:::

=== The drop intake runbook {#maintenance-runbook}

[[prime-changes]] explains each step of the drop loop and why it exists. Here is the routine as a team runs it every
quarter, start to finish, on a project you build in the sandbox. It takes the first drop through the project's
week zero, then takes the second drop through the full loop.

First, the project. `kickoff.pl start` is the week-zero sequence from [[playbook]]; with the layout map it puts every
prime package into the layered folders from the first drop:

```sh run expect="week zero is set up" timeout=300
perl "$KIT/tools/gitlab/kickoff.pl" start --yes --local gitlab --drop drops/v1 --version v1.0 \
    --layout-map "$KIT/examples/tidewater-v1/layout.map" --no-wiki --no-issues > start.log 2>&1
grep "week zero is set up" start.log
cat > env.sh <<EOF
export GITLAB_LOCAL="$PWD/gitlab" GITLAB_PROJECT=tidewater/model
gl() { perl "\$KIT/bin/gitlab.pl" "\$@"; }
EOF
```

`env.sh` gives you the `gl` shortcut for the project's GitLab (here the kit's offline stand-in). In a real terminal
you source it once; the blocks below each start with `. ../env.sh` because each one is tested on its own.

Week zero left drop 1 on its own branch, `feature/drop-v1.0`, ready for review. The prime's structure arrives all at
once, and with it the prime's outline violations (packages with one member, folders with one file). The government
did not make them and does not fix them in the drop's merge request. It records them, so that from now on the
outline gate fails only on violations the government adds:

```sh run cwd=model expect="merged as" timeout=300
. ../env.sh
n=$(perl ci/job.pl outline 2>&1 | sed -n 's/^outline violations: \([0-9]*\).*/\1/p')
echo "$n" > .ci/outline-max
git commit -qam "Record the outline allowance the prime's drop 1 brought in ($n)"
gl --as tom flow finish --title "Prime drop v1.0 (NWM-CR-0001)"
gl --as jim mr approve 1
gl --as bob mr approve 1
gl --as tom mr merge 1
```

Tom opened the merge request; Jim and Bob approved it. The project's approval rule wants one reviewer, the
interface files want a code owner other than the author (Bob), and no one approves their own change. That is the drop loop's first pass. The second drop shows every step.

**1. Receive and verify.** The drop arrives (by file transfer in the first months, later from the prime's Jenkins,
see [[jenkins]]). Before anything else, check that every file is the file the prime sent:

```sh run cwd=drops/v2 expect="tidewater.xmi: OK"
tr -d '\r' < MANIFEST.txt | sed -n 's/^  \([0-9a-f]\{64\}\)  \(.*\)$/\1  \2/p' | sha256sum -c
```

The manifest is written with Windows line endings, so `tr` strips them before `sha256sum` reads the list.
A failed check stops the intake: the drop goes back to the prime with a request to resend, and nothing is imported.

**2. Assess the impact against the government's model, before importing.** Run the impact report on `develop`, the
model as the government has it today. Run it before the import: on the drop's own branch, the drop's changes are
already in the files and the report mistakes them for government edits.

```sh run cwd=model expect="hand edits to redo +0" timeout=180
. ../env.sh
gl flow sync
git checkout -q develop
perl "$KIT/bin/xmi2sysml.pl" --delta ../drops/v1/tidewater.xmi ../drops/v2/tidewater.xmi \
    --impact model --layout-map .ci/layout.map > ../impact-v1.1.txt 2>&1
grep -E "^== NWM|touched|change requests|hand edits" ../impact-v1.1.txt
```

The report groups the changes by the prime's change requests and lists, for each, the requirements, verification
cases, interfaces and allocations it touches. "Hand edits to redo" is the line that matters most in maintenance:
every TODO the government closed by hand, and every definition it edited, that the drop changes underneath. Here it
is zero, because this sandbox's model has no hand edits yet; on Tidewater's real `develop` the drop 3 report flags
the hand-written state machine, because the prime added a storm mode the converter cannot carry ([[prime-changes]]
shows that run).

**3. Disposition.** Each significant change request becomes an issue with a `disposition::` label, decided at the
change board ([[maintenance-ccb]]). Nothing is merged before its disposition.

**4. Import on the vendor branch and merge the drop into a feature branch.** `flow vendor` converts the drop, commits
the raw conversion on `vendor/prime` (never edited by hand), and merges it into `feature/drop-v1.1`, listing any
conflicts:

```sh run cwd=model expect="merged as" timeout=300
. ../env.sh
gl --as tom flow vendor ../drops/v2 v1.1
perl "$KIT/tools/sysml/model.pl" docs > /dev/null
git add -A docs
git commit -qm "Regenerate docs for prime drop v1.1"
gl --as tom flow finish --title "Prime drop v1.1 (NWM-CR-0012 to 0014)"
gl --as jim mr approve 2
gl --as bob mr approve 2
gl --as tom mr merge 2
```

Two lines in that block are the lessons of past drops. The docs are regenerated on the drop's branch, because the
documents are generated from the model and kept in the repository: a drop changes the model, so it changes the
documents, and the pipeline's docs job refuses a merge request whose documents are stale. And the outline allowance
is checked again whenever a drop adds structure; this drop added none.

**5. Rework.** Conflicts and hand edits to redo become tasks on the drop's story, and the government's edits are
re-applied on top of the prime's new text ([[prime-changes]] and practice lesson 12 show a conflict resolved in Vim).

**6. Close the loop.** Close the Prime Drop issue, close the discrepancy reports the drop answers, open new ones for
what it got wrong, and record the drop latency (delivered to merged on `develop`) for the monthly status.

::: checklist The drop intake runbook
[ ] Checksums verified against the manifest; markings checked; the drop archived as received
[ ] Prime Drop issue opened with the transmittal record and the change requests listed
[ ] Impact report run on develop, before the import; attached to the issue
[ ] Every significant change request dispositioned at the CCB (disposition:: label, deputy PM concurrence)
[ ] flow vendor: raw conversion on vendor/prime; merged into feature/drop-VERSION
[ ] Conflicts resolved by taking the prime's text and re-applying the government's edits
[ ] Hand edits to redo done as tasks; docs regenerated; outline allowance recorded if the drop added structure
[ ] Merge request green, approved by two people other than the author, merged to develop
[ ] DRs answered by the drop closed; new DRs opened; Prime Drop issue closed; latency recorded
:::

**From the plan:** the drops' latency is a measured result of sprints 7 to 39 and is reported in a later edition. The
plan's target is that a drop is merged on `develop` within its sprint, and from drop 4 on (sprint 17's intake
automation) within days of delivery.

=== Baselines and releases {#maintenance-baselines}

A baseline is the configuration the program agrees to stand behind: the model, its generated documents, its
verification matrix and the tools that produced them, all at one commit, tagged and published. Tidewater plans
four: baseline-0 (the interim baseline at the end of the first twelve weeks, sprint 6), baseline-1 (port acceptance,
sprint 20), baseline-2 (sprint 30) and baseline-3 (the end of the eighteen months, sprint 39).

Every baseline follows the same path through gitflow: a release branch from `develop`, a changelog section, a merge
request to `main` with the change board's concurrence, a tag, a release, and a back-merge so `develop` has
everything `main` has. Cut baseline-1 from the two drops now on `develop`:

```sh run cwd=model expect="back-merge" timeout=300
. ../env.sh
gl flow sync
git checkout -q develop
gl --as tom flow start release baseline-1
perl -0pi -e 's/^\[Unreleased\]: /## [baseline-1] -- 2027-07-02\n\n### Prime drops merged\n\n- v1.0 (NWM-CR-0001) and v1.1 (NWM-CR-0012 to 0014)\n\n[Unreleased]: /m' CHANGELOG.md
git commit -qam "Changelog for baseline-1"
gl --as tom flow finish --title "Baseline 1"
gl --as jim mr approve 3
gl --as bob mr approve 3
gl --as tom mr merge 3
gl --as tom flow released 3
```

Tom prepared the baseline; Jim and Bob approved it. On Tidewater the release merge request also carries the deputy
program manager's concurrence as a comment: in GitLab terms that comment is the change board's signature
([[maintenance-ccb]]). `flow released` then tags `main` as `baseline-1` (the tag's message records the checksum of the
generated documents), publishes the release, and opens the back-merge request to `develop`:

```sh run cwd=model expect="merged as" timeout=300
. ../env.sh
gl --as jim mr approve 4
gl --as bob mr approve 4
gl --as tom mr merge 4
```

The tag's pipeline did the rest. The `baseline` job rebuilt the documents and checked their checksum against the
tag, which is the physical configuration audit done by machine. The release jobs published the baseline as a
package, so other teams can take a versioned copy without access to the repository:

```sh run cwd=model expect="tidewater-model/baseline-1"
. ../env.sh
gl package list
gl pipeline list | grep baseline-1
```

The package holds the model and documents as a tarball, the verification matrix, the toolchain inventory (which
versions of the kit, Perl and git produced the baseline) and a checksum file. The release links to each of them and
names the sprint milestones it closes; GitLab keeps the release's evidence (the milestones' issues and the test
report at release time) with it.

::: tip The release branch is the last place to fix, not to change
A release branch takes only fixes that make the baseline correct: a changelog line, a missing document, an outline
allowance a drop should have recorded. New work goes to `develop` and waits for the next baseline. If a fix is
needed on the release branch, it goes back to `develop` in the back-merge, so nothing is lost.
:::

**From the plan:** baseline-1 at sprint 20 also carries the port completeness report ([[proving]]) and the deputy
program manager's sign-off of the port; baseline-2 at sprint 30 is the first with signed tags ([[security]]) and
retires the prime's legacy test matrix for Stations ([[verification]]); baseline-3 closes the eighteen months.

=== Hotfixes {#maintenance-hotfix}

Sometimes a released baseline is wrong in a way that cannot wait for the next one. **From the plan:** in sprint 24
the program office finds a satisfy relationship in baseline-1 that points at the wrong element. The fix goes on a
hotfix branch from `main`, is merged to `main` as a patch baseline, and is merged back to `develop`:

```sh run cwd=model expect="merged as" timeout=300
. ../env.sh
gl flow sync
git checkout -q main
gl --as tom flow start hotfix sys-007-satisfy
sed -i 's/satisfy TW_SYS_007 by BulletinPublisher;/satisfy TW_SYS_007 by DataSegment::publicOut;/' \
    model/requirements/model/Requirements.sysml
perl "$KIT/tools/sysml/model.pl" docs > /dev/null
git add -A model docs
git commit -qm "Satisfy TW-SYS-007 by the public interface, not the publisher"
gl --as tom flow finish --title "Hotfix: TW-SYS-007 is satisfied by the public interface"
gl --as jim mr approve 5
gl --as bob mr approve 5
gl --as tom mr merge 5
gl --as tom flow released 5 --tag baseline-1.1
gl --as jim mr approve 6
gl --as bob mr approve 6
gl --as tom mr merge 6
```

Two things are easy to miss. The satisfy line lives in a file the converter writes from the prime's model, so the
hotfix is also a discrepancy report to the prime: unless the prime corrects its v1 model, the next drop puts the
wrong satisfy back, and the impact report will flag it as a hand edit to redo. And the patch baseline gets its own
tag, `baseline-1.1`, so anyone holding baseline-1 knows a corrected version exists.

=== The change board in GitLab {#maintenance-ccb}

Tidewater's change control board did not go away; it moved. The board's decisions are now records in GitLab:

|| Board activity | Where it lives in GitLab ||
| An engineering change proposal | A merge request, with the impact report attached |
| A prime change request to disposition | A `prime-change` issue with a `disposition::` label: accept, accept with impact, reject or clarify, no impact |
| The board's approval of a baseline | The deputy program manager's concurrence comment on the release merge request |
| The board's agenda | The open `prime-change` issues and release merge requests, listed by `gl issue list --label prime-change` |
| The minutes | The issues' and merge requests' comment threads, kept forever |
Table: The change board's records, before and after

The board meets once a month (the plan's "Monthly status and CCB items" story, every other sprint). Most decisions
are quick, because the impact report has already done the analysis a board used to spend its meeting on. The ones
that take time are the ones that should: a change with cost or schedule impact, or a change the prime made without
a reason. **From the plan:** drop 5's rename comes with no rationale; the board dispositions it "reject, clarify",
sends a discrepancy report asking why, and closes it when drop 6 answers. Drop 4's drifting buoys are "accept with
impact": they add verification work, and the board records the cost.

=== Discrepancy reports, upstream and back {#maintenance-drs}

A discrepancy report is the government's formal question to the prime about its model: a requirement nothing
satisfies, a wording difference between DOORS and the model, a duplicate block, a change with no reason. On
Tidewater they are GitLab issues labelled `type::discrepancy` and `owner::prime`, sent through the contracting
channel with a transmittal memo ([[memos]]), and kept open until a drop answers them.

The drops show the loop working. Drop 2's NWM-CR-0014 aligns TW-SYS-006 with DOORS, closing the first drift the
team found in sprint 1. Drop 3's NWM-CR-0018 and 0019 answer the reports about TW-SYS-012 and the duplicate
SensorSuite. Drop 4's NWM-CR-0022 brings TW-SYS-016 into the model. Drop 6's NWM-CR-0028 deletes the Legacy Import
package the team untangled in sprint 5. Each change request names the report it answers in its rationale, which
is why the team asked for change notes in week zero.

=== The life cycle beyond the port {#maintenance-lifecycle}

Tidewater's eighteen months sit inside a longer life. The same repository, pipeline and routine serve every phase;
what changes is where the pipeline's emphasis sits:

|| Phase | Repository activity | Pipeline emphasis ||
| Concept | Stakeholder needs, use cases, early trades | Validation, trade analysis |
| Requirements (to SRR) | Requirement models, satisfy links | Trace coverage, completeness, the recipe |
| Architecture (to PDR) | Structure, interfaces, behavior | Interface consistency, budgets, the data exchange table |
| Detailed design (to CDR) | Refined parts, parameters | Full analysis, simulation hooks |
| Integration and test | Verification cases, results linked back | The verification matrix, results ingestion ([[verification]]) |
| Production and sustainment | One configuration per fielded block | Change impact on old baselines, fixes upstream first |
Table: The life cycle and the pipeline's emphasis

Tidewater uses gitflow, with baselines as releases on `main`. When a program fields several configurations at once
(block 1 in service while block 2 is designed), the alternative is a long-lived release branch per fielded
configuration, cut from its baseline tag: fixes land on `develop` first and are cherry-picked onto each fielded
branch that needs them. That is GitLab flow's release-branch variant, and the choice is worth a decision record
the day the second configuration is fielded.

=== Retirement and archival {#maintenance-retirement}

Every model ends. The prime's contract closes, the system leaves service, or a successor model takes over. Plan the
end while the team still remembers how everything works:

- **Freeze.** Cut a final baseline, protect every branch so nothing more can merge, and archive the GitLab project
  (archived projects are read-only and stay searchable).
- **Keep what an auditor will ask for.** The baseline packages, the release evidence, the toolchain inventory and
  the drops as received are formal records; their retention is set by the program's records schedule, not by
  GitLab's default artifact expiry. Copy them to the program's records system with their checksums.
- **Keep the tools that read them.** A tagged copy of the kit (the slim `release.pl --profile mbse` zip) beside the
  archive means the model can be checked and its documents rebuilt years later, on whatever Perl is current then.
- **Hand over or shut down.** Transfer the project to its successor, or revoke every token, remove the runners and
  close the schedules (a schedule runs as its owner: an owner who leaves stops it, which is the one clean-up that
  happens by itself).
- **Write it down.** The runbook and lessons learned are the plan's last story (sprint 39). The next team that ports
  a model will read them before they read this book.

=== Applying this to your project {#maintenance-apply}

- Make the drop loop a checklist on day one and run it the same way every time; the second drop is where teams
  either have a routine or have a crisis.
- Run the impact report on your integration branch before the import, never on the drop's branch.
- Record inherited counts (outline, complexity, trace gaps) in the drop's merge request so the gates measure only
  what your team adds.
- Baseline on a calendar the program understands (milestones, quarters), and publish each baseline as a package
  with its toolchain inventory.
- Put the change board's decisions in the issues and merge requests; the board's minutes then write themselves.
- Plan retirement before the people who built the model move on.

=== You can now... {#maintenance-can-now}

- take a prime drop from delivery to merged: checksums, impact report on develop, disposition, vendor import,
  regenerated documents, two approvals;
- record what a drop brings in so the gates measure only your team's changes;
- cut a baseline, publish it as a package with its toolchain inventory, and merge it back to develop;
- ship a hotfix to a released baseline and tell the prime why it must change its model too;
- run the change board in GitLab, and plan the model's archival.
